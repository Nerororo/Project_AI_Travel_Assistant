# ADR-001 - 도메인 중심 패키지 구조 사용

## 상태

Accepted

## 문제

Spring 프로젝트를 처음 학습하는 단계에서 다음 두 가지 패키지 구조를 고려했다.

### 선택지 A

계층 중심:

```text
controller/
service/
repository/
domain/
```

### 선택지 B

도메인 중심:

```text
place/
travelplan/
route/
ai/
recommendation/
```

## 결정

도메인 중심 패키지를 사용한다.

각 도메인 안에서 필요한 Controller / Service / Repository / DTO를 둔다.

## 이유

프로젝트 기능이 여행지, 여행 계획, 추천, 경로, AI 등으로 명확하게 나뉘며 프로젝트가 커졌을 때 관련 코드를 한 곳에서 찾기 쉽다.

## 재검토 조건

도메인 규모가 매우 커져 더 세밀한 모듈화가 필요해질 경우 재검토한다.

# ADR-002 - 관광지 / 호텔 / 음식점을 Place로 통합

## 상태

Accepted for MVP

## 문제

다음 Entity를 각각 만들 수 있다.

```text
Attraction
Hotel
Restaurant
Cafe
```

하지만 공통적으로 이름, 주소, 좌표 같은 속성을 가진다.

## 결정

초기 MVP에서는 `Place` Entity로 통합하고 `PlaceType`으로 구분한다.

```text
ATTRACTION
HOTEL
RESTAURANT
CAFE
```

## 이유

- 중복 필드 감소
- 거리 계산 로직 재사용
- 첫 Spring 프로젝트의 복잡도 제어
- 여행 일정에서 모든 장소를 동일한 위치 객체로 다루기 쉬움

## 단점

호텔 가격이나 음식점 메뉴 등 타입별 특성이 증가하면 Place가 비대해질 수 있다.

## 재검토 조건

장소 유형별 전용 속성과 비즈니스 규칙이 크게 증가하면 Detail Entity 또는 별도 Entity 분리를 검토한다.

# ADR-003 - AI와 경로 최적화 책임 분리

## 상태

Accepted

## 문제

LLM에게 "최적의 여행 일정을 만들어줘"라고 요청하면 구현은 간단하지만 실제 거리 계산의 정확성, 재현성, 테스트 가능성을 보장하기 어렵다.

## 결정

AI는 자연어 이해와 후보 추천을 담당한다.

경로 계산과 최적화는 Java 백엔드 알고리즘이 담당한다.

## 이유

- 결과가 결정적이고 테스트 가능함
- 실제 좌표 데이터를 기준으로 계산 가능
- 알고리즘 개선을 측정할 수 있음
- 백엔드 프로젝트로서 기술적 깊이를 확보할 수 있음

---

# ADR-004 - 경로 최적화 1차 구현은 Nearest Neighbor

## 상태

Accepted

## 문제

여러 여행지를 방문하는 이동 경로 최적화는 TSP와 유사하다.

첫 구현부터 최적해 알고리즘을 적용하면 학습 / 구현 복잡도가 증가한다.

## 결정

첫 버전은 Nearest Neighbor를 사용한다.

## 이유

- 구현이 단순함
- Greedy Algorithm 학습 가능
- 시간 복잡도 설명이 쉬움
- 이후 개선 기준선(Baseline)으로 사용 가능

## 재검토 / 개선

Nearest Neighbor 완료 후 2-opt를 적용하여 경로 개선 정도를 측정한다.

# ADR-005 - 호텔 추천은 이동 거리 합을 첫 기준으로 사용

## 상태

Accepted for MVP

## 문제

호텔 추천에는 가격, 평점, 편의시설 등 많은 요소가 있다.

모든 요소를 처음부터 적용하면 추천 기준이 불명확해지고 구현 범위가 커진다.

## 결정

MVP에서는 호텔과 선택 여행지 사이의 총 이동 거리를 핵심 점수로 사용한다.

```text
HotelScore = Σ distance(hotel, selectedPlace)
```

## 이유

이 프로젝트의 핵심 가치 중 하나가 "여행 동선 최적화"이므로 추천 기준과 프로젝트 목적이 일치한다.

## 재검토 조건

핵심 기능 완성 후 가격 / 평점 등의 가중치를 추가할 수 있다.

---

# ADR-006 - 음식점 추천은 음식 일치 + 동선 이탈을 우선

## 상태

Accepted for MVP

## 문제

맛집 추천은 평점만 사용하면 여행 경로를 크게 벗어나는 식당이 추천될 수 있다.

## 결정

MVP에서는 다음 두 요소를 우선한다.

1. 사용자가 원하는 음식과의 일치
2. 기존 여행 경로에서 발생하는 이탈 거리

## 이유

서비스의 핵심인 여행 동선 최적화와 음식 추천을 결합할 수 있다.

## 개선

향후 다음 요소를 추가할 수 있다.

- 평점
- 리뷰 수
- 영업시간
- 가격대

# ADR-007 - Spring Security는 핵심 여행 기능 이후 구현

## 상태

Accepted

## 문제

Spring 학습 초기부터 Security / JWT를 도입하면 인증 설정 학습 때문에 여행 서비스의 핵심 로직 개발이 지연될 수 있다.

## 결정

다음 핵심 흐름을 먼저 완성한다.

```text
Place
→ TravelPlan
→ AI
→ Route
→ Hotel
→ Restaurant
```

이후 User / Security를 추가한다.

## 이유

첫 프로젝트의 학습 위험을 낮추고 핵심 도메인을 먼저 완성하기 위해서다.

# ADR-008 - 외부 API Key는 환경변수로 관리

## 상태

Accepted

## 문제

DB Password, OpenAI API Key 등을 코드나 Git Repository에 저장하면 보안 문제가 발생한다.

## 결정

민감 정보는 환경변수 또는 `.env`를 사용한다.

`.env`는 `.gitignore`에 포함한다.

## 이유

Credential의 Git 노출을 방지하기 위해서다.

# ADR-009 - 실제 도로 거리 API는 초기 MVP 이후 검토

## 상태

Proposed

## 문제

직선 거리와 실제 도로 이동 거리 / 시간은 다르다.

하지만 초기부터 외부 지도 API까지 도입하면 API 정책, 비용, 인증, 데이터 변환까지 동시에 학습해야 한다.

## 결정

Phase 5의 첫 구현에서는 위도 / 경도를 이용한 서버 내부 거리 계산으로 알고리즘을 검증한다.

핵심 경로 로직이 안정화된 후 실제 지도 / 길찾기 API를 검토한다.

## 이유

문제를 다음 두 단계로 분리하기 위해서다.

```text
1. 경로 알고리즘이 올바른가?
2. 실제 이동 데이터를 연결할 수 있는가?
```

## 재검토 조건

호텔 및 여행 경로 추천의 현실성을 높이는 단계에서 검토한다.

# ADR-010 - 설계 변경은 문서와 함께 반영

## 상태

Accepted

## 결정

다음 항목이 변경되면 관련 문서도 함께 수정한다.

```text
기능 요구사항
패키지 책임
Entity 관계
API Contract
알고리즘
개발 순서
```

설계 선택 자체가 바뀌었다면 이 문서에 새 ADR을 추가한다.

## 이유

Codex와 장기간 협업할 때 현재 코드와 오래된 설계 문서가 충돌하는 것을 방지하기 위해서다.

# Architecture Decision Records

## 1. 작성 규칙

각 ADR은 문제, 결정, 이유, 영향과 상태를 기록한다.

상태:

- Proposed: 검토 중
- Accepted: 채택됨, 구현 완료를 의미하지 않음
- Superseded: 이후 결정으로 대체됨
- Rejected: 검토 후 채택하지 않음

제품 요구사항은 docs/01-requirements.md, DB 계약은 docs/03-database.md, HTTP 계약은 docs/04-api-spec.md가 기준이다.

---

## 2. 유지하는 기존 결정

### ADR-001 - 도메인 기준 패키지 구조

**상태: Accepted**

ai, place, route, recommendation, travelplan, user와 global로 책임을 나눈다. 관련 코드를 한 곳에서 찾기 쉽고 외부 제공자 변경의 영향을 제한하기 위해서다.

### ADR-002 - Controller, Service, Repository, DTO 분리

**상태: Accepted**

Controller는 HTTP, Service는 비즈니스 흐름, Repository는 DB 접근을 담당한다. Entity는 API 응답으로 직접 반환하지 않는다.

### ADR-003 - AI와 서버 알고리즘 책임 분리

**상태: Accepted**

AI는 허용된 국내 지역 후보의 선택 이유와 음식 자연어 구조화만 담당한다. 거리·경로·시간표·추천 점수는 서버의 결정적 로직이 담당한다.

### ADR-004 - Nearest Neighbor 후 2-opt

**상태: Accepted**

Haversine 비용으로 Nearest Neighbor 초기 순서를 만들고 2-opt로 개선한다. 순수 Java 알고리즘으로 유지해 외부 API 없이 단위 테스트할 수 있게 한다.

### ADR-005 - 숙소는 제작 중 지도에서 사용자가 직접 선택

**상태: Accepted, 국내·Haversine 기준으로 갱신**

관광지의 기하 중앙값 주변 5km를 기본으로 보여주고 사용자가 10km 확대, 메도이드인 중심 관광지 주변 검색 또는 현재 지도 영역 재검색을 선택한다. 후보에 거리 점수나 자동 추천 순위를 부여하지 않으며 관광지와 숙소 위치를 지도에서 비교한 사용자가 직접 선택한다. 가격·평점·예약 가능성을 보장하지 않는다.

### ADR-006 - 음식점은 음식 일치와 시간·동선으로 평가

**상태: Accepted, 저장 전 제작 흐름 기준으로 갱신**

식사 시각에 대응하는 관광지 주변에서 음식점 후보를 찾는다. AI가 식당을 평가하지 않으며 영업·예약 가능성을 보장하지 않는다.

음식 자연어 AI는 지역·작성 중 관광지 맥락에서 최대 5개의 구체적인 메뉴·카카오 검색어·이유·대상 관광지를 제안하고 사용자가 수정·삭제·확정한다. 일반 식사는 60분과 한쪽 기본 15분의 이동 여유를 확보하고, 긴 체류 안의 식사는 체류시간에 중복 합산하지 않는다. estimate 뒤 저장 전 후보를 Haversine 이탈 순으로 지도·목록에 표시하며 선택한 음식점만 최종 경로와 저장에 포함한다.

# ADR-026 - 시·군·구를 최종 여행 지역으로 사용하는 국내 행정구역 목록

## 상태

Superseded by ADR-035 (2026-09-13)

## 문제

외부 장소 검색과 AI가 각각 지역명을 만들면 이름 표기, 국내 여부, 행정구역 수준이 달라질 수 있다.

## 결정

- 서울특별시·광역시·도는 상위 탐색 항목으로 지원한다.
- 사용자는 상위 항목 아래의 시·군·구 하나를 최종 여행 지역으로 선택한다.
- 세종특별자치시처럼 하위 시·군·구가 없는 예외는 자체를 선택할 수 있다.
- 읍·면·동과 해외 지역은 제외한다.
- regions.json에 내부 ID, 표준 이름, 별칭, 상위 지역, 유형, 최종 선택 가능 여부, 대표 좌표, 출처와 기준일을 둔다.
- 직접 검색과 AI 추천은 같은 목록을 사용한다.
- 대표 좌표는 카카오가 아닌 출처가 명확한 공공자료로 구축한다.
- 완료 일정에는 regionId와 당시 표준 이름을 저장한다.

## 이유와 영향

외부 제공자와 AI가 지역의 존재를 결정하지 않게 하고 같은 입력을 결정적으로 검증할 수 있다. 행정구역 개편 시 기준 파일과 출처를 갱신해야 한다.

# ADR-027 - 카카오를 장소·경로 제공자로 사용하고 저장 범위를 최소화

## 상태

Accepted (2026-09-11), 좌표의 제작 중 활용 조건은 ADR-028에서 확정

## 결정

- 관광지·숙소·음식점은 카카오맵 장소 검색을 사용한다.
- 자동차는 카카오모빌리티, 대중교통은 카카오맵 경로 API를 사용한다.
- 대중교통은 일반 카카오맵 REST endpoint를 사용하고 카카오모빌리티 제휴용 대중교통 API는 사용하지 않는다.
- 장소 ID와 URL, 사용자 작성 정보, Routy 일정만 저장한다.
- 카카오 장소명·주소·좌표·전화번호·카테고리·검색 원문·경로 원문·경로 좌표는 영속 저장하지 않는다.
- 외부 Client는 place/client와 route/client에 격리한다.
- API별 무료 한도의 90%에서 각각 차단하고 유료 초과를 자동 허용하지 않는다. 대중교통 경로는 공식 일일 1,000건을 기준으로 900건에서 신규 호출을 차단한다.

## 이유

카카오는 국내 장소 범위와 자동차·대중교통 경로 조합이 제품 요구에 가깝다. 네이버 지역 검색도 저장·가공 제한이 있고 공개 Maps에는 대중교통 경로가 없으며, TourAPI는 카카오의 전체 POI 범위를 대체하지 못한다.

## 영향

제공자 정책과 쿼터 변경을 계속 확인해야 한다. 완료 화면은 저장된 시간표와 카카오 외부 링크만 사용한다.

# ADR-028 - 장소 좌표는 브라우저 제작 흐름과 서버 요청 안에서만 사용

## 상태

Accepted (2026-09-11, 카카오 DevTalk 답변 확인)

## 문제

여러 장소의 순서를 계산하려면 좌표를 모아야 하지만 카카오 Local API 응답을 영속 저장할 수는 없다. 그래서 브라우저 메모리와 단일 서버 요청에서만 좌표를 사용하고 즉시 폐기하는 구체적인 흐름을 카카오 DevTalk에 문의했다.

## 결정

- 검색 결과는 현재 브라우저 탭 메모리에만 유지한다.
- localStorage, sessionStorage, IndexedDB, 서버 세션, Redis, Caffeine, DB에는 저장하지 않는다.
- 선택값은 인증 사용자 ID를 포함해 서명한 짧은 수명의 selectionToken으로 무결성과 사용자 경계를 보호한다.
- 브라우저는 한 번의 작성 흐름 동안 메모리에서만 좌표와 token을 유지한다.
- 서버는 estimate와 create 각 요청의 지역 변수에서만 좌표를 사용하고 응답 전에 폐기한다.
- 새로고침·완료·취소·탭 종료 시 브라우저 상태를 폐기한다.
- 제작 중 초안 복구는 제공하지 않는다.

## 승인 조건

카카오 DevTalk에서 "일시적으로 저장 및 참조 후 즉시 폐기하는 구조는 허용 가능합니다."라는 답변을 받았다. 따라서 이 흐름을 채택하며, 영속 저장·캐시·로그 기록 또는 완료 후 재사용은 허용 범위에 포함하지 않는다.

# ADR-029 - Haversine으로 먼저 배치하고 최종 후보만 실제 경로로 검증

## 상태

Accepted (2026-09-11), ADR-028의 확정된 수명 조건에 따라 구현

## 결정

- 일정마다 자동차 또는 대중교통 하나를 선택하고 혼합하지 않는다.
- Haversine, Nearest Neighbor, 2-opt로 초기 날짜·순서 후보를 만든다.
- 장소 선택마다 실제 경로를 호출하거나 실제 API로 모든 순열을 비교하지 않는다.
- 거의 완성된 후보의 인접 구간만 실제 API로 검증한다.
- 장소·식사·순서 변경은 영향 구간만, 이동수단 변경은 전체 구간을 재조회한다.
- 정상 경로 없음은 최종 확정을 차단한다.
- 기술 장애는 1회 재시도 후 거리 기반 추정값으로 대체할 수 있다.

## 이유와 영향

외부 호출량과 제공자 의존을 줄이면서 완료 직전 실제 이동 가능성을 확인한다. 이동수단별 초기 추정 계수는 구현 전 별도 ADR에서 수치와 근거를 확정한다.

# ADR-030 - 이동·체류시간을 10분 단위로 관리하고 시간 초과는 사용자가 조정

## 상태

Accepted (2026-09-11), 구현 전

## 결정

- 실제 경로 초는 600초 단위로 올려 10분 단위 예상 이동시간으로 사용한다.
- 체류시간은 10분 단위, 30~480분이다.
- 카카오 카테고리는 기본 체류시간 계산에만 쓰며 유형을 노출·저장하지 않는다.
- 하루 시간은 체류, 식사 60분, 이동시간의 합으로 계산한다.
- 별도의 고정 이동 여유를 더하지 않는다.
- 종료 시각을 넘으면 허용 오차 없이 저장을 차단한다.
- 서버가 장소를 삭제하거나 시간을 줄이지 않고 사용자가 종료 시각·체류·장소·식사·순서를 조정한다.

## 이유와 영향

분 단위 정밀도를 가장하지 않고 읽기 쉬운 시간표를 만든다. 조정에 따라 경로가 바뀐 구간만 다시 검증한다.

# ADR-031 - 완료 일정은 외부 호출 없이 조회하고 제한된 텍스트만 편집

## 상태

Accepted (2026-09-11), 구현 전

## 결정

- 완료·공유 화면은 고정 HTML 템플릿에 저장된 제목, 시간표, 사용자 작성 표시 이름, 카카오 외부 링크를 채운다.
- 완료 화면에서 지도·좌표·경로선을 표시하거나 외부 API를 호출하지 않는다.
- 완료 후 제목, 표시 이름, 메모만 수정한다.
- 날짜·순서·시각·체류시간·이동수단·장소는 수정하지 않는다.
- 동선을 바꾸려면 기존 일정을 보존하고 새 일정을 만든다.

## 이유

좌표를 폐기한 완료 일정에서 지리적 정합성을 다시 검증할 수 없으며, 조회 때마다 외부 호출하면 저장 일정의 안정성과 쿼터 통제가 약해진다.

# ADR-032 - 인증과 소유권을 일정 저장보다 먼저 구현

## 상태

Accepted (2026-09-11), 구현 전

## 결정

- 이메일·비밀번호와 Spring Security·JWT를 MVP에 포함한다.
- User와 TravelPlan 소유권을 첫 목표 스키마부터 포함한다.
- 비용·쿼터가 발생하는 제작 기능은 인증 사용자만 이용한다.
- 비회원은 소개·예시·공유 일정만 조회한다.
- 소셜 로그인은 제외한다.

## 이유

사용자별 호출 제한과 자신의 일정만 조회·편집·삭제하는 규칙을 나중에 덧붙이면 API와 migration을 반복 변경하게 된다.

# ADR-033 - 외부 호출은 사용자 한도와 requestId로 통제

## 상태

Accepted (2026-09-11), 구현 전

## 결정

- 장소 검색 20회/분·300회/일, 자동차·대중교통 경로는 각각 60회/분·120회/일, AI 지역 2회/분·10회/일, 메뉴 AI 3회/분·15회/일을 초기 사용자 한도로 둔다.
- 하루는 Asia/Seoul 자정 기준이다.
- 사용자·기능·requestId로 중복 호출을 막는다.
- 사용자별 분·일 카운터와 API별 서비스 전체 일 카운터는 MySQL `api_usage_counters`, 요청 ID와 상태는 MySQL `request_executions`에 10분 유지한다. payload와 response는 저장하지 않는다.
- 조건부 갱신과 짧은 DB 트랜잭션으로 필요한 수량을 원자적으로 확보한 뒤 트랜잭션을 끝내고 외부 API를 호출한다. 만료 행은 주기적으로 묶어서 삭제한다.
- 재시도와 분할 호출도 사용량에 포함한다.
- 완료 생성은 필요한 경로 요청 수를 먼저 계산해 사용자·서비스 쿼터를 원자적으로 확보한다. 확보하지 못하면 외부 경로 API를 호출하지 않고 일정 전체를 Haversine 기반 예상시간으로 계산해 warning을 반환한다.
- AI 원문과 외부 원문을 로그·DB·오류 응답에 남기지 않는다.

## 영향

서비스 전체 AI 예산은 실제 모델·요금과 운영 환경을 확인한 뒤 운영 문서에서 확정해야 한다.

# ADR-034 - 완료 일정은 사용자 소유 Aggregate로 원자적으로 저장

## 상태

Accepted (2026-09-11), 구현 전

## 결정

- TravelPlan 아래 PlanPlace, TravelPlanDay, TravelPlanItem을 둔다.
- PlanPlace는 카카오 ID·URL과 사용자 작성 이름·메모·역할·체류시간만 가진다.
- Day Item은 VISIT, STAY, MEAL, MOVE 시간표 행을 저장한다.
- MOVE에는 10분 단위 예상 이동시간만 저장한다.
- 이동시간이 제공자 응답인지 Haversine fallback인지 나타내는 enum·상태와 생성 warning은 저장하지 않는다. 완료·공유 조회는 모든 MOVE를 예상 이동시간으로 표시하고 fallback 원인은 개인정보나 일정 payload 없이 집계 metric으로만 관찰한다.
- 외부 검증과 계산을 마친 뒤 짧은 DB 트랜잭션으로 전체를 저장한다.
- 일부 저장을 허용하지 않는다.
- 제작 중 초안은 DB Aggregate로 만들지 않는다.

## 이유

완료 화면이 외부 호출 없이 동일한 시간표를 보여주고, 사용자별 표시 이름을 다른 일정과 분리할 수 있다.

# ADR-035 - 특별시·광역시는 도시 전체를 최종 여행 지역으로 사용

## 상태

Accepted (2026-09-13), ADR-026의 최종 선택 단위 대체, 2026년 통합 뒤 광주 범위는 ADR-038에서 보완

## 문제

특별시·광역시 여행은 여러 자치구를 함께 방문하는 경우가 일반적이다. 구 하나를 최종 여행 지역으로 강제하면 가까운 다른 구의 장소를 불필요하게 배제한다. 반대로 도·특별자치도 전체는 일정 하나의 검색 범위로 사용하기에 지나치게 넓다.

## 결정

- 서울특별시와 부산·대구·인천·대전·울산광역시는 도시 전체를 최종 여행 지역으로 선택할 수 있다. 종전 광주광역시는 전남광주통합특별시 출범 뒤에도 5개 구를 묶은 `광주` 여행 지역으로 같은 선택 경험을 유지한다.
- 세종특별자치시는 자체를 최종 여행 지역으로 선택한다.
- 도와 특별자치도는 상위 탐색 항목이며 그 아래 시·군 하나를 최종 여행 지역으로 선택한다.
- 특별시·광역시와 광주 여행 지역 아래 구·군은 장소 검색 범위를 좁히는 선택 필터로만 사용하고 완료 일정의 regionId로 저장하지 않는다.
- 읍·면·동과 해외 지역은 제외한다.
- 특별시·광역시·세종특별자치시의 대표 좌표 반경 20km는 초기 장소 검색에만 사용한다. 도시 전체 검색은 공식 지역명 결합 검색과 반환 주소의 행정구역 검증으로 보완한다.

## 이유와 영향

사용자가 인식하는 도시 여행 범위와 최종 지역 단위를 맞추면서 도 단위의 과도하게 넓은 선택은 방지한다. `regions.json`은 최종 선택 가능 여부와 검색 필터 여부를 구분해야 하며, 지역 API·AI 허용 목록·장소 검색 검증·테스트를 같은 기준으로 적용해야 한다.

# ADR-036 - 성공한 requestId 재요청은 결과를 재실행하지 않고 충돌로 응답

## 상태

Accepted (2026-09-13), ADR-033 보완, 구현 전

## 문제

중복 요청 저장소에 payload와 response를 보관하지 않는 조건에서 성공 응답을 그대로 재생할 수 없다. 결과 리소스 ID를 별도로 저장하면 기능별 분기와 추가 DB 계약이 필요하다.

## 결정

- 사용자·기능·requestId가 처리 중이면 409 `REQUEST_IN_PROGRESS`를 반환한다.
- 같은 조합이 이미 성공했으면 409 `REQUEST_ALREADY_COMPLETED`를 반환한다.
- 두 경우 모두 외부 API, 저장 로직과 호출량 차감을 반복하지 않는다.
- `request_executions`에는 처리 상태와 만료 시각만 두고 결과 리소스 ID, payload와 response를 저장하지 않는다.
- 10분 수명이 끝난 requestId는 새 요청으로 처리할 수 있다.
- 클라이언트는 성공 완료 충돌을 받으면 필요한 자원을 별도 조회 API로 확인하고, 새로운 작업에는 새로운 requestId를 사용한다.

## 이유와 영향

응답 재생보다 구현과 데이터 최소화를 우선한다. 네트워크 응답을 잃은 클라이언트가 같은 키로 생성 결과를 직접 복구할 수는 없으므로 완료 일정 등 영속 결과는 목록·상세 조회 흐름을 제공해야 한다.

# ADR-037 - 짧은 수명의 access JWT만 사용하고 회원 탈퇴 시 소유 데이터를 삭제

## 상태

Accepted (2026-09-15), 구현 전

## 문제

인증 구현 전에 비밀번호 입력 경계, JWT 수명과 키 교체, 공개 endpoint, refresh·로그아웃 범위와 User 삭제 시 소유 일정 처리를 확정해야 한다. 이 값이 미정이면 API validation, Security 설정과 첫 User migration이 서로 다른 가정을 갖게 된다.

## 결정

- 비밀번호는 8~64 Unicode code point이며 UTF-8 인코딩 기준 72바이트 이하여야 한다. 앞뒤 공백을 제거하거나 Unicode를 정규화하지 않고 입력 그대로 검증·해시하며, 제어 문자는 거부한다. 문자 종류 조합 규칙은 두지 않는다.
- 검증된 adaptive one-way password hash를 사용한다. U1-03 구현에서는 Spring Security `PasswordEncoder`의 BCrypt를 기본으로 사용하고 strength는 12로 시작한다. 평문은 요청 처리 중 검증·해시에만 사용하고 응답, 로그, DB와 fixture에 남기지 않는다.
- access JWT의 수명은 발급 시점부터 1시간이다. refresh token, 서버 저장 세션, token denylist와 로그아웃 endpoint는 MVP에서 제공하지 않는다. 사용자는 브라우저 메모리의 token을 버리는 방식으로 로그아웃하며 만료 후 다시 로그인한다.
- JWT에는 `sub`로 내부 User ID, `iss`, `iat`, `exp`, `jti`와 서명 key ID만 넣고 이메일·비밀번호·권한 상세와 개인정보는 넣지 않는다. 서버는 서명, 허용 알고리즘, issuer, 만료와 User 존재 여부를 매 요청 검증한다.
- JWT 서명 key는 최소 256-bit 무작위 secret을 환경 또는 secret manager에서 key ID별로 주입한다. 새 key로만 발급하고 이전 key는 access token 최대 수명인 1시간 동안 검증한 뒤 제거하는 방식으로 교체한다. 알고리즘과 key ID를 token header 값만 믿어 동적으로 선택하지 않고 서버 allowlist와 대조한다.
- 공개 API는 `POST /api/users`, `POST /api/auth/login`, `GET /api/shared/travel-plans/{shareToken}`뿐이다. 명세된 공개 정적 화면과 운영 health endpoint가 후속 작업에서 생기면 API와 보안 allowlist를 같은 변경 단위에서 명시한다. 그 밖의 `/api/**`는 인증이 필요하다.
- 인증 사용자는 `DELETE /api/users/me`로 탈퇴한다. 한 번의 짧은 DB 트랜잭션에서 소유 TravelPlan Aggregate, 사용자 범위 호출 카운터와 requestId 처리 행, User를 영구 삭제한다. 외부 API는 호출하지 않는다.
- 탈퇴 성공은 204이며 응답 body를 반환하지 않는다. 삭제 후 기존 JWT는 User 존재 검증에 실패해 다른 잘못된 token과 같은 401 `AUTHENTICATION_REQUIRED`로 처리한다. 별도의 복구·유예 기간은 MVP에 두지 않는다.

## 이유와 영향

짧은 access token만 두면 별도 refresh token 저장소와 폐기 목록 없이 인증 경계를 학습할 수 있다. User 존재를 함께 검사하면 stateless JWT의 서명 검증만으로는 처리할 수 없는 탈퇴 직후 token 무효화를 보장한다. 회원 탈퇴 때 소유 데이터를 함께 삭제하면 개인정보 최소화와 소유권 모델이 단순해지지만 복구할 수 없으므로 화면은 삭제 전 명시적 확인을 받아야 한다. User와 TravelPlan FK, 사용자 종속 운영 행의 실제 삭제 방식은 새 migration에서 이 원자적 삭제 계약을 만족하도록 정한다.

# ADR-038 - 공공 행정구역 코드와 경계로 정적 지역 기준 데이터를 생성

## 상태

Accepted (2026-09-17), G1-01 결정 완료, 데이터 생성은 G1-02에서 구현

## 문제

직접 검색과 AI 추천이 같은 국내 지역 목록을 사용하려면 이름·계층·존폐 여부와 대표 좌표의 원천, 기준일과 갱신 책임이 고정되어야 한다. 사람이 임의로 목록과 좌표를 입력하면 행정구역 개편을 누락하거나 같은 입력에서 다른 결과를 만들 수 있다. 반대로 서버 시작이나 요청마다 외부 공공 API를 호출하면 지역 기준이 실행 시점에 따라 달라지고 외부 장애가 핵심 조회 기능으로 전파된다.

## 결정

- 이름·계층·존폐 여부의 1차 원천은 행정안전부 행정표준코드관리시스템의 [법정동 코드 전체자료](https://www.code.go.kr/stdcode/regCodeL.do)로 한다. 공공데이터포털의 [국토교통부 전국 법정동 파일](https://www.data.go.kr/data/15063424/fileData.do)은 내려받기 가능한 교차 검증 자료로 사용한다.
- 대표 좌표의 원천은 국토교통부 국가공간정보센터의 [행정구역도 WFS](https://www.data.go.kr/data/15059008/openapi.do) 중 광역시도와 시군구 경계다. 경계를 WGS84로 변환한 뒤 해당 다각형 내부가 보장되는 point-on-surface를 계산한다. 단순 꼭짓점 평균이나 카카오 좌표는 사용하지 않는다.
- 최초 데이터 기준일은 법정동 전체자료와 행정구역도 원본을 실제로 내려받아 서로 대조한 G1-02 생성일로 정한다. `regions.json`에는 코드 원본 기준일, 경계 원본 기준일과 생성 시각을 서로 구분해 기록한다. 이 ADR 작성일을 데이터 기준일로 대신 사용하지 않는다.
- 생성기는 현존 코드만 입력으로 받고 ADR-035의 선택 규칙을 적용한다. 서울특별시·광역시·세종특별자치시는 자체를 최종 지역으로, 도·특별자치도는 상위 항목으로, 그 아래 시·군은 최종 지역으로 분류한다. 특별시·광역시 아래 구·군은 검색 필터로만 분류하며 읍·면·동·리와 해외는 제외한다.
- 2026-07-01 전남광주통합특별시 출범 뒤에는 통합특별시 자체를 최종 지역으로 사용하지 않는다. 종전 광주광역시 5개 구의 공식 경계를 묶은 논리 지역 `광주`를 기존 `METROPOLITAN_CITY` 유형의 최종 지역으로 두고, 5개 구는 검색 필터로 둔다. 종전 전라남도 시·군은 `전남`으로 표시하는 전남광주통합특별시 상위 항목 아래 최종 지역으로 둔다.
- 최종 지역과 검색 필터의 `addressBoundary`는 공식 주소 1단계 허용 이름 목록과 2단계 허용 이름 목록을 가진다. 분구된 일반시는 시 자체만 최종 선택 항목으로 두되 2단계 목록에 모든 일반구 공식 이름을 넣는다. 카카오 같은 장소 제공자의 주소 검증은 이 공통 경계를 사용하고 제공자 결과를 기준 데이터에 복제하지 않는다.
- 원천 코드와 경계의 코드·정식 명칭·상위 관계가 일치하지 않거나 필요한 경계가 없으면 생성에 실패한다. 누락 값을 임의 좌표, 카카오 결과 또는 이전 지역의 값으로 채우지 않는다. 행정구역 개편으로 두 원천의 기준시점이 다르면 일치하는 공식 자료가 제공될 때까지 기존 검증본을 유지한다.
- 내부 regionId는 Routy가 소유하는 불투명하고 안정적인 식별자다. 최초 값이 공공 행정구역 코드에서 파생됐더라도 외부 코드·배열 순서·명칭 변경만으로 자동 변경하지 않으며, 접두사·숫자 길이·문자열 구조에 계층이나 유형 의미를 부여하지 않는다. 폐지된 ID를 다른 지역에 재사용하지 않고 폐지·통합·분할은 기존 ID의 의미를 바꾸는 대신 영향과 이전 규칙을 별도 결정으로 검토한다. 외부 원천 코드 자체를 런타임 계약에 사용해야 할 때는 regionId와 분리된 필드로 관리한다.
- 생성 결과는 정렬 규칙이 고정된 정적 `src/main/resources/data/regions.json`으로 커밋한다. 애플리케이션은 런타임에 원천 API를 호출하지 않는다. 생성 명령, 원천 URL·기준일·해시, 제외·분류 건수와 검증 결과를 변경 기록에 남겨 같은 입력으로 같은 파일을 재현할 수 있게 한다.
- 별칭은 공식 정식 명칭과 별도로 검토되는 작은 allowlist로만 관리한다. 외부 검색 결과나 AI 응답에서 자동 수집하지 않으며, 중복 별칭이 둘 이상의 지역을 가리키면 생성에 실패한다.

## 갱신 책임

- 백엔드 저장소 관리자가 매월 첫 개발 주에 행정표준코드 변경 공지와 두 원천의 기준일을 확인하고, 행정구역 개편 공지가 있으면 정기 확인일을 기다리지 않고 갱신 여부를 검토한다.
- 원천이 바뀌지 않았으면 파일을 다시 생성하지 않고 확인 일자만 운영 기록에 남긴다. 원천이 바뀌면 생성기를 다시 실행하고 추가·폐지·명칭·상위 관계·좌표 변경 diff와 지역 검증 테스트를 함께 검토한다.
- 갱신은 일반 기능 변경과 분리된 변경으로 수행한다. 원천 자료와 생성 중간 파일은 저장소에 커밋하지 않고, 출처 표시 조건은 생성 결과와 문서에서 유지한다.

## 이유와 영향

공식 코드가 지역의 존재와 계층을 결정하고 공식 경계에서 계산한 내부점이 대표 좌표를 결정하므로 AI와 카카오가 기준 데이터를 만들지 않는다. 정적 snapshot은 외부 장애와 원천의 예고 없는 변경을 런타임에서 차단한다. 대신 행정구역 개편을 자동 반영하지 않으므로 정기·사건 기반 점검과 재현 가능한 생성 기록이 필수다. G1-02는 이 결정에 따라 실제 기준일과 원천 해시를 확정하고, G1-03은 불일치·누락·중복을 시작 시 검증한다.

# ADR-039 - OpenAI Responses API와 제공자 비용 차단 계약

## 상태

Accepted (2026-09-17, A1-02 공식 계약 감사 완료)

## 문제

지역 추천과 메뉴 분석은 짧은 자연어를 서버 계약에 맞는 JSON으로 구조화해야 한다. 모델, API 저장 기본값, 구조화 출력, timeout과 재시도를 명시하지 않으면 제공자 변경·장애·비용 증가 때 동작이 달라질 수 있다. 사용자 원문과 AI 원문을 Routy가 저장하지 않더라도 Responses API의 저장 옵션을 생략하면 제공자에 애플리케이션 상태가 남을 수 있다.

## 결정

- 공통 endpoint는 `POST https://api.openai.com/v1/responses`이며 서버 전용 project API key를 `Authorization: Bearer`로 전달한다. 키는 환경 변수 또는 secret manager로만 주입한다.
- 기본 모델은 `gpt-5.6-luna`, reasoning effort는 `none`이다. 모델은 설정으로 주입하되 운영 배포 전에 지원 여부·가격·Structured Outputs 지원을 smoke에서 다시 확인한다.
- 요청마다 `store: false`를 명시하고 conversation, previous response, background, streaming, tool과 metadata를 사용하지 않는다. Routy DB·cache·session·로그에도 사용자 원문, 제공자 원문, token usage와 비용을 저장하지 않는다. `store: false`는 OpenAI의 기본 abuse-monitoring 보존과 별도이므로 운영 계정에서 이용 가능한 데이터 통제 조건을 배포 전에 확인한다.
- 응답은 `text.format.type=json_schema`, `strict: true`를 사용한다. 모든 object schema는 모든 속성을 `required`에 열거하고 `additionalProperties: false`로 제한하며 nullable 값은 `null`을 union에 명시한다. 지역 추천과 메뉴 분석은 서로 다른 schema 이름과 DTO 매핑을 사용한다.
- 지역 추천 `max_output_tokens`는 512, 메뉴 분석은 768이다. refusal, incomplete, 빈 output, JSON 해석 실패, schema 불일치와 서버의 허용 목록·중복·개수 계약 위반은 성공 결과로 사용하지 않는다.
- 연결 timeout은 3초, 최초 호출부터 재시도까지 포함한 기능별 전체 요청 시간 예산은 15초다. 인증·권한·잘못된 요청·결제 또는 소진된 quota는 재시도하지 않는다. 연결 실패·timeout·일시적 5xx와 일시적 rate limit만 전체 시간 예산 안에서 최대 한 번 재시도한다. 유효한 `Retry-After`가 있으면 그 이상 기다리되 15초 예산을 넘으면 재시도하지 않고 `AI_UNAVAILABLE`로 변환한다. `Retry-After`가 없으면 짧은 exponential backoff와 jitter를 사용한다. SDK와 애플리케이션의 중첩 재시도는 허용하지 않는다.
- 구조화 출력 계약 위반 재시도는 메뉴 분석에서만 최대 한 번 수행하고 각 실제 외부 호출을 사용자 사용량에 포함한다. 지역 추천 구조 위반은 재시도하지 않고 `AI_RESPONSE_INVALID`로 끝낸다.
- 월 계획 예산은 USD 5이며 전용 OpenAI project의 월 hard spend limit을 USD 4로 설정해 20% 완충분을 둔다. 비용 차단은 OpenAI project가 담당하며 Routy는 별도 비용 ledger나 서비스 전체 일일 호출 카운터를 추가하지 않는다. 기존 사용자별 지역 추천 2회/분·10회/일과 메뉴 분석 3회/분·15회/일만 MySQL 공유 호출 카운터로 적용한다.
- 가격 기준은 2026-09-17 공식 문서의 `gpt-5.6-luna` short-context standard 가격인 입력 USD 0.20/1M tokens, cached input USD 0.02/1M tokens, cache write USD 0.25/1M tokens, 출력 USD 1.20/1M tokens다. 모델·가격·project spend-limit 지원은 변경될 수 있으므로 배포 전과 월 1회 공식 문서·Costs 대시보드로 재확인한다.

공식 근거는 OpenAI의 [GPT-5.6 Luna 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.6-luna), [Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [오류 처리](https://developers.openai.com/api/docs/guides/error-codes), [rate limit](https://developers.openai.com/api/docs/guides/rate-limits), [가격](https://developers.openai.com/api/docs/pricing), [project hard spend limit API](https://developers.openai.com/api/reference/typescript/resources/admin/subresources/organization/subresources/projects)에 둔다.

## 결과

단일 저비용 모델과 짧은 동기 요청으로 구현 범위를 제한하면서 schema와 서버 검증을 함께 적용할 수 있다. 비용 상태를 서버에 추가 저장하지 않아 데이터 경계와 구현이 단순하지만 제공자 project 설정이 빠지면 비용 차단이 작동하지 않으므로 배포 체크리스트에서 hard spend limit을 필수 확인한다. 모델 alias의 동작과 가격은 바뀔 수 있어 smoke·공식 계약 재확인을 운영 게이트로 유지한다.

# ADR-040 - 순수 좌표 계산과 이동수단별 초기 시간 추정 계약

## 상태

Accepted (2026-09-17, R1-01 결정 완료), 구현은 R1-02~06에서 검증

## 문제

Haversine 거리, 숙소 검색 중심, 방문 순서와 실제 경로를 호출할 수 없을 때의 예상 이동시간이 같은 수치 계약을 사용해야 한다. 단위·좌표 범위·수렴 조건·동률과 이동수단별 계수를 정하지 않으면 같은 입력이 구현 위치나 실행 순서에 따라 다른 결과를 만들고, 추정값이 실제 경로처럼 보일 수 있다.

## 결정

### 좌표와 거리

- `Coordinate`는 WGS84 위도·경도를 `double`로 받는다. 위도는 `[-90, 90]`, 경도는 `[-180, 180]`이며 `NaN`과 양·음의 무한대는 거절한다. `-0.0`은 `0.0`으로 정규화한다.
- 거리의 내부·공개 알고리즘 단위는 km이고 시간 단위는 분이다. 거리 계산 중간값은 `double`을 유지하며 UI 표시를 위한 반올림을 알고리즘 입력에 다시 사용하지 않는다.
- Haversine은 평균 지구 반지름 `6_371.0088 km`와 radian 변환을 사용한다. 부동소수점 오차로 역삼각함수 입력이 범위를 벗어나지 않도록 haversine 중간값을 `[0, 1]`로 제한한다.
- 같은 좌표의 거리는 정확히 `0.0 km`로 반환한다. 거리 비교는 `1e-6 km` 이내를 동률로 본다. 알려진 거리의 단위 테스트 허용 오차는 절대 `0.001 km`로 둔다.
- 이 계산은 직선거리 기반 초기 비용이다. 도로·철도망의 실제 거리나 제공자 검증 결과로 표시하지 않는다.

### Nearest Neighbor 방문 순서

- 입력은 안정 키와 `Coordinate`를 가진 장소 목록, 그리고 선택적인 시작점 안정 키다. 목록·원소·안정 키·좌표와 시작점 키 wrapper는 null일 수 없고, 안정 키는 빈 문자열일 수 없으며 목록 안에서 유일해야 한다. 서로 다른 안정 키가 같은 좌표를 가지는 것은 허용하며 서로 다른 장소로 취급한다.
- 빈 목록에는 시작점 키가 없어야 하며 불변 빈 목록을 반환한다. 비어 있지 않은 목록에는 목록에 존재하는 시작점 키가 반드시 있어야 한다. 시작점 누락, 목록 밖 시작점, 중복 안정 키와 잘못된 원소는 자동 보정하지 않고 거절한다.
- 출력은 입력과 같은 장소를 정확히 한 번씩 담는 새 불변 목록이다. 첫 원소는 지정한 시작점으로 고정한다. 입력 목록을 변경하지 않고 시작점으로 되돌아오는 폐쇄 구간은 추가하지 않는 열린 경로를 반환한다.
- 시작점에서 출발해 아직 방문하지 않은 장소 중 현재점과의 Haversine 거리가 가장 짧은 장소를 다음 장소로 선택하며 모든 장소를 방문할 때까지 반복한다. 실제 Route Client, 이동시간 추정 계수와 2-opt는 이 단계에 사용하지 않는다.
- 거리 차이가 ADR-040의 동률 허용치 `1e-6 km` 이내이면 안정 키의 Java 자연 순서 오름차순으로 선택한다. 후보는 먼저 안정 키 순서로 고정한 뒤 순회하고, 새 후보가 현재 최선보다 `1e-6 km`를 초과해 짧을 때만 거리로 교체하므로 입력 배열 순서와 hash 순회 순서가 결과에 영향을 주지 않는다.
- 안정 키는 알고리즘 호출자가 한 요청 안에서 부여하는 불투명 식별자다. 장소 표시 이름·카카오 장소명·좌표 문자열을 동률 키로 사용하지 않으며, 알고리즘은 키의 형식이나 의미를 해석하지 않는다.
- 장소 수를 `n`이라 할 때 각 단계에서 미방문 후보를 선형 탐색하므로 시간복잡도는 `O(n²)`, 후보 정렬은 `O(n log n)`이고 전체 상한은 `O(n²)`이다. 방문 집합과 결과 목록을 위한 추가 공간은 `O(n)`이다. 거리 행렬은 만들지 않는다. MVP의 하루 관광지 최대 5개에서는 단순성과 검증 가능성을 우선한다.

### 기하 중앙값과 메도이드

- 빈 좌표 목록은 거절하고 하나의 좌표는 그대로 반환한다. 입력 순서는 결과 의미에 영향을 주지 않는다.
- 기하 중앙값은 국내 범위의 좌표를 기준점 주변의 local equirectangular km 평면으로 투영한 뒤 Weiszfeld 방식으로 각 입력점까지의 거리 합을 최소화한다. 기준점은 입력 위도·경도의 산술 평균이며 경도 차이는 `[-180, 180]`로 정규화한다. 결과는 WGS84 위도·경도로 역투영한다.
- Weiszfeld 반복은 이동량이 `1e-6 km` 이하이면 수렴으로 끝내고 최대 `1_000`회에서 반드시 종료한다. 반복점이 입력점과 `1e-9 km` 이내로 겹치면 0으로 나누지 않도록 해당 점의 subgradient 조건을 평가하는 modified Weiszfeld 규칙을 사용한다. 반복 상한에 도달하면 마지막 유한 좌표를 결정적으로 반환하며 수렴 여부를 별도 상태로 노출하거나 저장하지 않는다.
- 메도이드는 입력에 실제 존재하는 좌표 중 다른 모든 입력까지의 Haversine 거리 합이 가장 작은 좌표다. 합계가 `1e-6 km` 이내로 같으면 안정적인 호출자 키의 오름차순으로 고른다. 알고리즘 DTO는 좌표와 함께 null이 아니고 목록 안에서 유일한 안정 키를 요구하며, 입력 배열 순서를 동률 규칙으로 사용하지 않는다.
- 숙소 검색의 기본 중심은 기하 중앙값이고 사용자가 선택한 `중심 관광지 주변에서 보기`만 메도이드를 사용한다. 어느 결과도 숙소 자동 추천 점수로 사용하지 않는다.

### 초기 이동시간 추정

- 일정 하나는 `CAR` 또는 `PUBLIC_TRANSIT` 하나만 사용한다. 각 인접 구간의 Haversine 거리 `d`에 대해 `ceil((d × 우회계수 ÷ 평균속도 × 60) ÷ 10) × 10`분을 반환한다.
- 기본값은 `CAR = 우회계수 1.30, 평균속도 30 km/h`, `PUBLIC_TRANSIT = 우회계수 1.40, 평균속도 20 km/h`다. 자동차는 국내 도시권의 교차로·도로 굴곡을, 대중교통은 노선 굴곡·환승을 포함한 보수적 초기 일정 예산을 의도한다. 이는 제공자 실측 통계나 도착 보장이 아니라 MVP 초기 휴리스틱이다.
- 정확히 `0.0 km`인 구간은 `0분`, 양의 거리는 최소 `10분`이다. 별도의 고정 이동 buffer, 승하차·대기시간 또는 식사 이동 여유를 이 식에 더하지 않는다.
- 우회계수와 평균속도는 운영 설정으로 주입할 수 있지만 우회계수는 `[1.0, 3.0]`, 평균속도는 `(0, 200] km/h`만 허용하고 누락 시 위 기본값을 사용한다. 시작 시 한 번 검증한 불변 정책 객체를 일정 계산에 전달하며 구간마다 설정을 다시 읽지 않는다.
- 추정값은 항상 10분 단위 예상시간이며 실제 경로 검증값으로 표시하지 않는다. 실제 Route Client 결과가 있으면 ADR-030의 `ceil(seconds / 600) × 10`분 계약이 이 초기 추정값을 대체한다.

## 이유와 영향

평균 지구 반지름과 단위를 하나로 고정하면 순서·중심·시간 추정이 같은 거리 정의를 공유한다. 국내 여행이라는 제품 범위에서는 local equirectangular 투영이 단순하고 결정적이며, modified Weiszfeld의 허용 오차와 반복 상한으로 중복점과 비수렴에서도 종료를 보장한다. 메도이드는 실제 관광지만 반환하고 안정 키로 동률을 해소하므로 배열 순서에 의존하지 않는다.

초기 시간 계수는 실제 도로·대중교통 경로를 가장하지 않고 일정 초안과 전체 fallback에 일관된 보수적 값을 제공한다. 값은 운영 관찰 뒤 설정으로 조정할 수 있지만 수식·허용 범위·10분 올림과 이동수단 혼합 금지는 코드 계약으로 유지한다. R1-02~06은 이 ADR의 경계값, 수렴, 동률과 이동수단 분리를 각각 단위 테스트로 증명해야 한다.

# ADR-001 - 도메인 중심 패키지 구조 사용

## 상태

Accepted

## 문제

Spring 프로젝트를 처음 학습하는 단계에서 다음 두 가지 패키지 구조를 고려했다.

### 선택지 A

계층 중심:

```text
controller/
service/
repository/
domain/
```

### 선택지 B

도메인 중심:

```text
place/
travelplan/
route/
ai/
recommendation/
```

## 결정

도메인 중심 패키지를 사용한다.

각 도메인 안에서 필요한 Controller / Service / Repository / DTO를 둔다.

## 이유

프로젝트 기능이 여행지, 여행 계획, 추천, 경로, AI 등으로 명확하게 나뉘며 프로젝트가 커졌을 때 관련 코드를 한 곳에서 찾기 쉽다.

## 재검토 조건

도메인 규모가 매우 커져 더 세밀한 모듈화가 필요해질 경우 재검토한다.

# ADR-002 - 관광지 / 호텔 / 음식점을 Place로 통합

## 상태

Superseded by ADR-016

## 문제

다음 Entity를 각각 만들 수 있다.

```text
Attraction
Hotel
Restaurant
Cafe
```

하지만 공통적으로 이름, 주소, 좌표 같은 속성을 가진다.

## 결정

초기 MVP에서는 `Place` Entity로 통합하고 `PlaceType`으로 구분한다.

```text
ATTRACTION
HOTEL
RESTAURANT
CAFE
```

## 이유

- 중복 필드 감소
- 거리 계산 로직 재사용
- 첫 Spring 프로젝트의 복잡도 제어
- 여행 일정에서 모든 장소를 동일한 위치 객체로 다루기 쉬움

## 단점

호텔 가격이나 음식점 메뉴 등 타입별 특성이 증가하면 Place가 비대해질 수 있다.

## 재검토 조건

장소 유형별 전용 속성과 비즈니스 규칙이 크게 증가하면 Detail Entity 또는 별도 Entity 분리를 검토한다.

# ADR-003 - AI와 경로 최적화 책임 분리

## 상태

Accepted

## 문제

LLM에게 "최적의 여행 일정을 만들어줘"라고 요청하면 구현은 간단하지만 실제 거리 계산의 정확성, 재현성, 테스트 가능성을 보장하기 어렵다.

## 결정

AI는 자연어 이해와 후보 추천을 담당한다.

경로 계산과 최적화는 Java 백엔드 알고리즘이 담당한다.

## 이유

- 결과가 결정적이고 테스트 가능함
- 실제 좌표 데이터를 기준으로 계산 가능
- 알고리즘 개선을 측정할 수 있음
- 백엔드 프로젝트로서 기술적 깊이를 확보할 수 있음

# ADR-004 - 경로 최적화 1차 구현은 Nearest Neighbor

## 상태

Accepted

## 문제

여러 여행지를 방문하는 이동 경로 최적화는 TSP와 유사하다.

첫 구현부터 최적해 알고리즘을 적용하면 학습 / 구현 복잡도가 증가한다.

## 결정

첫 버전은 Nearest Neighbor를 사용한다.

## 이유

- 구현이 단순함
- Greedy Algorithm 학습 가능
- 시간 복잡도 설명이 쉬움
- 이후 개선 기준선(Baseline)으로 사용 가능

## 재검토 / 개선

Nearest Neighbor 완료 후 2-opt를 적용하여 경로 개선 정도를 측정한다.

# ADR-005 - 호텔 추천은 이동 거리 합을 첫 기준으로 사용

## 상태

Accepted for MVP

## 문제

호텔 추천에는 가격, 평점, 편의시설 등 많은 요소가 있다.

모든 요소를 처음부터 적용하면 추천 기준이 불명확해지고 구현 범위가 커진다.

## 결정

MVP에서는 호텔과 선택 여행지 사이의 총 이동 거리를 핵심 점수로 사용한다. 서비스는 점수가 낮은 순서로 여러 후보를 반환하고, 사용자는 추천 후보 또는 같은 지역의 임의 `HOTEL` 장소 중 하나를 선택한다. 선택한 호텔은 최종 여행 계획 생성 요청에 포함되며 각 날짜 경로의 시작·종료점으로 사용한다.

```text
HotelScore = Σ distance(hotel, selectedPlace)
```

## 이유

이 프로젝트의 핵심 가치 중 하나가 "여행 동선 최적화"이므로 추천 기준과 프로젝트 목적이 일치한다.

## 재검토 조건

핵심 기능 완성 후 가격 / 평점 등의 가중치를 추가할 수 있다.

# ADR-006 - 음식점 추천은 식사 시간 충족 + 음식 일치 + 동선 이탈을 우선

## 상태

Accepted for MVP

## 문제

맛집 추천은 평점만 사용하면 여행 경로를 크게 벗어나는 식당이 추천될 수 있다.

## 결정

MVP에서는 다음 요소를 순서대로 적용한다.

1. 점심 또는 저녁 시간대 안에 60분 식사가 가능한지
2. 사용자가 원하는 음식과의 일치
3. 기존 여행 경로에서 발생하는 이탈 시간·거리

관광 장소의 체류 구간이 식사 시간대 전체를 포함하면 해당 장소 내부 음식점을 우선하고, 내부 후보가 없으면 인접 음식점을 추천한다.

## 이유

서비스의 핵심인 여행 동선 최적화와 음식 추천을 결합할 수 있다.

## 개선

향후 다음 요소를 추가할 수 있다.

- 평점
- 리뷰 수
- 영업시간
- 가격대

# ADR-009 - 실제 도로 거리 API는 초기 MVP 이후 검토

## 상태

Superseded by ADR-017

## 문제

직선 거리와 실제 도로 이동 거리 / 시간은 다르다.

하지만 초기부터 외부 지도 API까지 도입하면 API 정책, 비용, 인증, 데이터 변환까지 동시에 학습해야 한다.

## 결정

Phase 5의 첫 구현에서는 위도 / 경도를 이용한 서버 내부 거리 계산으로 알고리즘을 검증한다.

핵심 경로 로직이 안정화된 후 실제 지도 / 길찾기 API를 검토한다.

## 이유

문제를 다음 두 단계로 분리하기 위해서다.

```text
1. 경로 알고리즘이 올바른가?
2. 실제 이동 데이터를 연결할 수 있는가?
```

## 재검토 조건

호텔 및 여행 경로 추천의 현실성을 높이는 단계에서 검토한다.

# ADR-011 - 공유 환경의 DB 스키마는 Flyway migration으로 관리

## 상태

Accepted

## 문제

JPA의 `ddl-auto: update`는 개발 속도는 빠르지만 스키마 변경 이력, 재현성, 배포 안전성을 보장하지 않는다.

## 결정

첫 스키마부터 모든 DB 변경은 Flyway versioned migration으로 관리한다.

모든 profile의 Hibernate는 `ddl-auto: validate`만 사용한다.

## 이유

- 새 환경에서 같은 스키마를 재현할 수 있다.
- 제약조건과 인덱스 같은 DB 수준 규칙을 코드 리뷰할 수 있다.
- 적용 이력이 남아 협업과 배포 시 변경 원인을 추적하기 쉽다.

## 단점

초기 개발에서도 schema 변경마다 migration 파일을 작성해야 한다.

## 재검토 조건

JPA 매핑을 빠르게 실험해야 하면 별도 임시 DB에서만 수행하며, 프로젝트 설정의 `ddl-auto: update`로 전환하지 않는다.

# ADR-012 - MVP 일정은 균등 배치 후 날짜별 경로를 최적화

## 상태

Superseded by ADR-017

## 문제

여행 일정 생성에서 영업시간, 체류 시간, 식사 시간, 실제 도로 이동 시간까지 동시에 고려하면 제약 충족 최적화 문제가 되어 구현과 검증이 복잡해진다.

## 결정

MVP는 여행 기간별 장소 수를 최대 6개 범위에서 균등 배치한 뒤, 각 날짜 안에서만 Nearest Neighbor 기반 경로 최적화를 수행한다.

필수 장소는 누락 없이 포함한다. 숙소는 매일 `호텔 → 관광 장소들 → 호텔` 경로의 시작·종료 기준점으로 사용하되 방문 순서에는 포함하지 않는다. 음식점은 자동 일정 삽입 대신 추천 후보로 반환한다.

## 이유

- 일정 배분과 경로 최적화를 분리해 각 결과를 단위 테스트할 수 있다.
- 사용자가 이해하기 쉬운 최대 방문 장소 수를 제공한다.
- 필수 장소 보장이라는 서비스 약속을 검증 가능하게 만든다.

## 단점

영업시간이나 실제 이동 시간에 따라 현실적인 시간표를 만들지는 못한다.

## 재검토 조건

외부 지도 데이터의 영업시간·경로 시간을 안정적으로 사용할 수 있고, 체류 시간 기반의 일일 시간표가 제품 요구로 확정되면 제약 기반 일정 생성으로 확장한다.

# ADR-013 - AI 도시 후보는 구조화 응답과 서버 검증을 함께 사용

## 상태

Accepted

## 문제

자유 형식 LLM 응답을 그대로 사용하면 도시 이름·국가 코드·추천 이유의 누락이나 형식 오류로 추천 흐름이 불안정해질 수 있다.

## 결정

AI는 선택 국가를 기준으로 3~5개의 도시 이름·국가 코드·추천 이유를 제한된 JSON Schema/structured output으로 반환하고, 서버가 DTO validation을 수행한다. 이후 Google Places로 도시의 존재와 국가 일치를 검증하고 Google Place ID가 확인된 후보만 사용자에게 반환한다.

AI 통신은 `AiClient` 인터페이스 뒤에 감추고, 테스트에서는 fake 구현체를 사용한다. timeout은 10초, 네트워크·provider 5xx 재시도는 최대 1회로 제한한다.

## 이유

- 추천 입력값을 결정적으로 검증할 수 있다.
- provider 장애와 계약 위반을 구분해 사용자와 운영자가 원인을 판단할 수 있다.
- 외부 네트워크·비용 없이 서비스 테스트를 수행할 수 있다.

## 단점

Schema, DTO와 Google 검증 흐름을 함께 관리해야 하며 AI와 Google 중 하나가 실패하면 도시 추천 기능을 제공할 수 없다.

## 재검토 조건

도시 추천 기준을 개인 취향까지 확장할 때는 별도 요구사항으로 정의한다. AI 결과는 거리 계산이나 DB 상태 변경의 직접 입력으로 사용하지 않는다.

# ADR-014 - 환경은 Spring profile로 분리하고 외부 의존성 장애를 독립 관찰

## 상태

Accepted

## 문제

개발 환경의 상세 SQL 로그와 `ddl-auto: update` 설정을 운영 환경에 그대로 적용하면 데이터 안전성과 보안에 문제가 생긴다. 또한 AI·지도 API의 장애가 애플리케이션 또는 DB 장애와 구분되지 않으면 원인 파악이 어렵다.

## 결정

`local`, `test`, `prod` Spring profile을 분리한다. 운영에서는 migration 적용 후 `ddl-auto: validate`만 사용하며, 민감 정보와 사용자 원문을 로그에서 제외한다.

애플리케이션·DB 상태는 필수 health check로 확인하고, AI·지도 API 상태는 별도 dependency 상태와 호출량으로 관찰한다.

## 이유

- 환경별 안전한 기본값을 강제할 수 있다.
- 외부 제공자 장애가 발생해도 서비스 내부 장애와 구분해 대응할 수 있다.
- 비용과 장애 추세를 요청 단위가 아닌 집계 지표로 확인할 수 있다.

## 재검토 조건

배포 플랫폼이 확정되면 Google Maps Platform 키 제한, profile별 설정, health endpoint와 지표 도구를 해당 플랫폼에 맞게 구체화한다.

# ADR-015 - TravelPlan 영속성 선택을 구현 전에 고정

## 상태

Accepted

## 문제

초기 DB 문서에 사용자 FK 추가 시점, 선택 호텔의 null 허용 여부, 일정 순서 UNIQUE 적용 여부가 선택지로 남아 있었다. 이 상태에서 Entity와 migration을 구현하면 작업마다 다른 결정을 내리거나 이미 적용된 migration을 다시 수정할 위험이 있다.

## 결정

- T1에서는 `travel_plans.user_id`를 만들지 않고 U1 인증 단계의 새 migration에서 추가한다.
- `travel_plans.selected_hotel_id`는 DB에서 nullable로 유지하되, 최종 일정 생성 API에서는 필수로 검증한다.
- 계획별 Day 번호·날짜와 Day별 방문 순서의 중복 방지 UNIQUE 제약은 필수로 적용한다.

## 이유

- 로그인 구현을 핵심 여행 기능과 분리하면서 나중에 사용자 FK를 명시적인 migration으로 학습할 수 있다.
- DB nullable과 최종 API의 호텔 필수 validation을 구분한다. T1/T2 단계 경계는 ADR-019로 구체화하며, 호텔 없는 기본 계획 API를 별도로 만들지는 않는다.
- 애플리케이션 validation뿐 아니라 DB에서도 일정 순서의 중복을 차단할 수 있다.

## 재검토 조건

- U1 시작 전 기존 TravelPlan 데이터의 사용자 소유권 이관과 `user_id`의 최종 null 허용 여부를 결정한다.

# ADR-016 - Google Place ID를 전 세계 장소의 기준 식별자로 사용

## 상태

Accepted

## 문제

국내외 관광지·호텔·음식점을 모두 자체 DB에 적재하고 최신 상태로 유지하는 것은 프로젝트 범위를 벗어난다. 또한 Google Places 콘텐츠는 저장·표시 정책의 적용을 받으므로 외부 장소 본문을 내부 데이터처럼 영구 복제해서는 안 된다.

## 결정

- Google Places를 국가·도시·관광지·호텔·음식점의 장소 원천으로 사용한다.
- 사용자는 Google 자동완성으로 도시를 직접 선택하거나, 국가 선택 후 AI가 제안하고 Google Places가 검증한 도시 후보 중 하나를 선택한다.
- AI는 도시 이름·국가 코드·추천 이유만 생성하며 Google Place ID를 생성하거나 추측하지 않는다.
- DB의 `Place`는 내부 ID와 `google_place_id`만 가진 참조 Entity로 사용한다.
- Google 장소명·주소·좌표·사진 등은 별도 허용 근거 없이 영구 저장하지 않고 필요한 시점에 조회한다.
- Google Places 후보 전체를 DB에 저장하지 않고, 사용자가 일정에 선택한 장소만 내부 Place 참조로 연결한다.
- 취향 입력이 없는 일반 방문 장소 추천은 Google Text Search의 관련도 순서를 사용하고, Spring은 도시·유형·중복·필수 장소·결과 개수를 검증한다.
- 자동 테스트는 `FakeGooglePlacesClient`를 사용하고 실제 Google API를 호출하지 않는다.

## 이유

- 하나의 Place ID를 Places, Routes, Maps JavaScript API에서 연결해 사용할 수 있다.
- 전 세계 장소 데이터의 수집·정정·갱신 책임을 프로젝트가 직접 떠안지 않는다.
- 외부 API 통신과 여행 일정 규칙을 분리해 테스트할 수 있다.
- Google 제공 데이터와 Routy가 생성한 일정·순서·추천 점수의 소유 경계가 명확해진다.

## 재검토 조건

- Google 정책 또는 비용 구조가 프로젝트 요구와 맞지 않게 변경될 때 provider 교체를 검토한다.
- 오프라인 조회나 장기 보존이 필요해지면 저장이 허용되는 자체·공공 장소 데이터와 Google 참조를 분리하는 방안을 검토한다.

## 공식 참고

- Google Place ID: https://developers.google.com/maps/documentation/places/web-service/place-id
- Google Places 저장·표시 정책: https://developers.google.com/maps/documentation/places/web-service/policies

# ADR-017 - 목적지 현지 시각 기반의 시간표와 식사 슬롯을 사용

## 상태

Accepted for MVP

## 문제

장소 수만 균등 배치하면 놀이공원과 전망대를 같은 체류 시간으로 취급하고, 오후 3시처럼 식사하기 부자연스러운 시각에 거리만 가까운 음식점을 추천할 수 있다.

## 결정

- 하루 기본 범위는 목적지 현지 시각 `10:00~21:00`이며 사용자가 시작·종료 시각을 변경할 수 있다.
- `StayDurationPolicy`는 Google 장소 유형을 60·90·120·180·240·360분의 기본 체류 시간에 결정적으로 매핑한다. 여러 유형이면 가장 긴 값을 사용하고, 사용자 수정값이 항상 우선한다.
- 관광 장소는 하루 최대 6개지만 실제 수용 가능 여부는 시간표로 판단한다. ADR-022에 따라 긴 체류 안의 식사·외출 이동은 체류에 포함하고, 체류 밖 식사·이동만 별도로 반영한다.
- 최종 시간표는 Google Routes의 `TRAFFIC_UNAWARE` 이동 시간으로 계산한다. Haversine은 알고리즘 학습·fallback 검토용이며 최종 시간표의 정상 결과로 표시하지 않는다.
- 점심은 `11:30~14:00`, 저녁은 `17:30~20:30` 안에서만 추천하며, 사용자 지정 하루 범위에 해당 시간대가 60분 이상 포함될 때만 슬롯을 만든다.
- 긴 체류가 식사 시간대 전체를 포함하면 Google Places 포함 관계로 확인된 내부 음식점을 우선하고, 없으면 장소 중심 Nearby Search의 인접 후보를 추천한다.
- 음식점 후보는 자동 확정하거나 영구 저장하지 않는다.
- 필수 장소를 포함한 시간 용량이 부족하면 장소를 임의로 삭제하지 않고 요청을 거절한다.

## 이유

- 장소 성격에 맞는 체류 시간을 사용해 현실적인 시간표를 만들 수 있다.
- 식사 추천이 거리만 짧은 부자연스러운 시각에 배치되는 것을 막는다.
- 외부 호출과 순수 알고리즘을 분리해 fake 행렬과 정책 단위 테스트가 가능하다.

## 외부 API 경계

- `route/client`만 Google Routes를 호출한다.
- `route/algorithm`은 거리·시간 행렬만 입력받는다.
- `recommendation`은 음식점 후보의 시간대·내부/인접 관계·이탈 비용을 검증하고 정렬한다.

## 공식 참고

- Google Routes route matrix: https://developers.google.com/maps/documentation/routes/compute_route_matrix
- Google Routes Place ID 위치 지정: https://developers.google.com/maps/documentation/routes/specify_location-rm
- Google Places Nearby Search: https://developers.google.com/maps/documentation/places/web-service/nearby-search
- Google Places 장소 유형: https://developers.google.com/maps/documentation/places/web-service/place-types

# ADR-018 - Google Place ID 전체 검증 후 일정 저장 트랜잭션을 시작

## 상태

Accepted for MVP

## 문제

형식이 올바른 Google Place ID라도 다른 도시의 장소이거나, 호텔을 관광지로 전달하거나, 일정에 없는 장소의 체류 시간을 수정하는 등 역할과 관계가 잘못될 수 있다. 외부 검증 중 DB 저장을 시작하면 provider 장애 시 일부 Place 참조나 일정만 남을 수도 있다.

## 결정

TravelPlan 생성과 재계산 전에 다음 검증을 모두 수행한다.

1. 선택 도시는 Google Places에 존재하고 도시 유형이어야 한다.
2. 필수·선택 방문 장소는 존재하고 허용된 관광 유형이며 선택 도시 소속이어야 한다.
3. 호텔은 존재하고 허용된 숙박 유형이며 선택 도시 소속이어야 한다.
4. 필수·선택 목록 내부와 목록 사이, 도시·호텔·방문 장소 역할 사이에 Google Place ID 중복이 없어야 한다.
5. 체류 시간 수정 ID는 중복 없이 최종 방문 장소 집합에 포함돼야 한다.
6. 도시 소속을 Google 응답의 포함 행정구역 등으로 확인할 수 없으면 일치한다고 추측하지 않고 거절한다.
7. Google Places·Routes 검증과 일정 계산을 모두 끝낸 뒤 DB 트랜잭션을 시작해 Place 참조와 TravelPlan Aggregate 전체를 저장한다.

하나라도 실패하면 요청 전체를 거절한다. 이미 존재하던 공유 Place 데이터는 변경하지 않으며, 현재 요청 때문에 새 Place 참조나 일부 Day·PlanPlace가 남아서는 안 된다.

## 이유

- 사용되지 않는 입력을 조용히 무시하지 않아 API 사용자의 오해를 막는다.
- 다른 도시나 잘못된 유형의 장소가 일정에 섞이는 것을 방지한다.
- 느린 외부 호출 동안 DB 트랜잭션을 유지하지 않는다.
- provider 실패와 DB 실패 모두에서 원자적인 일정 저장을 보장한다.

## 책임 경계

- `TravelPlanService`: 목록 관계·중복·체류 시간 수정 대상 검증과 전체 흐름 조합
- `PlaceService`: Google 장소 존재·유형·도시 소속 검증
- `RouteService`와 `RecommendationService`: 검증된 장소만 입력받아 계산
- Repository: 검증 정책을 판단하지 않고 트랜잭션 안에서 저장

# ADR-019 - T1 저장 계층과 T2 일정 생성·공개 API를 분리

## 상태

Accepted

## 문제

Google Routes 기반 시간표 도입으로 도착·출발 시각과 체류 시간이 필수 저장값이 됐다. 기존 로드맵은 T1에서 기본 CRUD를 구현하고 T2에서 시간표를 계산하도록 되어 있어, T1에서 임시 값을 만들거나 아직 없는 계산 기능을 앞당겨 구현할 위험이 있었다.

## 결정

- T1은 계산 완료 일정의 내부 전달 DTO와 저장·조회·교체·삭제 계층을 구현한다. HTTP API는 노출하지 않는다.
- 테스트는 고정된 완성 일정 fixture를 전달해 필수 저장값, DB 제약, 조회 결과, 원자적 저장·교체·삭제를 검증한다.
- 시각·체류 시간의 DB 제약을 유지하며 운영용 임시 시간값이나 학습용 중간 생성 API를 만들지 않는다.
- T2는 Google 검증과 시간표 계산을 완료한 뒤 T1 저장 계층을 호출한다. Place 참조 저장도 같은 트랜잭션에 참여하도록 Place Service 계약을 사용한다.
- 공개 생성·조회·수정·삭제 API는 T2에서 연결한다. T1의 내부 DTO는 HTTP 계약으로 사용하지 않는다.
- T1은 영속성 검증 완료로만 기록하며, 외부 검증·일정 계산·공개 API의 완료 판정은 T2로 이월한다.
- ADR-015의 호텔 DB nullable 결정은 유지한다. 이는 별도 기본 계획 API를 제공한다는 의미가 아니다.

## 이유

JPA 연관관계와 트랜잭션을 외부 통신·시간표 알고리즘에 앞서 학습하면서도 최종 저장 구조를 그대로 사용할 수 있다. 테스트용 일정과 실제 생성 결과는 같은 저장 계약을 사용하되, 생성 결과의 정확성은 T2에서 별도로 검증한다.

## 재검토 조건

사용자가 편집 중인 미완성 계획을 저장하는 기능이 실제 요구사항으로 추가되면, 별도 초안 계약과 저장 정책을 설계한다.

# ADR-020 - 식사 시간은 저장하고 음식점 후보 검색은 분리

## 상태

Accepted

## 문제

식사 슬롯을 저장하지 않고 조회마다 계산하면 사용자가 저장한 식사 시간이 달라질 수 있다. Google 표시 정보와 저장된 일정의 책임을 구분해야 한다.

## 결정

- Day에 속한 `TravelPlanMealSlot`에 식사 종류·확정 시작·종료 시각을 저장한다. Google 음식점 콘텐츠와 음식점 Place 참조는 저장하지 않는다.
- GET은 저장된 순서·방문 시각·식사 슬롯을 유지하고 Google Places로 표시 정보만 조회한다.
- 음식점 후보는 별도 요청으로 검색한다. 생성·조회·수정 응답에는 후보 목록을 포함하지 않으며 검색 결과는 저장된 시간표를 변경하지 않는다.
- 일정 조건 수정은 외부 검증·재계산 성공 후 방문 일정과 식사 슬롯을 원자적으로 교체한다. 실패 시 기존 일정을 보존한다. 음식 목록만 변경하면 시간표를 유지한다.
- T1부터 식사 슬롯의 저장·조회·교체·삭제를 fixture로 검증하고 공개 API는 T2에서 연결한다.

## 이유

저장된 식사 시간을 유지하면서 음식점은 필요할 때 최신 후보로 검색할 수 있다. 음식점 검색 장애가 일정 저장을 막지 않는다.

## 구현 전 남은 논의

검색 입력 계약은 ADR-021, 체류·식사·이탈 이동 시간의 합산 규칙은 ADR-022에서 확정했다. 후보 검색은 확정된 시간표 안에서 수행하며 자동 재배치로 우회하지 않는다.

## 재검토 조건

사용자가 음식점을 일정에 확정하거나 식사 시간을 직접 편집하는 기능을 요청하면 별도 계약을 설계한다.

# ADR-021 - 음식점 검색은 저장된 계획·날짜·식사 종류로 식별

## 상태

Accepted

## 결정과 이유

검색 요청은 `travelPlanId`, `date`, `mealType`, `food`만 받는다. 도시·호텔·하루 범위·방문 시각·식사 시각은 서버가 저장 일정에서 확보한다. 클라이언트가 별도 시간표를 보내 저장값과 불일치하는 문제를 방지한다. 음식은 이번 검색 조건이며 저장된 선호를 변경하지 않는다.

URL은 `/api/recommendations/restaurants`를 유지하고 `travelplan`의 Controller·Service가 조회를 조합한다. `recommendation`은 전달 DTO로 후보를 계산하며 TravelPlan을 역참조하지 않는다. R2에서는 계산 Service를 고정 DTO로 검증하고 공개 API 연결은 T2-07A에서 수행한다.

없는 계획·기간 밖 날짜·없는 슬롯은 외부 검색 전에 오류로 반환한다. 후보가 없는 정상 검색과 제공자 장애를 구분하며, 모든 검색은 저장된 일정과 슬롯을 유지한다. 시간 합산 규칙은 ADR-022를 따른다.

# ADR-022 - 긴 체류에는 식사와 음식점 왕복 이동을 포함

## 상태

Accepted

## 결정

긴 체류 장소의 식사 60분과 인접 음식점 왕복 이동은 기존 체류 시간에 포함한다. 예를 들어 360분 체류 중 식사 60분·왕복 이동 20분이면 관광 가능 시간은 280분이며 장소 출발 시각은 유지한다. 체류에 포함된 식사·이동을 일일 용량에 다시 더하지 않는다. 일반 장소 사이의 식사는 체류와 별도로 확보한다.

후보는 고정된 식사 시작까지 도착하고 식사 후 해당 장소의 출발 또는 다음 방문의 도착 시각을 지켜야 한다. 조건을 만족하는 내부 후보가 없으면 인접 후보를 검토하고, 모두 없으면 빈 목록을 반환한다. 후보 검색을 위해 식사 시각·체류·이후 일정을 변경하지 않는다. 상세 경계식은 요구사항 FR-11, 검증 항목은 테스트 전략을 따른다.

## 이유와 영향

사용자가 지정한 장소 체류 시간을 전체 방문 시간으로 해석한다. 식사를 위해 장소에 머무는 시간을 자동 연장하지 않으며, 대신 실제 관광에 쓸 수 있는 시간이 줄어든다. 최소 순수 관광 시간을 별도로 강제하는 정책은 이번 결정에 추가하지 않는다.

# ADR-023 - 일정 배치는 입력 우선순위와 가장 이른 날짜를 사용하는 결정적 탐욕 방식으로 시작

## 상태

Superseded in part by ADR-024 (자동 날짜 배치·식사 시각 선택). 사용자 지정 날짜 유지와 실패 시 기존 일정 보존 결정은 유지한다.

## 결정

MVP의 기본 날짜별 일정 배치는 필수 장소의 요청 순서, 선택 장소의 요청 순서로 후보 우선순위를 고정한다. 각 후보를 첫째 날부터 날짜순으로 임시 추가하고, 호텔 왕복 경로와 체류·이동·식사 시간을 다시 계산해 최대 6개와 시간 용량을 모두 만족하는 가장 이른 날짜에 확정한다. 비교 우선순위가 같으면 Google Place ID 오름차순으로 결정한다.

모든 날짜에 배치할 수 없는 장소가 하나라도 있으면 해당 장소를 제외하거나 다른 후보로 바꾸지 않고 `PLAN_CAPACITY_EXCEEDED`로 전체 요청을 거절한다. 점심은 12:00, 저녁은 18:00 시작을 우선하고, 하루 범위 때문에 불가능하면 허용 시간대와 하루 범위가 겹치는 구간의 가장 이른 연속 60분을 사용한다.

사용자는 수정 요청에서 모든 최종 방문 장소의 날짜를 직접 지정할 수 있다. 이 경우 서버는 날짜 그룹을 바꾸지 않고 각 날짜 안의 경로와 시간표만 다시 계산한다. 배정 목록이 최종 장소 집합과 다르거나 여행 기간 밖 날짜를 포함하면 거절하며, 지정한 날짜의 수량·시간 용량을 초과해도 다른 날짜로 자동 이동하지 않고 기존 계획을 유지한다. 배정 목록을 생략한 채 일정 조건을 바꾸면 기본 자동 배치를 다시 적용하고, 음식 목록만 바꾸면 기존 배치와 시간표를 유지한다.

## 이유

같은 입력에 항상 같은 결과를 만들고 필수 장소와 사용자가 선택한 장소를 조용히 누락하지 않기 위해서다. 초기 구현에서 전역 최적 배치를 탐색하는 복잡도를 피하면서도 각 날짜의 실제 이동 시간과 식사 시간을 기준으로 수용 가능 여부를 판단할 수 있다.

## 재검토 조건

가장 이른 날짜 우선 배치가 전체 이동 시간이나 날짜별 편차를 과도하게 키운다는 실제 사례가 확인되면, 입력·출력 계약은 유지한 채 날짜 배치 정책을 교체한다. 변경 시 기존 방식과 결과·시간 복잡도를 비교하는 테스트를 추가한다.

# ADR-024 - 소요 시간 분산과 식사 이동 여유, 저장 후 음식점 검색 유지

## 상태

Accepted (2026-09-09), 구현 전. ADR-023의 자동 배치·식사 시각 선택을 대체하고 ADR-022의 일반 구간 시간 합산을 보완한다.

## 문제

앞 날짜부터 채우면 여행 기간이 길어도 관광지가 첫날에 몰릴 수 있다. 식사만 60분 예약하면 저장 후 음식점 검색에서 경유 시간이 부족할 수 있다. 사용자는 일정 저장 후 음식점 후보를 별도로 검색하는 흐름을 유지하기로 했다.

## 결정

- 필수·선택 입력 순서를 유지하면서 각 장소를 추가한 뒤 소요 시간이 최소인 유효한 날짜를 선택한다. 동률은 날짜순이다. 대기·자유 시간은 분산 점수에서 제외하고 하루 용량 검증에는 포함한다.
- 전체 배치 후 단일 장소 이동으로 날짜 간 최대·최소 소요 시간 차이를 줄이는 보정을 최대 장소 수만큼 수행한다. 엄격한 개선과 결정적 동률 규칙은 FR-11을 따른다. 사용자 날짜 배정은 보정하지 않는다. 관광지가 없는 날은 자유 일정으로 보존한다.
- 일반 식사는 직접 이동에 더해 60분과 한쪽 기본 15분의 여유를 예약한다. `mealTravelBufferMinutes`는 0~60분 정수이며 계획에 저장한다. 직접 이동 분배·복수 식사·긴 체류의 중복 합산 방지와 시각 선택은 FR-11을 따른다.
- 음식점은 생성·수정 중 검색하지 않는다. 별도 검색은 저장 시각을 지킬 수 있는 후보만 반환하며, 빈 결과 원인과 provider 장애를 구분한다. 후보가 반드시 존재하거나 따로 검색한 후보 조합을 함께 방문할 수 있다고 보장하지 않는다.
- 여유를 늘리는 명시적 PUT은 재계산을 수행하며 실패하면 입력·일정·슬롯 전체를 보존한다. 음식만 바꾼 검색은 저장값을 변경하지 않는다.

## 영향과 검증

여유 확보는 후보 방문 가능성을 높이기 위한 정책이지 실측 개선율이나 성공 보장이 아니다. 여유 때문에 관광 장소가 덜 들어갈 수 있다. 긴 체류 내부 식사는 별도 여유를 더하지 않는다. 탐욕 배치와 제한된 보정은 전역 최적해·완벽한 균등 배치를 보장하지 않는다.

T1에서 여유값 저장을 준비하고, R2는 완성 fixture의 실제 시간 조건과 빈 결과 사유를 검증하며, T2에서 분산·식사 배치·명시적 재계산을 조합한다. 날짜 수 D, 장소 수 N에 대해 초기 배치는 최대 N×D회의 하루 평가, 보정은 최대 N×N×(D-1)개의 이동 후보 평가를 수행한다. 각 평가는 하루 최대 6개 장소와 최대 2개 식사 슬롯을 대상으로 한다. 시간 행렬은 요청 내 재사용하며 후보 평가마다 외부 API를 다시 호출하지 않는다. T2-01에서 하루 평가의 시각 탐색 비용까지 설명하고 최대 입력 fixture로 검증한다.

# ADR-025 - 화면은 API 단계별로 연결하고 MVP 지도는 마커와 방문 순서를 표시

## 상태

Accepted (2026-09-09), 구현 전.

## 결정

- 브라우저 흐름은 목적지 선택, 여행 조건, 장소·호텔 선택, 일정 생성·지도 확인, 날짜 수정, 음식점 검색, 로그인 후 다시 열기 순서다. 도시 직접 선택은 AI 추천을 건너뛴다.
- 화면 골격은 F0 뒤에 준비하고, 공개 API가 완성될 때마다 해당 화면을 연결한다. 전체 백엔드 완료 뒤 한 번에 연결하지 않는다.
- MVP 지도는 현재 Google 표시 좌표로 호텔·관광지 마커와 날짜별 방문 번호를 표시한다. 도로 polyline과 실시간 위치·교통은 후속 범위다.
- 일정 조회 응답은 지도 표시 좌표를 제공하지만 이를 Routy DB에 영구 저장하지 않는다. 지도 렌더링 실패는 일정 저장·조회 결과를 변경하지 않는다.
- 로그인 전에는 생성 직후 받은 ID로 현재 일정을 볼 수 있다. 영구적인 다시 열기는 U1의 인증된 내 일정 목록을 사용하며 브라우저 저장소를 소유권 근거로 삼지 않는다.

## 이유와 영향

단계별 연결은 API와 화면의 불일치를 해당 기능이 작을 때 발견하게 한다. 마커·방문 번호만으로도 날짜별 위치와 순서를 확인할 수 있고, 도로선 계약과 추가 호출 비용은 실제 필요를 확인한 뒤 설계할 수 있다. 사이트 완료는 API 테스트만으로 판정하지 않고 핵심 브라우저 흐름과 실제 연동 smoke 결과를 함께 확인한다.

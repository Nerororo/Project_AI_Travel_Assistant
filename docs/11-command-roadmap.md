# Codex 대화형 구현 로드맵

## 1. 역할과 사용법

이 문서는 Routy의 실제 작업 순서와 작업 ID를 관리한다. 큰 개발 방향은 `docs/05-development-plan.md`, 현재 구현 상태는 `docs/07-implementation-readiness.md`, 경로별 수정 범위는 `docs/12-harness-boundaries.md`를 따른다.

한 번에 작업 ID 하나만 진행한다. 구현 전에는 적용되는 문서를 읽고 다음 Change Envelope를 제시한다.

Change Envelope 형식과 변경 전후 검사는 `docs/12-harness-boundaries.md`, 완료 판정은 `docs/10-definition-of-done.md`를 따른다. 표의 요청 문구는 작업 선택 예시이며 승인 범위를 넓히지 않는다.

## 2. 완료된 선행 기준과 전체 순서

구현을 시작하기 위한 문서·정책 게이트는 완료됐다.

- `D0`: 요구사항·아키텍처·DB·API·테스트·운영·완료 기준과 하네스 경계를 현재 제품 계약에 맞게 정렬했다. 개별 문서 편집 이력은 이 로드맵에서 관리하지 않는다.
- `K0-02A`: 2026-09-11 카카오 DevTalk 답변을 ADR-028과 관련 계약에 반영했다. 정책 확인은 기능 구현 완료가 아니며 P1 이후 좌표 기반 구현은 일시 사용·즉시 폐기 조건을 지켜야 한다.

앞으로 진행할 구현 순서는 다음과 같다.

```text
F0 개발 기반
→ U1 인증·소유권 → W1-01A 가능
→ G1 국내 지역 기준
→ A1 지역·메뉴 AI → W1-01B 가능
→ R1 순수 거리·경로
→ C1 Place·Route Client 계약과 Fake
→ P1 장소 → W1-02·W1-02A 가능
→ R2 독립 경로 기반
→ S1 추정 일정·추천 → W1-03·W1-03A 가능
→ T1 외부 경로 통합·완료 일정 저장·API → W1-04·W1-05 가능
→ W1-06 화면 전체 회귀 → Q1 운영
```

인증은 사용자별 호출 한도와 일정 소유권의 선행 조건이다.

위 순서는 백엔드의 주 흐름과 화면 Task가 시작 가능한 시점을 함께 표시한다. 한 번에는 여전히 작업 ID 하나만 진행하며, W1 전체를 T1 뒤까지 미루지 않고 표의 선행 조건을 충족한 Task부터 연결할 수 있다.

## 6. A1 — 지역·메뉴 AI

선행 조건: U1과 G1 완료.

지역 추천은 G1의 허용 지역 목록만 사용한다. 메뉴 분석의 관광지 맥락은 브라우저가 부여한 `clientPlaceId`와 사용자 작성 이름으로 전달하며 Place·Route 구현에 의존하지 않는다.

| ID | 작업 | 완료 확인 |
|---|---|---|
| A1-01 | 지역 추천·메뉴 분석 계약·DTO·Fake·Service | 지역은 허용 목록에서 정확히 3개, 메뉴는 1~5개·검색어·이유·선택적 대상 관광지, 계약 위반 테스트 |
| A1-02 | OpenAI 공통 공식 계약 감사 | 모델·구조화 출력·endpoint·인증·timeout·재시도·비용·전체 예산 확정 |
| A1-03 | 승인된 계약에 따른 공통 OpenAI Client와 기능별 응답 매핑 | 공통 HTTP transport 재사용, 지역·메뉴 검증 분리, 자동 테스트는 Fake |
| A1-04 | 지역 추천 API와 인증·한도·`requestId` 연결 | 2회/분·10회/일, 중복 실행·차감 방지와 HTTP 오류 계약 |
| A1-05 | 메뉴 분석 API와 인증·한도·`requestId` 연결 | 3회/분·15회/일, 구조 오류 1회 재시도, 재실패 오류와 직접 입력 fallback 계약 |
| A1-06 | AI 단계 DoD 점검 | 실제 OpenAI 없는 자동 테스트, 원문·비밀값 미저장, 지역·메뉴 API 계약 통과 |

## 15. 작업 종료 보고

각 작업의 완료 보고에는 다음을 포함한다.

1. 변경 결과와 수정 파일
2. Change Envelope와 범위 밖 변경 여부
3. 관련 테스트와 전체 테스트 결과
4. `git diff --check` 결과
5. 확인한 DoD 항목
6. 남은 미확정 사항과 외부 제공자 재확인 항목
7. 처음 사용한 Spring 개념 설명

완료 판정 뒤에는 `docs/07-implementation-readiness.md`의 실제 구현 상태와 이 문서 16절의 다음 시작 작업을 함께 갱신한다. 두 파일은 Change Envelope에 실제 상태 변경을 위한 Conditional Paths로 미리 적고, 관련 테스트·전체 테스트·`git diff --check`·DoD 증거가 없으면 완료 또는 다음 작업으로 이동했다고 기록하지 않는다. 점검 작업에서 문제를 발견했지만 수정하지 않았다면 상태만 사실대로 기록하고 해당 수정은 별도 Task ID와 Change Envelope로 제안한다.

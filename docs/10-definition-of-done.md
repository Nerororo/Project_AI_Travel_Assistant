# Definition of Done

## 1. 목적

이 문서는 기능이 단순히 구현된 상태와, 요구사항·테스트·문서·운영 기준까지 갖춘 완료 상태를 구분한다.

현재 구현 상태는 `docs/07-implementation-readiness.md`에서 관리하며, 이 문서에는 완료 판정 기준만 둔다.

기능이 아래 조건을 만족하기 전에는 README나 개발 계획의 체크박스를 완료로 바꾸지 않는다.

## 2. 모든 기능의 공통 완료 조건

- [ ] 관련 요구사항, API, DB, ADR 문서의 현재 기준을 확인했다.
- [ ] 변경 범위가 한 도메인 또는 한 API 흐름으로 제한되어 있다.
- [ ] Controller, Service, Repository, Entity, DTO 책임이 프로젝트 규칙에 맞게 분리되어 있다.
- [ ] 성공 시나리오와 최소 한 개의 실패 또는 경계 시나리오를 자동 테스트했다.
- [ ] API가 있으면 해당 API에 적용되는 성공·validation·not found 등 상태 코드와 오류 응답이 명세와 일치한다.
- [ ] `./gradlew test`가 통과한다.
- [ ] API, DB 스키마, 설정, 알고리즘이 바뀌었다면 관련 문서를 갱신했다.
- [ ] 설계 선택이 바뀌었다면 ADR을 추가하거나 기존 ADR의 재검토 상태를 갱신했다.
- [ ] 로그·오류 응답·테스트 fixture에 비밀값이나 사용자 원문이 없다.

## 3. Place와 Google Places 완료 조건

- [ ] Google Places client 인터페이스와 실제 HTTP 구현, fake 구현이 분리돼 있다.
- [ ] 국가·도시·관광지·호텔·음식점 유형을 서버가 검증한다.
- [ ] `google_place_id` UNIQUE와 내부 Place 참조 FK가 migration에 반영됐다.
- [ ] Google 장소 본문을 별도 허용 근거 없이 영구 저장하지 않는다.
- [ ] timeout·provider 오류·장소 없음이 API 오류 계약과 일치한다.
- [ ] 도시 직접 선택과 장소 상세 API 테스트, DB 통합 테스트가 통과한다.

## 4. TravelPlan 완료 조건

T1의 완료 범위는 내부 저장 계층이다. 공통·DB 완료 조건 중 적용 항목과 `08-test-strategy.md`의 T1 저장·조회·교체·삭제·rollback 검증을 충족해야 한다. Google 검증, 시간표 계산, 공개 CRUD API는 T2로 이월하며 T1 완료를 TravelPlan 기능 전체 완료로 표시하지 않는다. 아래 전체 체크리스트는 T2-08에서 확인한다.

- [ ] 시작일·종료일, 장소 중복, 필수 장소, 일일 최대 6개 장소 제약이 검증된다.
- [ ] 목적지 현지 시각 기본 `10:00~21:00`과 사용자 지정 시작·종료 시각이 저장·수정·검증된다.
- [ ] 장소 유형별 기본 체류 시간과 사용자 수정값 우선 규칙이 결정적으로 적용된다.
- [ ] 긴 체류 안의 식사·음식점 왕복 이동을 체류 시간에 포함해 중복 합산하지 않으며, 시간표가 일일 용량을 넘으면 필수 장소를 누락시키지 않고 요청을 거절한다.
- [ ] 필수 장소가 최종 일정에서 누락되지 않는다.
- [ ] 날짜별 시간 용량 안에서 배치하고 날짜별 경로만 최적화한다.
- [ ] 저장·수정·삭제가 Aggregate 생명주기와 DB 삭제 정책을 지킨다.
- [ ] 실패 시 일부 Day·Place 관계만 남지 않도록 트랜잭션을 검증했다.
- [ ] 일정 응답의 `assumptions`, 숙소, 저장된 식사 슬롯이 API 계약과 일치하며 음식점 후보는 별도 검색 응답으로만 제공한다.
- [ ] GET은 장소 표시 정보만 갱신하며 저장된 방문 순서·시각·식사 슬롯을 재계산하거나 변경하지 않는다.
- [ ] 일정 조건 수정은 식사 슬롯까지 원자적으로 교체하고 재계산·저장 실패 시 기존 일정을 유지한다. 음식 선호만 수정하면 시간표는 유지한다.
- [ ] 식사 슬롯의 DB 제약과 일정 삭제 시 함께 삭제되는 생명주기를 검증했다.
- [ ] 선택 도시와 모든 방문 장소·호텔의 Google Place ID 참조가 저장된다.
- [ ] 선택 도시·방문 장소·호텔의 존재, 허용 유형, 도시 소속을 저장 전에 검증한다.
- [ ] 필수·선택 목록과 역할 사이 중복, 일정에 없는 체류 시간 수정 대상을 거절한다.
- [ ] Google 검증·경로 계산은 DB 트랜잭션 전에 끝나며 실패 시 새 Place 참조나 일부 일정 데이터가 남지 않는다.
- [ ] 생성·조회·수정·삭제 API와 핵심 통합 테스트가 통과한다.

## 5. Route와 Recommendation 완료 조건

- [ ] 거리 계산은 단위와 반올림 규칙을 포함해 단위 테스트됐다.
- [ ] RouteOptimizer는 빈·단일·복수 장소와 동률 거리에서 결정적으로 동작한다.
- [ ] 모든 장소를 중복 없이 한 번씩 방문한다.
- [ ] 2-opt를 추가했다면 기존 경로보다 길어지지 않는 테스트가 있다.
- [ ] Google Routes의 정적 이동 시간·거리 행렬은 `route/client`에서 가져오고 fake client로 테스트된다.
- [ ] 호텔은 총 이동 거리, 음식점은 식사 시간 충족·음식 일치·동선 이탈 시간과 거리 기준으로 정렬된다.
- [ ] 점심·저녁 범위 밖에는 식사 슬롯을 만들지 않으며 긴 체류 시 시간 조건을 만족하는 내부 후보 우선·인접 후보 대체가 검증된다. 음식점 왕복이 체류 구간을 넘거나 후속 일정에 늦으면 후보를 제외하고 저장 시각은 유지한다.
- [ ] 알고리즘은 Spring, DB, AI에 직접 의존하지 않는 순수 Java 로직으로 유지된다.

## 6. AI 도시 추천 완료 조건

- [ ] `AiClient`와 provider HTTP 구현이 분리되어 있다.
- [ ] 도시 후보 JSON Schema/structured output과 Java DTO validation을 모두 적용한다.
- [ ] 도시 후보 수·국가 코드·필수 필드·JSON 파싱 실패가 `AI_RESPONSE_INVALID`으로 변환된다.
- [ ] AI가 만든 도시 이름은 Google Places가 실제 도시와 국가 일치를 검증한 뒤에만 반환한다.
- [ ] timeout·provider 5xx는 최대 한 번 재시도한 뒤 `AI_UNAVAILABLE`으로 변환된다.
- [ ] 인증 오류와 요청 오류는 재시도하지 않는다.
- [ ] fake `AiClient`만으로 성공·계약 위반·장애 테스트가 통과한다.
- [ ] 자동 테스트는 실제 OpenAI를 호출하지 않는다.
- [ ] API 키, 사용자 원문, provider 원문 요청·응답이 로그 또는 오류 응답에 없다.

## 7. DB와 migration 변경 완료 조건

- [ ] 새 테이블·컬럼·인덱스·제약조건은 versioned Flyway migration으로 추가했다.
- [ ] 이미 적용된 migration 파일을 수정하지 않았다.
- [ ] 빈 DB에서 migration 적용을 검증했다.
- [ ] UNIQUE, CHECK, FK 등 의도한 DB 무결성 제약을 통합 테스트했다.
- [ ] 파괴적 변경이면 데이터 백업, 호환 기간, 복구 절차를 별도 계획에 기록했다.
- [ ] 운영 profile에서 `ddl-auto: validate`로 schema 일치를 확인한다.

## 8. 외부 API와 운영 변경 완료 조건

- [ ] 실제 외부 API 호출은 자동 테스트와 분리됐다.
- [ ] timeout, 재시도 대상, 오류 코드 변환을 명시하고 테스트했다.
- [ ] 호출량·오류율은 원문 payload 없이 집계할 수 있다.
- [ ] health check에서 앱·DB와 외부 의존성 상태를 구분한다.
- [ ] profile별 비밀값과 로그 정책을 확인했다.
- [ ] 배포 전후 체크리스트는 `docs/09-operations.md`를 따른다.

## 9. 완료 기록 방법

기능 완료 시 다음을 함께 갱신한다.

1. 필요하면 README와 `11-command-roadmap.md`의 현재 작업
2. API, DB, 아키텍처 문서 중 변경된 계약
3. 새 설계 결정이 있다면 `06-decisions.md`
4. 테스트 실행 결과와 수동 smoke test 결과(수행했다면)

커밋은 하나의 기능 또는 설계 변경을 설명할 수 있는 작은 단위로 준비한다. 이 문서는 커밋 자체를 강제하지 않지만, 완료된 변경이 무엇인지 추적 가능해야 한다.

# 프로젝트 요구사항 명세서

## 1. 프로젝트 개요

### 프로젝트명

**Routy - AI 여행 일정 관리 & 최적화 서비스**

### 목적

사용자가 국가 또는 도시를 선택하면 여행 도시와 방문 장소 후보를 제공하고, 선택된 장소들의 위치를 기반으로 이동 동선을 최적화하여 여행 일정을 생성한다. 사용자는 도시를 직접 선택할 수 있으며, 국가만 선택한 경우에는 AI가 도시 후보를 제안하고 Google Places가 실제 도시를 검증한다.

또한 선택된 관광지들을 방문하기 유리한 위치의 호텔과 각 날짜의 여행 동선 근처에서 사용자가 원하는 음식을 먹을 수 있는 음식점을 추천한다.

---

## 2. 프로젝트 핵심 원칙

이 프로젝트에서 AI와 Spring Backend의 책임을 명확히 분리한다.

### AI가 담당하는 영역

- 국가를 기준으로 도시 후보 생성
- 도시 후보의 추천 이유 생성
- 음식 관련 자연어 해석(후속 범위)
- 사용자에게 보여줄 추천 이유나 일정 설명 생성

### Spring Backend가 담당하는 영역

- 사용자 및 여행 데이터 저장
- Google Places를 통한 국가·도시·장소 검증
- Google Place ID 기반 장소 참조 관리
- 여행 계획 생성 및 저장
- 장소 간 거리 계산
- 호텔 후보 평가
- 음식점 후보 평가
- 여행 경로 최적화
- 비즈니스 규칙 적용
- Validation / Exception Handling
- 인증 / 인가
- 테스트

### 금지 원칙

다음 기능을 LLM의 답변만으로 결정하지 않는다.

- 최단 이동 거리 계산
- 경로 최적화
- 호텔의 이동 효율 점수 계산
- 음식점의 동선 이탈 거리 계산

## 3. 사용자 시나리오

### 시나리오 A - 국가 기반 도시 후보 추천

사용자가 다음과 같이 입력한다.

> 일본

서비스는 선택된 국가를 Google Places로 검증한 뒤 AI를 이용해 도시 후보를 만든다.

예:

```json
{
  "countryGooglePlaceId": "ChIJ...",
  "cities": ["도쿄", "오사카", "교토"]
}
```

서버는 각 도시를 Google Places로 다시 검증하고 Google Place ID가 확인된 후보만 사용자에게 제공한다. 사용자는 후보 중 하나를 선택하거나 Google 장소 검색을 통해 도시를 직접 선택할 수 있다.

---

### 시나리오 B - 도시 직접 선택과 장소 추천

사용자가 다음 정보를 입력한다.

- 도시: 부산(Google Place ID로 선택)
- 반드시 방문할 장소: 해운대, 감천문화마을
- 먹고 싶은 음식: 돼지국밥, 회

서비스는 Google Places에서 부산의 관광지 후보를 조회하고, 필수 장소를 포함하면서 추가 방문 장소와 음식점 후보를 추천한다.

---

### 시나리오 C - 여행 계획 생성

사용자가 추천 여행지 중 방문할 장소를 선택하면 시스템은 다음 과정을 수행한다.

1. 선택 장소의 위치 정보 확보
2. 장소 간 거리 계산
3. 호텔 후보 평가
4. 날짜별 방문 장소 분배
5. 날짜별 이동 경로 최적화
6. 동선 근처 음식점 추천
7. 최종 여행 일정 생성
8. 여행 계획 DB 저장

---

### 시나리오 D - 브라우저에서 완료하는 전체 여행 계획 흐름

사용자는 다음 순서로 한 번의 여행 계획을 완료한다.

1. Google 장소 검색으로 국가 또는 도시를 선택한다.
2. 국가를 선택했다면 AI 도시 후보를 확인하고 하나를 선택한다. 도시를 직접 선택했다면 이 단계를 건너뛴다.
3. 여행 날짜, 하루 활동 시간, 식사 이동 여유와 원하는 음식을 입력한다.
4. 필수 장소를 검색하고 추천 관광지를 선택하며 필요한 장소의 체류 시간을 조정한다.
5. 선택한 관광지를 기준으로 호텔 후보를 확인하고 하나를 선택한다.
6. 일정을 생성·저장한 뒤 날짜별 시간표와 지도에서 장소 마커·방문 순서를 확인한다.
7. 필요하면 장소별 날짜를 다시 배정하고 재계산한다. 실패하면 기존 일정을 계속 볼 수 있어야 한다.
8. 저장된 점심·저녁 슬롯에서 원하는 음식으로 음식점 후보를 검색한다. 빈 결과는 이유를 구분해 안내한다.
9. 인증 완료 후 내 일정 목록에서 저장한 일정을 다시 연다.

화면은 사용자가 이미 완료한 입력과 선택을 다음 단계에서도 유지한다. 로딩 중 중복 요청을 막고, validation·빈 결과·외부 제공자 장애를 사용자가 다음 행동을 선택할 수 있는 문구로 표시한다. API 오류의 원문이나 비밀값을 표시하지 않는다.

MVP 지도는 일정 조회 응답의 현재 좌표로 호텔과 관광지 마커, 날짜별 방문 번호를 표시한다. 실제 도로 경로선, 실시간 위치, 내비게이션은 후속 범위다. 지도 표시 실패가 저장된 시간표를 지우거나 재계산하게 해서는 안 된다.

## 4. 기능 요구사항

### FR-01 국가 또는 도시 입력

사용자는 다음 정보를 입력할 수 있다.

- Google Places에서 선택한 국가 또는 도시의 Place ID
- 여행 시작일
- 여행 종료일
- 반드시 방문하고 싶은 장소
- 먹고 싶은 음식

여행 취향과 혼잡도는 입력받지 않는다. 도시가 직접 선택되면 도시 추천 단계를 생략하고, 국가가 선택되면 도시 후보 선택 단계를 진행한다.

---

### FR-02 국가 기반 도시 후보 추천

사용자가 국가를 선택하면 서버는 Google Places로 국가를 검증하고 OpenAI API를 이용해 해당 국가의 대표 여행 도시 후보를 생성한다.

예상 결과:

```json
{
  "cities": [
    {
      "name": "도쿄",
      "countryCode": "JP",
      "reason": "교통과 관광 인프라가 잘 갖춰진 대표 여행 도시"
    }
  ]
}
```

AI 응답은 자유 텍스트가 아니라 구조화된 형태로 받는다. AI가 반환한 이름은 장소 식별자가 아니며, 서버가 Google Places로 검증하여 Google Place ID를 붙인 후보만 응답한다.

#### AI 응답 계약

서버는 AI가 반환한 값을 신뢰하지 않고 DTO validation을 수행한다.

| 필드 | 타입 | 규칙 |
|---|---|---|
| `cities` | 배열 | 3~5개, 도시 이름 중복 없음 |
| `cities[].name` | 문자열 | 앞뒤 공백 제거 후 1~100자 |
| `cities[].countryCode` | 문자열 | 선택 국가와 일치하는 ISO 3166-1 alpha-2 코드 |
| `cities[].reason` | 문자열 | 사용자에게 표시할 1~200자 추천 이유 |

AI가 JSON이 아닌 응답을 반환하거나 허용하지 않은 값이 포함되면 서버는 해당 결과를 저장하거나 추천에 사용하지 않고 `AI_RESPONSE_INVALID`로 처리한다.

---

### FR-03 도시 선택과 방문 장소 추천

사용자는 AI가 제안하고 Google Places가 검증한 도시 후보 중 하나를 선택하거나 Google Places 검색을 통해 도시를 직접 선택한다.

도시가 확정되면 서버는 Google Places에서 해당 도시의 관광지 후보를 조회한다. 최종 여행 계획 저장에는 여행 기간, 방문 장소와 호텔 선택이 추가로 필요하다.

추천 시 고려할 수 있는 조건:

- 선택한 도시
- Google Places의 장소 유형과 검색 관련도
- 사용자가 이미 지정한 필수 여행지

초기 MVP에서는 추천 규칙을 단순하게 유지한다.

---

### FR-04 필수 여행지 지정

사용자는 Google Places 검색 결과에서 반드시 방문할 장소를 선택할 수 있다.

필수 장소는 일정 생성 과정에서 임의로 제거하지 않는다.

---

### FR-05 음식 선호 입력

사용자는 여행 중 먹고 싶은 음식을 복수로 입력할 수 있다.

MVP에서는 각 음식 값을 앞뒤 공백을 제거한 문자열로 검증·저장하고, 음식점 검색 조건으로 그대로 사용한다. 동의어 통합, 음식 카테고리 분류, 알레르기·식단 의도 추론 같은 AI 자연어 해석은 현재 A1·R2 범위에 포함하지 않으며 별도 요구사항과 AI 계약을 확정한 뒤 추가한다.

예:

- 돼지국밥
- 회
- 밀면

---

### FR-06 여행 계획 생성

서비스는 다음 데이터를 이용해 여행 계획을 생성한다.

- 여행 기간
- 필수 여행지
- 선택된 추천 여행지
- 사용자가 선택한 추천 호텔
- 위치 정보
- 음식점
- 장소별 예상 체류 시간
- 하루 시작·종료 시각

#### MVP 입력 제약

- 여행 기간은 1일 이상 14일 이하이며, `startDate`는 `endDate`보다 늦을 수 없다.
- 필수 장소와 선택 추천 장소를 합친 방문 장소는 중복 없이 1개 이상이어야 한다.
- 하루 최대 방문 관광 장소 수는 6개다. 숙소의 출발/도착과 음식점 추천 후보는 방문 장소 수에 포함하지 않는다.
- 전체 방문 장소 수는 `여행 일수 × 6`을 초과할 수 없다.
- 필수 장소 ID는 모두 최종 일정에 포함해야 하며, 필수 장소와 선택 추천 장소 간 중복은 허용하지 않는다.
- 선택 호텔의 Google Place ID는 유효해야 하며, Google Places에서 숙박 장소로 확인되고 선택 도시 범위와 일치해야 한다.
- 하루 기본 일정은 목적지 현지 시각 `10:00~21:00`이다. 사용자는 시작·종료 시각을 변경할 수 있으며 시작 시각은 종료 시각보다 빨라야 한다.
- 장소별 체류 시간은 Google 장소 유형에 따른 기본값을 사용하되, 사용자가 선택 장소별로 양의 분 단위 값을 지정해 덮어쓸 수 있다.
- 선택 도시, 필수 장소, 선택 장소, 호텔의 모든 Google Place ID는 저장 전에 Google Places에서 존재·유형·도시 소속을 검증한다.
- 필수 장소와 선택 장소는 모두 관광 장소 유형이어야 하며 선택 도시의 행정구역에 속해야 한다. 호텔은 허용된 숙박 유형이어야 하며 같은 도시 범위에 속해야 한다.
- 도시·호텔·방문 장소는 서로 다른 역할의 ID로 중복 사용할 수 없다.
- 체류 시간 수정 대상은 반드시 필수 장소와 선택 장소를 합친 최종 방문 장소 집합에 포함돼야 한다.

제약을 만족하지 않거나 Google 검증을 완료할 수 없으면 계획을 부분 생성하거나 임의로 장소를 제외하지 않고 요청을 거절한다. 모든 외부 검증과 일정 계산이 성공한 뒤 하나의 DB 트랜잭션으로 전체 계획을 저장한다.

---

### FR-07 장소 간 거리 계산

경로 알고리즘 학습과 단위 테스트에서는 각 장소의 위도·경도를 이용한 직선 거리를 사용할 수 있다. 최종 시간표 생성에서는 Google Routes의 정적 이동 거리와 이동 시간을 사용한다.

외부 API 통신은 `route/client`에 격리하고, `route/algorithm`은 전달받은 거리·시간 행렬만 사용하는 순수 Java 로직으로 유지한다. 실시간 교통은 MVP에 반영하지 않는다.

---

### FR-08 여행 경로 최적화

선택된 여행지의 방문 순서를 결정한다. 호텔이 선택된 일정에서는 호텔에서 출발해 모든 관광 장소를 방문한 뒤 같은 호텔로 돌아오는 경로를 계산한다. 호텔은 방문 장소 목록과 방문 순서에는 포함하지 않는다.

#### 초기 알고리즘

Nearest Neighbor

현재 위치에서 가장 가까운 미방문 장소를 반복해서 선택한다.

#### 개선 알고리즘

2-opt

Nearest Neighbor가 만든 초기 경로의 일부 간선을 교환하여 전체 이동 거리를 개선한다.

---

### FR-09 호텔 추천

여행지 후보와 각 호텔 후보 사이의 이동 비용을 계산하여 이동 효율이 높은 숙소를 추천한다.

서비스는 점수가 낮은 순서로 여러 호텔 후보를 반환한다. 사용자는 추천 후보 중 하나 또는 선택 도시에서 직접 검색한 숙박 장소를 선택하고, Google Place ID를 여행 계획 생성 요청에 전달한다. 서버는 Google Places에서 숙박 장소 유형과 선택 도시 범위를 검증한 뒤 그 호텔을 각 날짜 경로의 시작·종료점으로 사용한다.

초기 점수:

```text
HotelScore =
Σ distance(hotel, selectedPlace)
```

점수가 낮을수록 이동 측면에서 유리한 호텔이다.

향후 고려 가능 요소:

- 가격
- 평점
- 역 / 공항 접근성
- 체크인 / 체크아웃
- 사용자의 숙박 선호

---

### FR-10 음식점 추천

사용자는 저장된 여행 계획 ID·현지 날짜·식사 종류·원하는 음식으로 후보 검색을 요청한다. 서버는 해당 계획의 식사 슬롯·도시·호텔·방문 순서와 시각을 읽어 검색하며 클라이언트가 보낸 별도 시간표를 신뢰하지 않는다. 해당 식사 슬롯이 없으면 검색하지 않고 오류를 반환한다. 후보 검색은 음식 선호와 저장 일정을 변경하지 않는다.

사용자가 먹고 싶은 음식과 여행 동선을 함께 고려하되, 점심·저녁 시간대에 들어갈 수 있는 음식점만 추천한다. 모든 관광 구간에 음식점을 끼워 넣지 않는다.

초기 기준:

- 음식 종류 일치 여부
- 식사 시간대 충족 여부
- 식사 직전 장소와 직후 장소 사이의 동선 이탈 시간·거리

식사 시간대는 목적지 현지 시각 기준 점심 `11:30~14:00`, 저녁 `17:30~20:30`이며 식사에는 기본 60분을 확보한다. 사용자가 바꾼 하루 범위 안에 해당 식사 시간대가 60분 이상 포함될 때만 그 식사 슬롯을 만든다.

관광 장소의 도착~출발 구간이 식사 시간대 전체를 포함하는 경우, 일반 경로 구간 후보 대신 해당 장소를 기준으로 음식점을 찾는다. Google Places의 `containingPlaces` 등 포함 관계로 시설 내부임을 확인할 수 있는 음식점을 먼저 제시하고, 내부 후보가 없으면 해당 장소 중심의 Nearby Search와 이동 시간으로 인접 후보를 제시한다. 포함 관계를 확인할 수 없으면 내부라고 단정하지 않고 인접 후보로 표시한다.

향후 기준:

- 평점
- 리뷰 수
- 영업시간
- 가격대

### FR-11 날짜별 일정 생성

여행 기간과 선택 장소 수를 고려하여 장소를 날짜별로 배치한다.

초기 버전은 장소 수와 체류·이동 시간을 함께 고려해 날짜별로 나누고 경로와 시간표를 계산한다.

#### MVP 배치 규칙

1. 하루 일정은 목적지 현지 시각 `10:00~21:00`을 기본으로 하며 사용자가 시작·종료 시각을 변경할 수 있다.
2. 장소는 일자별로 `최대 6개`까지 배치하되, 개수보다 아래 시간 합산 규칙에 따른 일일 시간 용량을 우선한다. 6개는 안전 상한이다.
3. 장소별 기본 체류 시간은 Google 장소 유형을 서버의 결정적 정책에 매핑해 계산한다. 여러 유형이면 가장 긴 값을 사용하고, 사용자의 장소별 수정값이 있으면 그 값을 최우선한다.

   | Google 장소 유형 예시 | 기본 체류 시간 |
   |---|---:|
   | `observation_deck`, `monument`, `plaza` | 60분 |
   | `beach`, 종교 시설 유형, `tourist_attraction` | 90분 |
   | `museum`, `art_gallery`, `botanical_garden`, `park` | 120분 |
   | `aquarium`, `zoo`, `national_park` | 180분 |
   | `shopping_mall`, `market` | 240분 |
   | `amusement_park`, `water_park`, `ski_resort` | 360분 |
   | 분류되지 않은 장소 | 90분 |

4. 사용자가 날짜 배치를 지정하지 않은 생성·수정 요청에서는 필수 장소를 일반 후보보다 먼저 배치 대상에 포함하며, 일정 생성 후 누락 여부를 검증한다.
   - 배치 후보 순서는 `필수 장소의 요청 목록 순서 → 선택 장소의 요청 목록 순서`로 고정한다. 같은 우선순위를 별도 자료구조에서 비교해야 하면 Google Place ID 오름차순으로 동률을 해소한다.
   - 각 후보를 모든 날짜에 임시 추가하고 호텔 왕복 경로와 체류·이동·식사·식사 이동 여유를 다시 계산한다. 하루 최대 6개와 시간 용량을 만족하는 날짜 중 **추가 후 소요 시간이 가장 짧은 날짜**에 확정하며, 동률이면 앞 날짜를 선택한다.
   - 분산 점수인 `소요 시간`은 관광 체류 + 호텔 왕복 직접 이동 + 체류 밖 식사 60분 + 체류 밖 식사별 이동 여유의 합이다. 긴 체류 안의 식사·외출 이동은 중복 합산하지 않는다. 대기와 자유 시간은 점수에서 제외하되 실제 시간표의 하루 용량 검증에는 포함한다.
   - 어떤 날짜에도 들어가지 않는 후보가 있으면 필수·선택 여부와 관계없이 임의로 제외하거나 다음 후보로 대체하지 않고 `PLAN_CAPACITY_EXCEEDED`로 요청 전체를 거절한다.
   - 전체 배치 후 단일 장소의 날짜 이동을 최대 `전체 방문 장소 수`회 적용한다. 매 회 모든 장소·다른 날짜 조합의 두 날짜 경로·시간표를 재계산해, 유효한 이동 중 전체 날짜의 `최대 소요 시간 - 최소 소요 시간`을 가장 많이 줄이는 이동 하나를 적용한다. 동률은 Google Place ID, 대상 날짜 오름차순이다. 편차가 엄격히 줄지 않으면 종료하며 교환·전역 탐색은 하지 않는다. 배치 실패를 복구하는 탐색이 아니므로 전역 최적 배치나 모든 가능한 일정의 수용을 보장하지 않는다.
   - 여행 기간의 모든 Day를 만들고 관광지가 없는 날은 `places: []`인 자유 일정으로 허용한다. 그날도 식사 슬롯 규칙을 적용하며 음식점 검색의 양쪽 기준은 호텔이다. 관광지가 없는 날짜를 늘리는 보정 이동은 허용하지 않는다. 사용자 지정 날짜에는 자동 분산·보정을 적용하지 않는다.
5. 같은 날짜에 배치된 장소만 대상으로 해당 날짜의 경로를 최적화한다.
6. 호텔은 모든 날짜의 경로 시작 및 종료 기준점으로 사용하지만, 관광 장소 방문 순서에는 포함하지 않는다. 하루의 총 이동 시간은 `호텔 → 첫 관광 장소 → ... → 마지막 관광 장소 → 호텔` 구간의 합이다.
7. Google Routes의 정적 이동 시간을 이용해 도착·출발 시각을 순서대로 계산한다. 실시간 교통은 반영하지 않는다.
8. 점심과 저녁은 각각의 시간대가 사용자 지정 하루 범위 안에 60분 이상 포함될 때만 슬롯을 만들고 60분을 확보한다. 긴 체류 장소가 식사 시간대 전체를 포함하면 시설 내부 후보를 우선하고 없으면 인접 후보를 추천한다.
   - 점심의 우선 시작 시각은 `12:00`, 저녁은 `18:00`이다. 하루 범위와 식사 허용 시간대의 겹침이 60분 미만일 때만 슬롯을 생략한다. 생성 대상 슬롯을 관광·이동과 함께 배치할 수 없으면 슬롯을 없애지 않고 `PLAN_CAPACITY_EXCEEDED`로 거절한다.
   - 시작은 허용 구간 안의 분 단위 값으로 결정한다. 관광 순서는 유지하고 체류를 임의로 분할하지 않는다. 긴 체류 안의 식사를 제외하면 관광·이동과 식사가 겹치지 않아야 하며 일반 식사는 아래 이동 여유까지 확보한다. 유효한 하루 시간표 중 점심·저녁 시작의 우선 시각 대비 절대 편차 합이 가장 작은 것을 선택한다. 동률이면 점심 시작, 저녁 시작, 호텔 복귀 시각, 식사가 들어간 경로 구간 순번 순으로 오름차순 비교하고 없는 슬롯은 제외한다. 식사 전 필요한 대기만 넣고 나머지 이동·체류는 가능한 가장 이른 시각에 진행한다.
9. 확정한 식사 슬롯의 종류·시작·종료 시각은 일정과 함께 저장한다. 음식점 후보는 사용자가 별도로 요청할 때 검색하여 응답하며 자동 확정하거나 Place 참조로 저장하지 않는다. 후보 검색은 저장된 시간표를 변경하지 않는다.
10. 필수 장소와 식사 시간을 포함한 시간표가 하루 범위를 넘으면 장소를 임의로 제외하지 않고 `PLAN_CAPACITY_EXCEEDED`로 거절한다.

#### 체류·식사·이동 시간 합산

- `stayMinutes`는 해당 장소의 도착부터 출발까지 확보한 전체 시간이다. 긴 체류 구간이 식사 허용 시간대 전체를 포함하면 식사 60분을 그 체류 안에 배치하며 추가로 합산하지 않는다.
- 내부 음식점이 없어 인접 음식점으로 나가는 경우에도 장소에서 음식점까지의 이동·식사·장소로 돌아오는 이동을 모두 같은 체류 구간에 포함한다. 실제 관광에 쓸 수 있는 시간은 그만큼 줄어든다. 장소 출발 시각과 이후 일정은 유지한다.
- 예: 놀이공원 `10:00~16:00`(360분), 점심 `12:00~13:00`, 왕복 이동 20분이면 실제 관광 가능 시간은 280분이다. 전체 체류는 여전히 360분이며 식사나 왕복 이동을 일일 용량에 다시 더하지 않는다.
- 장소 P의 도착·출발을 a·d, 고정 식사 시작·종료를 s·e라고 할 때 인접 후보 R은 `s - 이동시간(P,R) >= a`, `e + 이동시간(R,P) <= d`를 모두 만족해야 한다. 왕복은 방향별 시간을 사용하며 편도 값을 두 배로 추정하지 않는다. 동일 체류 중 복수 식사가 있으면 식사·외출 구간이 서로 겹쳐서는 안 된다.
- 일반 장소 사이의 식사는 체류와 별도로 60분과 전후 이동 여유를 확보한다. 계획 입력 `mealTravelBufferMinutes`는 한쪽 여유이며 기본 15분, 정수 0~60분이다. 점심·저녁에 동일한 값을 적용한다. 실제 이동 시간 추정치가 아니라 식당 경유를 위한 추가 여유다.
- 직접 구간 이동을 T분, 한쪽 여유를 b분, A 출발을 a, 식사 시작·종료를 s·e라 하면 `s >= a + ceil(T/2) + b`, `B 도착 >= e + floor(T/2) + b`로 시간표를 생성한다. 직접 이동은 합계 T분만 반영하며 일반 식사 구간의 최소 길이는 `T + 60 + 2b`분이다. T는 Routes의 방향별 이동 시간을 분으로 올림한 값이다. 절반 분배는 시간 예약 규칙이며 음식점 위치나 실제 편도 시간을 뜻하지 않는다. 실제 후보는 아래 방향별 조건으로 다시 검증한다.
- 예: A 출발 11:35, 직접 이동 20분, b=15이면 점심 12:00~13:00, B 도착 13:25로 총 110분을 확보한다. 후보의 실제 A→음식점 20분·음식점→B 25분은 허용되지만 어느 한쪽이 26분이면 제외한다.
- 같은 A→B 구간에 두 식사가 들어가면 직접 이동 T는 한 번만 합산한다. 첫 식사 앞에 ceil(T/2), 마지막 식사 뒤에 floor(T/2)를 두고 각 식사의 전후 b를 확보하며 남는 시간은 대기로 둔다. 첫·마지막 구간은 호텔과 하루 경계를 사용한다. 자유 일정은 호텔→호텔 직접 이동 0분으로 같은 규칙을 적용한다.
- 하루 시간표는 체류·직접 이동·체류 밖 식사·추가 여유·필요한 대기를 포함한다. 긴 체류 안에는 추가 `2b`를 더하거나 출발을 늦추지 않으며 기존 체류 안의 실제 왕복 가능 여부로 후보를 검증한다.
- 일반 구간 후보 R은 직전 장소 A 출발 후 고정 식사 시작 s까지 도착하고, 식사 종료 e 이후 다음 장소 B의 저장된 도착 시각까지 갈 수 있어야 한다. 즉 `A 출발 + 이동시간(A,R) <= s`, `e + 이동시간(R,B) <= B 도착`을 검증한다. 하루 첫·마지막 구간에서는 호텔과 하루 시작·종료 시각을 경계로 사용한다.
- 음식점 후보는 일정 저장 후 검색하므로 특정 후보의 이탈 시간을 미리 일정에 더하지 않는다. 검색에서는 직접 구간 대신 후보를 경유하는 실제 구간 시간으로 가능 여부를 검증하고, 증가분은 순위 계산에 사용한다. 저장된 여유 시간 안에 맞지 않는 후보는 제외한다.
- 시간 조건을 만족하는 내부 후보를 우선하고, 없으면 같은 조건을 만족하는 인접 후보를 사용한다. 모두 없으면 빈 후보 목록을 반환한다. 슬롯 이동·체류 연장·후속 일정 재배치로 후보를 끼워 넣지 않는다.
- 이동 여유가 있어도 후보 존재는 보장하지 않는다. 정상 빈 결과는 검색한 범위에서 음식·장소 조건에 맞는 후보가 없었는지, 맞는 후보가 모두 시간 조건에서 제외됐는지 구분한다. provider 장애는 빈 결과로 바꾸지 않는다. 같은 체류·경로 구간의 다른 저장 식사 슬롯과 예약 구간을 침범하는 후보는 제외하며, 별도로 반환된 후보 조합의 동시 방문 가능성까지 보장하지 않는다.
- 복수 슬롯의 검색에서는 해당 식당 방문 구간 `[s - 이동시간(A,R), e + 이동시간(R,B)]`이 다른 일반 식사의 `[시작-b, 종료+b]`와 겹치면 제외한다. 긴 체류에서는 A=B=기준 장소이며 다른 내부 식사의 `[시작, 종료]`와 비교한다. 경계가 맞닿는 것은 허용한다. 전달 DTO에는 그날의 다른 슬롯과 저장된 여유값도 포함한다.
- 사용자는 음식을 바꿔 다시 검색하거나 PUT으로 `mealTravelBufferMinutes`를 늘려 명시적으로 재계산할 수 있다. 검색 요청은 여유나 일정을 변경하지 않는다. 재계산 실패 시 기존 입력값·시간표·슬롯을 모두 유지한다. 긴 체류 내부 식사는 여유값 증가로 체류가 늘지 않으므로 필요하면 체류 시간 또는 날짜 배정을 직접 수정한다.

#### 향후 고려 사항

- 영업시간
- 장소 중요도
- 휴식 시간

### FR-12 여행 계획 CRUD

사용자는 생성된 여행 계획을 조회, 수정, 삭제할 수 있어야 한다.

상세 조회는 저장된 방문 순서·도착·출발 시각·식사 슬롯을 그대로 반환하고, 장소명·주소 등 표시 정보만 Google Places에서 조회한다. 조회 중 경로나 시간표를 다시 계산하지 않는다. 도시·여행 날짜·방문 장소·호텔·하루 시간·체류 시간 조건을 수정하면 시간표와 식사 슬롯을 재계산한 뒤 함께 교체한다. 재계산 또는 저장 실패 시 기존 계획을 유지한다. 음식 목록만 변경하면 저장된 시간표는 유지하고 이후 음식점 검색에 변경된 선호를 사용한다.

수정 요청에서 사용자는 최종 방문 장소 각각을 여행 기간 안의 날짜에 직접 배정할 수 있다. 날짜 배정을 전달하면 모든 최종 방문 장소가 정확히 한 번 포함돼야 하며, 서버는 사용자가 지정한 날짜를 유지한 채 날짜별 방문 순서·도착과 출발 시각·식사 슬롯을 다시 계산한다. 날짜별 최대 6개 또는 시간 용량을 만족하지 못하면 일부 장소를 다른 날짜로 자동 이동하지 않고 수정 요청을 거절하며 기존 계획을 유지한다. 날짜 배정을 생략한 상태에서 일정 조건이 바뀌면 FR-11의 자동 배치 정책을 적용한다. 음식 목록만 바뀌면 기존 날짜 배치와 시간표를 유지한다.

## 6. 비기능 요구사항

### NFR-01 보안

- OpenAI API Key를 소스 코드에 작성하지 않는다.
- `.env` 또는 환경변수를 이용한다.
- `.env`는 Git에 커밋하지 않는다.
- 비밀번호를 저장하게 될 경우 평문으로 저장하지 않는다.
- AI 설정은 `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_TIMEOUT_MS`, `OPENAI_MAX_RETRIES` 환경변수로 분리한다. 기본값은 코드에 숨기지 않고 설정 문서에 명시한다.

### NFR-01-AI 안정성

- AI 요청은 최대 10초 안에 완료되어야 하며, 네트워크 오류 또는 5xx 응답에 한해 최대 1회 재시도한다.
- 인증 오류, 요청 형식 오류, JSON 파싱 오류는 재시도하지 않는다.
- 제공자 장애·timeout은 `AI_UNAVAILABLE`, 구조화 응답 검증 실패는 `AI_RESPONSE_INVALID`로 구분한다.
- API 키, AI 요청 원문, 제공자 원본 응답은 DB, 오류 응답, 일반 로그에 기록하지 않는다. 검증된 Google Place ID와 Routy가 생성한 일정 데이터만 영구 저장한다.
- 테스트와 로컬 개발에서 외부 호출이 필요하지 않은 경우 fake `AiClient`를 사용한다.

### NFR-02 유지보수성

- Controller는 HTTP 요청 / 응답 처리에 집중한다.
- Service는 비즈니스 로직을 담당한다.
- Repository는 데이터 접근을 담당한다.
- Entity와 API DTO를 구분한다.
- 도메인별 패키지 구조를 사용한다.

### NFR-03 테스트

테스트의 상세 책임, fixture 규칙, 기능별 완료 기준은 `docs/08-test-strategy.md`를 따른다.

최소한 다음에는 자동 테스트를 작성한다.

- 거리 계산과 경로 최적화 알고리즘
- 호텔·음식점 추천 점수와 정렬
- 핵심 Service 비즈니스 로직과 예외 처리
- Place·TravelPlan API의 validation 및 오류 응답
- AI 응답 계약 검증과 제공자 장애 변환
- DB 제약조건 및 migration 적용

### NFR-04 관찰 가능성

환경별 로그·헬스체크·외부 API 운영 기준은 `docs/09-operations.md`를 따른다.

- 개발 단계에서는 SQL 로그와 애플리케이션 로그를 이용해 요청 및 DB 동작을 확인한다.
- 운영 환경에서는 API 키, 비밀번호, access token, 사용자 자연어 원문, 외부 제공자 원문 응답을 로그에 출력하지 않는다.
- 애플리케이션과 DB의 정상 상태를 분리해 확인한다. AI·지도 API 장애는 서비스의 핵심 상태와 분리해 관찰한다.

# 프로젝트 요구사항 명세서

## 1. 프로젝트 개요

### 프로젝트명

**Routy - AI 여행 일정 관리 & 최적화 서비스**

### 목적

사용자가 여행 지역, 여행 취향, 반드시 방문하고 싶은 장소, 먹고 싶은 음식 등의 조건을 입력하면 해당 조건에 적합한 여행지를 추천하고, 선택된 장소들의 위치를 기반으로 이동 동선을 최적화하여 여행 일정을 생성한다.

또한 선택된 관광지들을 방문하기 유리한 위치의 호텔과 각 날짜의 여행 동선 근처에서 사용자가 원하는 음식을 먹을 수 있는 음식점을 추천한다.

---

이 프로젝트에서 AI와 Spring Backend의 책임을 명확히 분리한다.

- 사용자에게 보여줄 추천 이유나 일정 설명 생성

### Spring Backend가 담당하는 영역

- 사용자 및 여행 데이터 저장
- 장소 데이터 관리
- 여행 계획 생성 및 저장
- 장소 간 거리 계산
- 호텔 후보 평가
- 음식점 후보 평가
- 여행 경로 최적화
- 비즈니스 규칙 적용
- Validation / Exception Handling
- 인증 / 인가
- 테스트

### 금지 원칙

다음 기능을 LLM의 답변만으로 결정하지 않는다.

- 최단 이동 거리 계산
- 경로 최적화
- 호텔의 이동 효율 점수 계산
- 음식점의 동선 이탈 거리 계산

## 3. 사용자 시나리오

### 시나리오 A - 선호 조건 기반 여행지 추천

사용자가 다음과 같이 입력한다.

> 서울에서 사람이 너무 많은 곳은 피하고 싶고, 역사적인 장소와 사진 찍기 좋은 곳을 좋아해.

서비스는 자연어를 분석하여 구조화된 선호 조건을 만든다.

예:

```json
{
  "region": "서울",
  "interests": ["HISTORY", "PHOTOGRAPHY"],
  "crowdPreference": "LOW"
}
```

이 조건을 기반으로 여행지 후보를 추천한다.

---

### 시나리오 B - 방문 장소와 음식 기반 추천

사용자가 다음 정보를 입력한다.

- 지역: 부산
- 반드시 방문할 장소: 해운대, 감천문화마을
- 먹고 싶은 음식: 돼지국밥, 회

서비스는 필수 장소를 포함하면서 추가 여행지 후보와 음식점 후보를 추천한다.

---

### 시나리오 C - 여행 계획 생성

사용자가 추천 여행지 중 방문할 장소를 선택하면 시스템은 다음 과정을 수행한다.

1. 선택 장소의 위치 정보 확보
2. 장소 간 거리 계산
3. 호텔 후보 평가
4. 날짜별 방문 장소 분배
5. 날짜별 이동 경로 최적화
6. 동선 근처 음식점 추천
7. 최종 여행 일정 생성
8. 여행 계획 DB 저장

## 4. 기능 요구사항

### FR-01 여행 조건 입력

사용자는 다음 정보를 입력할 수 있다.

- 여행 지역
- 여행 시작일
- 여행 종료일
- 여행 선호 조건
- 혼잡도 선호
- 반드시 방문하고 싶은 장소
- 먹고 싶은 음식

---

### FR-02 자연어 여행 선호 분석

사용자가 자연어로 작성한 선호 조건을 OpenAI API를 이용하여 구조화한다.

예상 결과:

```json
{
  "destination": "도쿄",
  "interests": ["NATURE", "PHOTOGRAPHY"],
  "crowdPreference": "LOW"
}
```

AI 응답은 가능한 한 자유 텍스트가 아니라 구조화된 형태로 변환한다.

#### AI 응답 계약

서버는 AI가 반환한 값을 신뢰하지 않고 DTO validation을 수행한다.

| 필드 | 타입 | 규칙 |
|---|---|---|
| `destination` | 문자열 또는 null | 요청에서 목적지를 판단할 수 있으면 앞뒤 공백 제거 후 1~100자, 판단할 수 없으면 `null` |
| `interests` | 배열 | 0~7개, 중복 없음. 허용값만 포함 |
| `crowdPreference` | 문자열 | 허용값 중 하나. 선호가 불분명하면 `ANY` |

`interests` 허용값:

```text
NATURE
HISTORY
PHOTOGRAPHY
SHOPPING
ACTIVITY
RELAX
FOOD
```

`crowdPreference` 허용값:

```text
LOW
MEDIUM
HIGH
ANY
```

AI가 JSON이 아닌 응답을 반환하거나 허용하지 않은 값이 포함되면 서버는 해당 결과를 저장하거나 추천에 사용하지 않고 `AI_RESPONSE_INVALID`로 처리한다.

---

### FR-03 사용자 선호 기반 여행지 추천

구조화된 사용자 선호와 목적지를 이용해 여행지 후보를 추천한다. 예를 들어 사용자가 "도쿄에 가고 싶어"라고만 입력하면 AI는 `destination: "도쿄"`를 반환하고, 클라이언트는 이를 지역으로 사용해 도쿄의 장소 후보를 조회한다.

목적지만 입력한 요청도 선호 분석과 장소 후보 추천은 수행할 수 있다. 단, 최종 여행 계획 저장에는 여행 기간과 방문 장소 선택이 추가로 필요하다.

추천 시 고려할 수 있는 조건:

- 지역
- 여행 스타일
- 장소 카테고리
- 혼잡도 선호
- 사용자가 이미 지정한 필수 여행지

초기 MVP에서는 추천 규칙을 단순하게 유지한다.

---

### FR-04 필수 여행지 지정

사용자는 반드시 방문할 장소를 입력하거나 선택할 수 있다.

필수 장소는 일정 생성 과정에서 임의로 제거하지 않는다.

---

### FR-05 음식 선호 입력

사용자는 여행 중 먹고 싶은 음식을 복수로 입력할 수 있다.

예:

- 돼지국밥
- 회
- 밀면

---

### FR-06 여행 계획 생성

서비스는 다음 데이터를 이용해 여행 계획을 생성한다.

- 여행 기간
- 필수 여행지
- 선택된 추천 여행지
- 사용자가 선택한 추천 호텔
- 위치 정보
- 음식점
- 장소별 예상 체류 시간
- 향후 운영 시간 정보

#### MVP 입력 제약

- 여행 기간은 1일 이상 14일 이하이며, `startDate`는 `endDate`보다 늦을 수 없다.
- 필수 장소와 선택 추천 장소를 합친 방문 장소는 중복 없이 1개 이상이어야 한다.
- 하루 최대 방문 관광 장소 수는 6개다. 숙소의 출발/도착과 음식점 추천 후보는 방문 장소 수에 포함하지 않는다.
- 전체 방문 장소 수는 `여행 일수 × 6`을 초과할 수 없다.
- 필수 장소 ID는 모두 최종 일정에 포함해야 하며, 필수 장소와 선택 추천 장소 간 중복은 허용하지 않는다.
- 선택 호텔 ID는 존재해야 하며, 여행 지역과 일치하는 `HOTEL` 타입이어야 한다.

제약을 만족하지 않으면 계획을 부분 생성하거나 임의로 장소를 제외하지 않고 요청을 거절한다.

---

### FR-07 장소 간 거리 계산

각 장소의 위도 / 경도를 이용하여 장소 사이의 거리를 계산할 수 있어야 한다.

초기 구현은 직선 거리 계산으로 시작할 수 있다.

향후 지도 API를 도입하면 실제 도로 이동 거리 또는 이동 시간으로 교체할 수 있다.

---

### FR-08 여행 경로 최적화

선택된 여행지의 방문 순서를 결정한다. 호텔이 선택된 일정에서는 호텔에서 출발해 모든 관광 장소를 방문한 뒤 같은 호텔로 돌아오는 경로를 계산한다. 호텔은 방문 장소 목록과 방문 순서에는 포함하지 않는다.

#### 초기 알고리즘

Nearest Neighbor

현재 위치에서 가장 가까운 미방문 장소를 반복해서 선택한다.

#### 개선 알고리즘

2-opt

Nearest Neighbor가 만든 초기 경로의 일부 간선을 교환하여 전체 이동 거리를 개선한다.

---

### FR-09 호텔 추천

여행지 후보와 각 호텔 후보 사이의 이동 비용을 계산하여 이동 효율이 높은 숙소를 추천한다.

서비스는 점수가 낮은 순서로 여러 호텔 후보를 반환한다. 사용자는 추천 후보 중 하나 또는 같은 여행 지역의 임의 `HOTEL` 장소를 선택하고, 선택한 호텔 ID를 여행 계획 생성 요청에 전달한다. 서버는 선택한 장소가 해당 여행 지역의 `HOTEL`인지 검증한 뒤 그 호텔을 각 날짜 경로의 시작·종료점으로 사용한다.

초기 점수:

```text
HotelScore =
Σ distance(hotel, selectedPlace)
```

점수가 낮을수록 이동 측면에서 유리한 호텔이다.

향후 고려 가능 요소:

- 가격
- 평점
- 역 / 공항 접근성
- 체크인 / 체크아웃
- 사용자의 숙박 선호

---

### FR-10 음식점 추천

사용자가 먹고 싶은 음식과 여행 동선을 함께 고려하여 음식점을 추천한다.

초기 기준:

- 음식 종류 일치 여부
- 여행 경로로부터의 이탈 거리

향후 기준:

- 평점
- 리뷰 수
- 영업시간
- 가격대

---

### FR-11 날짜별 일정 생성

여행 기간과 선택 장소 수를 고려하여 장소를 날짜별로 배치한다.

초기 버전은 장소 수를 비교적 균등하게 나누고 날짜별 경로를 최적화한다.

#### MVP 배치 규칙

1. 장소를 일자별로 `최대 6개`까지 균등 배분한다. 앞선 날짜부터 한 곳씩 더 배정하여 각 날짜의 장소 수 차이는 최대 1개가 되게 한다.
2. 필수 장소는 일반 후보보다 먼저 배치 대상에 포함하며, 일정 생성 후 누락 여부를 검증한다.
3. 같은 날짜에 배치된 장소만 대상으로 해당 날짜의 경로를 최적화한다.
4. 호텔은 모든 날짜의 경로 시작 및 종료 기준점으로 사용하지만, 관광 장소 방문 순서에는 포함하지 않는다. 하루의 총 이동 거리는 `호텔 → 첫 관광 장소 → ... → 마지막 관광 장소 → 호텔` 구간의 합이다.
5. 음식점은 사용자가 요청한 음식과 동선 이탈 거리를 기준으로 추천한다. MVP에서는 일정에 자동 확정하지 않고 추천 후보로 응답한다.
6. 영업시간, 실시간 교통, 실제 도로 이동 시간, 체류 시간 기반 시간표는 MVP 최적화 제약에 포함하지 않는다.

향후에는 다음을 고려한다.

- 영업시간
- 체류시간
- 식사시간
- 장소 중요도
- 휴식 시간

---

## 6. 비기능 요구사항

### NFR-01 보안

- OpenAI API Key를 소스 코드에 작성하지 않는다.
- `.env` 또는 환경변수를 이용한다.
- `.env`는 Git에 커밋하지 않는다.
- 비밀번호를 저장하게 될 경우 평문으로 저장하지 않는다.
- AI 설정은 `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_TIMEOUT_MS`, `OPENAI_MAX_RETRIES` 환경변수로 분리한다. 기본값은 코드에 숨기지 않고 설정 문서에 명시한다.

### NFR-01-AI 안정성

- AI 요청은 최대 10초 안에 완료되어야 하며, 네트워크 오류 또는 5xx 응답에 한해 최대 1회 재시도한다.
- 인증 오류, 요청 형식 오류, JSON 파싱 오류는 재시도하지 않는다.
- 제공자 장애·timeout은 `AI_UNAVAILABLE`, 구조화 응답 검증 실패는 `AI_RESPONSE_INVALID`로 구분한다.
- API 키, 사용자 원문, 제공자 원본 응답은 DB, 오류 응답, 일반 로그에 기록하지 않는다. 자연어 원문은 요청 처리 중에만 사용하고 구조화된 선호 결과만 저장한다.
- 테스트와 로컬 개발에서 외부 호출이 필요하지 않은 경우 fake `AiClient`를 사용한다.

### NFR-02 유지보수성

- Controller는 HTTP 요청 / 응답 처리에 집중한다.
- Service는 비즈니스 로직을 담당한다.
- Repository는 데이터 접근을 담당한다.
- Entity와 API DTO를 구분한다.
- 도메인별 패키지 구조를 사용한다.

### NFR-03 테스트

테스트의 상세 책임, fixture 규칙, 기능별 완료 기준은 `docs/08-test-strategy.md`를 따른다.

최소한 다음에는 자동 테스트를 작성한다.

- 거리 계산과 경로 최적화 알고리즘
- 호텔·음식점 추천 점수와 정렬
- 핵심 Service 비즈니스 로직과 예외 처리
- Place·TravelPlan API의 validation 및 오류 응답
- AI 응답 계약 검증과 제공자 장애 변환
- DB 제약조건 및 migration 적용

### NFR-04 관찰 가능성

환경별 로그·헬스체크·외부 API 운영 기준은 `docs/09-operations.md`를 따른다.

- 개발 단계에서는 SQL 로그와 애플리케이션 로그를 이용해 요청 및 DB 동작을 확인한다.
- 운영 환경에서는 API 키, 비밀번호, access token, 사용자 자연어 원문, 외부 제공자 원문 응답을 로그에 출력하지 않는다.
- 애플리케이션과 DB의 정상 상태를 분리해 확인한다. AI·지도 API 장애는 서비스의 핵심 상태와 분리해 관찰한다.

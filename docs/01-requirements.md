# 프로젝트 요구사항 명세서

## 1. 프로젝트 개요

### 프로젝트명

**Routy - 국내 여행 일정 추천 및 경로 최적화 서비스**

### 목적

Routy는 사용자가 국내 여행 지역과 방문 장소를 선택하면 위치를 바탕으로 방문 순서를 계산하고, 자동차 또는 대중교통의 실제 경로를 최종 확인하여 날짜별 여행 시간표를 만드는 Spring Boot 백엔드 서비스다.

사용자는 지역을 직접 검색하거나 자연어로 원하는 여행 분위기를 입력해 AI 지역 후보를 받을 수 있다. AI는 서버가 제공한 국내 지역 목록 안에서만 후보와 추천 이유를 만들며, 장소 검증·거리·경로·시간표·호텔·음식점 판단은 Spring Backend가 담당한다.

이 프로젝트는 기능 구현과 함께 Controller, Service, Repository, DTO, 외부 Client, 순수 알고리즘의 책임을 학습하는 것을 목표로 한다.

---

## 2. 핵심 원칙

### AI의 책임

- 서버가 제공한 국내 지역 후보 중 사용자 요청에 어울리는 지역 3개와 추천 이유 생성
- 음식 자연어에서 음식 종류와 식당 검색어 추출

### Spring Backend의 책임

- 국내 지역 기준 데이터와 입력 검증
- 카카오 장소 검색과 외부 데이터 수명 통제
- 사용자와 여행 일정 데이터 저장
- Haversine 직선거리와 방문 순서 계산
- 자동차·대중교통 실제 경로 검증
- 날짜별 시간 예산과 시간표 계산
- 숙소 지도 탐색 중심 계산과 음식점 후보 평가
- 호출 한도와 중복 요청 통제
- 인증·인가와 일정 소유권 검증

### 금지 원칙

- AI가 허용된 국내 지역 목록 밖의 지역, 거리, 경로, 시간표 또는 추천 점수를 결정하지 않는다.
- Controller에 비즈니스 로직을 작성하지 않는다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- API 키, 개인정보, 외부 요청·응답 원문을 코드·Git·로그·fixture·오류 응답에 남기지 않는다.
- 카카오 장소·경로 응답을 자체 장소 DB나 캐시로 구축하지 않는다.

## 3. 서비스 범위

### 국내 지역

- 국내 여행만 지원한다.
- 서울특별시·광역시·도는 실제 여행 지역을 찾기 위한 상위 항목이다.
- 사용자는 상위 항목 아래의 시·군·구 중 최종 여행 지역 하나만 선택한다.
- 세종특별자치시처럼 별도의 하위 시·군·구가 없는 지역은 자체를 최종 지역으로 선택할 수 있다.
- 읍·면·동은 지역 선택 단위로 지원하지 않는다.
- 직접 검색과 AI 추천은 동일한 정적 지역 기준 데이터를 사용한다.
- 지역 기준 데이터는 src/main/resources/data/regions.json으로 관리하고 서버 시작 시 메모리에 읽는다.
- 대표 좌표는 카카오 응답이 아닌 출처가 명확한 공공 행정구역 자료를 사용한다.
- 완성 일정에는 내부 regionId와 일정 생성 당시의 표준 지역 표시 이름을 저장한다.

### 이동수단

- 일정마다 자동차 또는 대중교통 중 하나를 선택한다.
- 한 일정 안에서 두 이동수단을 혼합하지 않는다.
- 자동차 경로는 카카오모빌리티 자동차 길찾기 API를 사용한다.
- 대중교통 경로는 카카오맵 대중교통 경로 API를 사용한다.
- 완료 후 이동수단을 변경하려면 기존 일정을 보존하고 새 일정을 만든다.

## 4. 사용자 흐름

### 4.1 인증

1. 사용자는 이메일과 비밀번호로 회원가입하고 로그인한다.
2. AI 추천, 지역·장소 검색, 일정 제작·저장, 내 일정 조회·편집·삭제에는 로그인이 필요하다.
3. 비회원은 서비스 소개, 예시 화면, 공유 일정만 조회할 수 있다.

### 4.2 지역 선택

사용자는 직접 검색하거나 AI 추천으로 지역을 선택한다.

직접 검색은 정적 지역 기준 데이터의 공식 이름·짧은 이름·별칭을 사용한다. 서울특별시·광역시·도를 고르면 그 아래에서 선택 가능한 시·군·구를 보여준다. 이름이 중복되면 상위 지역을 함께 표시하며 최종 여행 지역은 하나만 선택한다.

AI 추천에서는 사용자가 여행 분위기를 자연어로 입력한다. AI는 서버가 제공한 후보 목록 안에서 지역 3개와 추천 이유를 구조화된 JSON으로 반환한다. 서버는 regionId를 검증하고 사용자는 한 후보를 선택한다.

### 4.3 여행 조건

사용자는 여행 날짜, 날짜별 활동 시작·종료 시각, 이동수단, 한쪽 식사 이동 여유와 먹고 싶은 음식 자연어를 입력한다.

여행 기간은 1일 이상 7일 이하이며 시작일은 종료일보다 늦을 수 없다. 첫날 도착 시각과 마지막 날 출발 시각을 해당 날짜 활동 범위에 반영한다.

### 4.4 관광지 선택

1. 선택 지역의 공공데이터 대표 좌표를 기준으로 최대 20km 안의 카카오 장소를 검색한다.
2. 반경 결과가 부족하거나 사용자가 지역 전체 검색을 요청하면 `선택 지역 공식 이름 + 검색어`로 다시 검색한다.
3. 대표 좌표에서 20km 이내이거나 카카오 주소의 행정구역이 선택 지역과 일치하는 결과만 사용한다.
4. 실제 검색 결과를 약 10~15개 제시하되 부족한 결과를 만들어 채우지 않는다.
5. 사용자는 목록과 제작 중 지도에서 장소를 선택한다.
6. 선택 직후 일정에 표시할 이름을 빈 입력창에 직접 작성한다.
7. 추천 체류시간을 확인하고 10분 단위로 조정한다.
8. 카카오맵 외부 링크로 장소 상세를 확인할 수 있다.

하루 관광지는 최대 5개다. 숙소와 음식점은 이 개수에 포함하지 않는다. 사용자가 최종 선택한 모든 관광지를 서버가 임의로 삭제하거나 대체하지 않는다.

### 4.5 숙소

- 당일치기에는 숙소가 없다.
- 1박 이상 일정에는 숙소 하나를 선택한다.
- 선택 관광지 좌표의 기하 중앙값을 기본 검색 중심으로 사용한다.
- 기본 5km 반경의 숙소를 지도와 목록에 표시하고 사용자가 원하면 10km로 넓힌다.
- 사용자가 `중심 관광지 주변에서 보기`를 선택하면 관광지 메도이드를 계산해 그 실제 관광지 주변을 다시 검색한다.
- 사용자가 지도를 이동하면 현재 지도 영역에서 다시 검색할 수 있다.
- 숙소에 거리 점수나 자동 추천 순위를 부여하지 않고 관광지·숙소 마커와 목록을 연동해 사용자가 직접 선택한다.
- 가격·평점·예약 가능 여부는 보장하지 않으며 사용자가 카카오 링크에서 확인한다.
- 첫날은 첫 관광지에서 시작해 숙소에서 끝나고, 중간 날은 숙소 왕복, 마지막 날은 숙소에서 시작해 마지막 관광지에서 끝난다.

### 4.6 식사와 음식점

- 사용자는 음식과 지역·관광지 맥락을 자연어로 입력하고 AI에게 최대 5개의 구체적인 메뉴명·카카오 검색어·추천 이유·대상 관광지를 제안받는다. 직접 메뉴를 입력하거나 AI 결과를 수정·삭제·재요청할 수 있으며 사용자가 확정한 메뉴만 사용한다.
- AI는 메뉴 후보만 만들며 식당 선택, 품질 평가, 동선 순위, 식사 시각과 이동시간을 결정하지 않는다.
- 점심은 11:30~14:00 안에서 12:00 시작을, 저녁은 17:30~20:30 안에서 18:00 시작을 우선하며 식사시간은 60분이다. 하루 활동 범위와 허용 시간대가 60분 이상 겹칠 때 슬롯을 만든다.
- 일반 식사에는 한쪽 기본 15분, 총 30분의 이동 여유를 확보한다. `mealTravelBufferMinutes`는 한쪽 기준 정수 0~60분이며 점심·저녁에 공통 적용한다.
- 긴 체류 장소 안에 식사를 배치하면 식사 60분과 음식점 왕복을 기존 체류 안에 포함하고 일일 용량에 중복 합산하지 않는다.
- estimate 뒤 최종 저장 전에 식사 슬롯과 직전·직후 장소를 기준으로 카카오 음식점을 1km, 3km, 최대 5km 순서로 검색한다. Haversine 이탈이 작은 순으로 목록과 지도에 함께 표시하고 사용자가 직접 선택하거나 미정으로 둔다.
- 지도에는 직전·직후 장소, 기준 관광지와 음식점 후보를 표시하며 목록·마커 선택을 연동하고 `현재 지도에서 다시 검색`을 제공한다.
- 선택한 음식점만 완료 생성의 실제 경로에 포함한다. 후보가 없으면 다른 메뉴나 식당을 자동 확정하지 않으며 영업시간·휴무·예약 가능 여부를 보장하지 않는다.

## 5. 기능 요구사항

### FR-01 지역 기준 데이터

각 지역은 regionId, 공식 이름, 짧은 이름, 별칭, 상위 지역, 지역 유형, 최종 선택 가능 여부, 대표 좌표, 출처와 기준일을 가진다. 서울특별시·광역시·도는 상위 탐색 항목으로 사용하고 그 아래 시·군·구 중 하나를 최종 선택한다. 사용자 입력 원문 대신 선택된 표준 regionId를 사용하며 존재하지 않는 지역, 선택 불가능한 상위 항목과 해외 지역은 최종 일정 입력에서 거부한다.

### FR-02 AI 지역 추천

AI 응답은 정확히 3개의 중복 없는 regionId와 각 1~200자의 추천 이유를 포함한다. 모든 regionId는 서버가 제공한 후보 목록에 있어야 한다. 잘못된 JSON이나 허용 목록 밖의 값은 저장하거나 추천에 사용하지 않는다.

### FR-03 장소 검색

- 관광지·숙소·음식점은 카카오맵 API로 검색한다.
- 목록과 제작 중 지도 선택은 동기화한다.
- 장소마다 카카오맵 외부 상세 링크를 제공한다.
- 실제 결과만 반환하며 AI로 장소를 생성하지 않는다.
- 관광지 후보는 대표 좌표 20km 이내 또는 주소 행정구역 일치 조건을 만족해야 한다.
- 영업시간·휴무·예약 가능성을 서버가 보장하지 않는다.

### FR-04 사용자 작성 표시 이름

- 장소 선택 직후 일정 후보에 추가하기 전에 직접 입력한다.
- 카카오 장소명을 입력값이나 placeholder로 자동 삽입하지 않는다.
- 앞뒤 공백 제거 후 1~50자이며 공백만 있는 값과 길이 초과 값을 거부한다.
- 동일 이름은 허용하고 별도 금칙어 필터는 두지 않는다.
- 출력 시 HTML 이스케이프 등 기본 보안 처리를 적용한다.

### FR-05 체류시간

- 카카오 카테고리는 제작 중 기본 체류시간 계산에만 사용한다.
- 체류 유형은 노출하거나 사용자가 변경하게 하지 않는다.
- 추천 체류시간만 표시하며 사용자는 10분 단위로 조정한다.
- 관광지는 최소 30분, 최대 8시간이다.
- 일반·자연 관광지 90분, 박물관·전시 120분, 체험 180분, 등산 240분, 테마파크 360분을 기본으로 한다.
- 분류가 불명확한 관광지는 90분이다.
- 식당은 60분이며 숙소는 관광지 체류시간 대상이 아니다.
- 최종 일정에는 stayMinutes만 저장하고 카카오 카테고리와 내부 체류 유형은 저장하지 않는다.

### FR-06 초기 거리와 방문 순서

- Haversine 직선거리로 초기 비용을 계산한다.
- Nearest Neighbor 후 2-opt로 방문 순서를 개선한다.
- 실제 경로 API로 모든 순열을 평가하지 않는다.
- 장소 검색이나 단순 선택 시 실제 경로 API를 호출하지 않는다.
- route/algorithm은 Spring, Repository, HTTP Client, AI Client에 의존하지 않는 순수 Java로 유지한다.
- 이동수단별 초기 시간 추정 계수는 구현 전 ADR에서 고정하고 운영 설정으로 조정 가능하게 한다.

### FR-07 실제 경로 검증

- 거의 완성된 후보 하나가 정해진 뒤 인접 구간만 조회한다.
- 자동차는 카카오모빌리티, 대중교통은 카카오맵 경로 API를 사용한다.
- 응답 소요시간은 ceil(응답 초 / 600) × 10분으로 올린다.
- 37분은 40분, 45분은 50분으로 반영한다.
- 10분 단위 올림 외에 고정 이동 여유시간을 더하지 않는다.
- 원본 시간·경로 원문·경로 좌표는 저장하지 않고 10분 단위 예상 이동시간만 저장한다.
- 외부 경로 API 결과인지 Haversine fallback인지 나타내는 출처·상태는 일정 DB에 저장하지 않는다. 완료·공유 조회에서는 모든 이동시간을 동일하게 예상 이동시간으로 표시한다.
- 장소·식사·순서 변경 시 영향 구간만, 이동수단 변경 시 전체 구간을 다시 조회한다.

### FR-08 경로 실패

- timeout과 5xx는 1회 재시도하며 재시도도 호출량에 포함한다.
- 기술 실패가 계속되거나 무료 한도에 도달하면 좌표 기반 추정시간을 10분 단위로 올려 사용할 수 있다.
- 완료 생성 전에 필요한 제공자 요청 수를 계산하고 사용자·서비스 잔여 한도를 원자적으로 확보한다. 잔여 한도가 부족하면 외부 경로 API를 호출하지 않고 일정 전체 구간을 좌표 기반 추정시간으로 계산한다.
- 정상 응답의 경로 없음이나 잘못된 좌표·요청은 추정값으로 대체하지 않고 최종 확정을 차단한다.
- 추정값 사용 사실은 완료 생성 응답의 warning으로만 알리되 제공자 오류 원문은 노출하지 않는다. warning은 완료 일정에 영속 저장하지 않는다.

### FR-09 시간 예산

하루 사용시간은 관광지 체류시간, 식사시간, 10분 단위 예상 이동시간의 합이다.

- 사용자 종료 시각을 넘으면 허용 오차 없이 최종 확정을 차단한다.
- 서버는 장소를 자동 삭제하거나 체류시간을 임의로 줄이지 않는다.
- 사용자가 종료 시각, 체류시간, 장소, 식사, 순서를 직접 조정한다.
- 최초 estimate는 날짜와 순서를 자동 추천하고, 이후 모든 장소에 날짜·순서가 지정된 요청은 사용자 배치를 보존한다.
- 최종 생성은 사용자가 확정한 날짜·순서를 검증하되 서버가 임의로 재정렬하지 않는다.
- 종료 시각·체류시간 변경은 경로를 재호출하지 않는다.
- 장소·식사·순서 변경은 영향 구간만 재호출한다.
- 시간이 남아도 장소를 자동 추가하지 않는다.

### FR-10 일정 확정과 저장

최종 확정 전 하루 관광지 최대 5개, 선택 장소 전체 포함, 날짜별 시간 예산, 숙소 선택, 표시 이름, 실제 경로 검증을 확인한다. 외부 호출과 계산이 끝난 뒤 저장 가능한 자체 일정만 하나의 DB 트랜잭션으로 저장하며 일부만 저장하지 않는다.

### FR-11 완료와 공유

- 고정 HTML 템플릿에 저장된 제목·시간표·사용자 작성 이름·카카오 외부 링크를 채운다.
- 일정마다 HTML 파일을 생성하거나 저장하지 않는다.
- 이동시간은 예상 이동시간으로 표시한다.
- 완료·공유 화면에서는 카카오 API를 호출하거나 지도·경로선을 표시하지 않는다.
- 공유 링크는 읽기 전용이다.

### FR-12 완료 후 편집

일정 제목, 사용자 작성 표시 이름, 메모만 수정할 수 있다. 날짜·순서·시각·체류시간·이동수단은 수정할 수 없다. 장소나 동선을 바꾸려면 기존 일정을 보존하고 새 일정을 생성한다. 완료 후 외부 API 호출이나 재계산은 없다.

### FR-13 인증과 소유권

- 이메일·비밀번호, Spring Security, JWT를 사용한다.
- 소셜 로그인은 제외한다.
- 사용자는 자신의 일정만 조회·편집·삭제할 수 있다.
- 공유 토큰 조회는 별도의 읽기 전용 계약이다.
- 비용이나 쿼터가 발생하는 기능은 인증 사용자만 이용한다.

### FR-14 호출 제한과 중복 요청

| 기능 | 분당 | 하루 |
|---|---:|---:|
| 카카오 장소 검색 | 20회 | 300회 |
| 자동차 경로 | 60회 | 120회 |
| 대중교통 경로 | 60회 | 120회 |
| AI 지역 추천 | 2회 | 10회 |
| AI 메뉴 분석 | 3회 | 15회 |

- 일일 한도는 Asia/Seoul 자정에 초기화한다.
- 재시도와 분할 경로 요청도 각각 호출량에 포함한다.
- 지도 관련 제공자 한도의 90%에서 새로운 호출을 차단한다.
- 대중교통 경로는 다른 API와 별도로 집계하며 공식 일일 1,000건을 기준으로 서비스 전체 900건에서 신규 호출을 차단한다.
- 일반 기능의 사용자 한도 초과는 HTTP 429와 재시도 정보를 반환한다. 완료 일정의 경로 한도 부족은 외부 호출 없이 전체 구간을 거리 기반으로 계산하고 warning을 반환한다.
- 사용자·기능·requestId 조합으로 중복 실행을 막는다.
- 사용자별 분·일 카운터, API별 서비스 전체 일 카운터와 requestId 상태는 MySQL의 별도 운영 테이블에 저장한다. 요청·응답 payload와 외부 데이터는 저장하지 않는다.
- 카운터는 조건부 갱신과 짧은 트랜잭션으로 외부 호출 전에 원자적으로 확보한다. 분·일 기준이 지난 행과 10분이 지난 requestId 상태는 만료 대상으로 정리한다.
- 이미 실행된 외부 호출은 이후 실패해도 호출량에 포함한다.

### FR-15 메뉴 분석 AI

- 입력은 최대 200자다.
- 선택 지역과 작성 중 관광지 맥락을 반영해 메뉴 1~5개, 카카오 검색어, 추천 이유와 선택적인 대상 관광지를 구조화한다.
- 식당을 추천·평가하거나 동선 순위를 결정하지 않으며 결과는 사용자 확정 전까지 선택값이 아니다.
- 잘못된 구조화 응답은 최대 1회 재시도한다.
- 두 번 실패하면 사용자가 검색어를 직접 입력하게 하며 기존 작성 내용은 유지한다.
- 요청·응답 원문은 DB·일반 로그·오류 응답에 저장하지 않는다.

## 6. 외부 데이터와 저장 정책

### 저장 대상

- 일정·항목 ID와 사용자 소유권
- regionId와 생성 당시 표준 지역 이름
- 여행 날짜, 이동수단, 날짜별 활동 시간
- 사용자 작성 제목·표시 이름·메모
- 카카오 장소 ID와 place_url
- 항목 종류, 날짜·순서·시작·종료 시각
- 확정 체류시간과 10분 단위 예상 이동시간
- 날짜별 식사 포함 여부와 식사시간

### 저장 금지

- 카카오 장소명·주소·좌표·전화번호·카테고리
- 장소 검색과 경로 요청·응답 원문
- 경로 좌표·폴리라인·지도 이미지
- 외부 API의 원본 소요시간
- 카카오 검색 결과 캐시

브라우저 localStorage·sessionStorage·IndexedDB 또는 서버 DB·Redis·Caffeine·세션에 외부 결과를 저장해 제한을 우회하지 않는다. 브라우저는 한 번의 작성 흐름 동안 메모리에서만 외부 결과를 유지하고, 서버는 estimate와 create 각각의 요청 지역 변수에서만 좌표를 사용한다.

### 제작 중 데이터 수명

검색 결과와 선택 좌표는 브라우저 탭의 JavaScript 메모리에서 한 번의 작성 흐름 동안만 유지한다. 브라우저는 estimate와 create 요청에 필요한 값을 전달하며 서버는 각 요청 안에서만 사용하고 응답 전에 참조를 폐기한다. 완료·취소·새로고침·탭 종료 시 브라우저 상태를 폐기하고 새로고침 복구는 제공하지 않는다.

2026-09-11 카카오 DevTalk에서 "일시적으로 저장 및 참조 후 즉시 폐기하는 구조는 허용 가능합니다."라는 답변을 받았다. 따라서 위 흐름을 확정한다. 좌표와 Local API 응답은 한 번의 제작 흐름과 해당 서버 요청에서만 사용하고 즉시 폐기하며, 영속 저장·캐시·로그 기록·완료 일정 재조회에는 사용하지 않는다.

## 8. 비기능 요구사항

### NFR-01 보안과 외부 데이터

- 비밀값은 환경변수 또는 승인된 외부 설정으로 주입한다.
- 비밀번호를 평문으로 저장하지 않는다.
- 사용자 입력을 검증하고 출력 시 안전하게 처리한다.
- 외부 원문과 비밀값을 일반 로그·fixture·오류 응답에 남기지 않는다.

### NFR-02 Client와 계층 분리

- OpenAI 코드는 ai 패키지에서 관리한다.
- 카카오 장소 코드는 place/client에서 관리한다.
- 자동차·대중교통 경로 코드는 route/client에서 관리한다.
- Service는 Client 인터페이스에 의존하고 구체 HTTP 구현을 직접 생성하지 않는다.
- 테스트에서는 fake Client를 사용한다.
- Controller, Service, Repository, Entity, DTO의 책임을 분리한다.

### NFR-03 신뢰성과 비용

- timeout, 인증 실패, 한도 초과, 제공자 장애, 정상 빈 결과를 구분한다.
- 중복 클릭과 네트워크 재전송으로 외부 호출이 반복되지 않게 한다.
- 지도 관련 API는 무료 제공량 안에서만 사용하고 유료 초과를 자동 허용하지 않는다.
- AI는 사용자 한도와 서비스 전체 예산으로 통제한다.
- 제공자 쿼터와 가격은 구현 시점의 공식 문서와 앱 콘솔에서 재확인한다.

### NFR-04 테스트

지역 검증, 거리·방문 순서, 10분 올림, 체류시간, 시간 예산, 경로 실패, 변경 구간 재조회, 추천 점수, 저장 금지 필드, 편집 범위, 호출 제한, 인증·소유권에 자동 테스트를 작성한다. 세부 책임은 docs/08-test-strategy.md를 따른다.

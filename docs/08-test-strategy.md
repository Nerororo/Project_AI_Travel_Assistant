# 테스트 전략

## 1. 목표

테스트는 구현 존재 여부가 아니라 여행 계획 결과의 정확성, 외부 장애 시의 예측 가능한 동작, DB 제약의 재현성을 검증한다.

각 기능은 필요한 가장 작은 테스트 수준을 선택한다. 단위 테스트로 충분한 알고리즘에 Spring Context나 실제 DB를 사용하지 않는다.

## 2. 테스트 수준과 책임

| 수준 | 대상 | 검증 내용 | 외부 의존성 |
|---|---|---|---|
| 단위 테스트 | 거리 계산, RouteOptimizer, 추천 점수, 일정 배치 | 입력 대비 결정적 결과와 경계값 | 없음 |
| 서비스 테스트 | Use case Service | 도메인 규칙, 예외 변환, 여러 컴포넌트 조합 | Repository/client fake 또는 mock |
| Repository 통합 테스트 | JPA Repository, migration, 제약조건 | 실제 SQL, Google Place ID UNIQUE·FK 제약 | 전용 MySQL 테스트 DB 또는 Testcontainers |
| API 테스트 | Controller와 Global Exception Handler | HTTP 상태, JSON 계약, validation 오류 | MockMvc, Service mock/fake |
| 애플리케이션 통합 테스트 | 핵심 생성 흐름 | DB 저장부터 응답까지의 주요 흐름 | 전용 MySQL 테스트 DB, 외부 client fake |
| 브라우저 흐름 테스트 | 실제 Routy 화면 | 입력 유지, 단계 전환, API 연결, 로딩·성공·실패 표시 | 테스트 서버와 외부 client fake |

## 3. 외부 클라이언트 규칙

자동 테스트는 OpenAI나 외부 지도 API를 실제 호출하지 않는다.

```text
Service
  ├── AiClient  → FakeAiClient / mock
  └── GooglePlacesClient → FakeGooglePlacesClient / mock
```

- fake 구현체는 고정된 요청에 항상 같은 응답을 반환한다.
- timeout, 5xx, 잘못된 JSON, 빈 검색 결과는 fake 또는 mock으로 재현한다.
- 실제 제공자 연결 확인은 자동 테스트와 분리한 수동 smoke test로만 수행한다. API 키가 없는 환경에서도 전체 테스트가 통과해야 한다.

## 4. Fixture 규칙

- 공통 fixture는 `src/test` 아래 도메인별 factory 또는 builder로 관리한다.
- 위도·경도·거리 기대값·장소 ID는 테스트마다 임의 생성하지 않고 명시적 상수를 사용한다.
- 시간에 의존하는 테스트는 `Clock`을 주입하거나 고정 날짜를 사용한다.
- 테스트 간 DB 상태를 공유하지 않으며, 각 테스트는 독립 실행 가능해야 한다.
- 알고리즘 테스트는 동일 거리 후보가 있을 때 ID 오름차순을 선택하는 등 동률 해소 규칙을 기대값에 포함한다.

## 5. 도메인별 필수 테스트

### Place와 Google Places

- 동일한 Google Place ID가 하나의 내부 Place 참조로 재사용되는지
- Google Place ID 중복 저장이 DB UNIQUE로 차단되는지
- 국가·도시·관광지·호텔·음식점 유형 검증이 잘못된 후보를 거절하는지
- 방문 장소와 호텔의 선택 도시 소속을 확인하고, 소속 근거가 없으면 추측하지 않고 거절하는지
- 도시 직접 선택 검증과 장소 상세 API의 `200`·`400`·`404`·`503`
- Google timeout·5xx·잘못된 응답이 도메인 오류로 변환되는지
- Google Places 후보 전체를 DB에 일괄 저장하지 않는지
- TravelPlan FK가 생긴 뒤 같은 Google Place ID 참조 재사용과 계획 삭제 후 공유 Place 유지 정책을 T1-06에서 통합 테스트한다.

### TravelPlan

T1에서는 계산 완료된 고정 일정 fixture로 내부 저장·조회·교체·삭제를 테스트한다. 날짜·순서·필수 표시·시각·체류 시간의 저장과 복원, DB 제약, 새 Place 참조를 포함한 전체 저장 rollback, 교체 실패 시 기존 계획 보존을 검증한다. 공유 Place 저장은 Place 도메인의 Service 계약을 사용한다. 다른 도메인의 Repository를 TravelPlan Service에서 직접 호출하지 않는다.

Fixture는 테스트 전용 데이터이며 실제 장소 검증 성공이나 일정 계산 정확성의 증거가 아니다. Google 검증·시간 용량 계산·공개 API 테스트는 T2에서 아래 항목까지 수행한다. T1을 통과했다는 이유로 이 항목들을 완료로 표시하지 않는다.

- 시작일이 종료일보다 늦은 요청 거절
- 1일과 14일의 경계값, 15일 요청 거절
- 필수 장소가 누락되지 않는지
- 중복 장소와 일일 6개·전체 용량 초과 거절
- 기본 `10:00~21:00`, 사용자 지정 시작·종료 시각과 잘못된 시간 범위 거절
- 장소 유형별 기본 체류 시간, 복수 유형의 최댓값, 사용자 수정값 우선 적용
- 자동 배치는 필수·선택 요청 순서와 추가 후 소요 시간 최소 날짜를 따르고 동률은 날짜순인지. 외부 응답·행렬이 같은 fixture에서 결정적 결과를 검증한다.
- 3일·동일 부담 장소 6개 fixture는 첫날 몰림 없이 2개씩 배치되는지, 긴 체류 1개와 짧은 장소 여러 개는 개수보다 체류·직접 이동·체류 밖 식사·여유 합으로 비교하는지 검증한다. 대기를 점수에 넣어 모든 날짜가 같은 부담으로 계산되는 오류를 막는다.
- 제한된 단일 장소 이동이 편차를 엄격히 줄이는 경우만 적용되고, 동률·최대 N회·개선 없음 종료·자유 일정 수 증가 금지·사용자 날짜 유지가 지켜지는지 검증한다. 다른 배치가 가능해도 탐욕 과정에서 수용 불가이면 전체 실패하는 한계를 fixture로 명시한다.
- 기간보다 장소가 적을 때 모든 Day를 반환하고 빈 날짜의 places는 빈 배열이며 식사 검색은 호텔 기준인지 검증한다.
- 식사 시각은 FR-11의 우선 시각 편차 최소화와 동률 규칙을 따르는지, 12시가 관광·이동·여유 때문에 불가능해도 허용 구간 내 다른 시각으로 배치되는지 검증한다. 짧은 체류를 임의 분할하거나 식사와 겹치게 하지 않는다.
- 여유값 생략=15, 0·60 허용, -1·61·소수·null 거절을 검증한다. T1에서 저장·조회·교체·rollback와 DB CHECK, T2에서 POST·GET·PUT의 입력값 복원을 검증한다.
- 긴 체류 안의 식사·외출 이동은 중복 합산하지 않고 체류 밖 식사·이동을 반영한 시간표가 용량을 초과하면 필수 장소를 제거하지 않고 거절하는지
- 선택 호텔이 추천 후보인지와 관계없이 Google Places에 존재하는지, 숙박 장소 유형인지, 선택 도시 범위와 일치하는지 검증하는지
- 선택된 호텔에서 출발하고 같은 호텔로 돌아오는 날짜별 경로가 계산되는지, 호텔과 음식점 추천 후보가 방문 장소로 저장되지 않는지
- 필수·선택 목록 내부 중복, 두 목록 사이 중복, 도시·호텔·방문 장소 역할 중복을 모두 거절하는지
- 체류 시간 수정 ID가 최종 방문 장소 집합에 포함되지 않거나 수정 목록에서 중복되면 거절하는지
- Google Places·Routes 검증 또는 계산 실패 시 `Place`, TravelPlan, Day, PlanPlace가 하나도 새로 저장되지 않는지
- 모든 외부 검증이 DB 트랜잭션 시작 전에 끝나고, 저장 단계 실패 시 Aggregate 전체가 rollback되는지
- 계획 삭제 시 식사 슬롯을 포함한 하위 Aggregate는 삭제되고 Place는 삭제되지 않는지
- 식사 슬롯의 종류·시작·종료 시각 저장·복원과 Day별 식사 종류 UNIQUE·시간 CHECK 제약 검증
- GET 반복 및 Google 표시 정보 변경·조회 실패에도 저장된 방문 순서·시간표·식사 슬롯이 유지되는지, Routes·일정 계산·음식점 검색·DB 변경을 호출하지 않는지
- PUT 전체 입력 교체·생략값 처리, 일정 조건 변경 시 재계산, 음식 목록만 변경 시 시간표 유지 검증
- PUT의 날짜 배정이 모든 최종 장소를 정확히 한 번 포함하는지 검증하고, 누락·중복·목록 밖 장소·기간 밖 날짜를 `INVALID_DAY_ASSIGNMENT`로 거절하는지
- 사용자가 지정한 날짜 그룹은 유지하면서 날짜별 경로·시각·식사 슬롯을 재계산하고, 최대 6개나 시간 용량 초과 시 다른 날짜로 자동 이동하지 않으며 기존 계획을 보존하는지
- 재계산·저장 실패 시 기존 방문 일정과 식사 슬롯 전체 보존 검증
- 생성·조회·수정 응답에 음식점 후보가 없고 별도 후보 검색이 저장된 시간표를 변경하지 않는지

### Route와 Recommendation

- 저장 일정 기반 검색은 계획 ID·날짜·식사 종류·음식만으로 저장된 도시·호텔·방문 시각·식사 시각이 전달되는지 검증한다.
- 계획 없음·기간 밖 날짜·식사 슬롯 없음·잘못된 입력 시 각각의 API 오류 코드와 외부 Client 미호출을 검증한다.
- 클라이언트의 별도 도시·시간표·식사 시각 입력을 거절하고 저장된 값이 검색 기준이 되는지 검증한다.
- 정상 빈 검색은 `200`과 빈 후보 목록, 제공자 장애는 `503`으로 구분한다. 다른 음식으로 검색해도 선호·일정·슬롯이 변경되지 않는지 검증한다.

- Haversine 거리 계산의 0 거리·대칭성·대표 좌표 결과
- fake Google Routes 행렬의 이동 시간·거리 매핑과 provider 오류 변환
- Nearest Neighbor가 모든 장소를 한 번만 방문하는지
- 동률 후보의 결정적 선택과 빈/단일 장소 입력
- 2-opt 적용 결과가 기준 경로보다 길어지지 않는지
- 호텔 총거리와 음식점 이탈시간·거리 기준의 정렬
- 점심 `11:30~14:00`, 저녁 `17:30~20:30` 밖의 음식점 슬롯을 만들지 않는지
- 사용자 지정 하루 범위와 식사 시간대의 겹침이 60분 미만이면 해당 슬롯을 생략하는지
- 긴 체류가 식사 시간대 전체를 포함하면 내부 후보를 우선하고, 없으면 인접 후보로 대체하며 미확인 후보를 내부로 표시하지 않는지

#### 식사 시간 합산 경계 테스트

- 일반 구간 T=20, b=15, A 출발 11:35이면 12:00~13:00 식사와 B 도착 13:25로 최소 110분을 확보한다. 직접 이동을 두 번 더하지 않으며 reservedMinutes는 60이다. 25분 편도는 허용하고 26분은 제외한다. 비대칭 실제 이동 시간도 각각 검증한다.
- 홀수 T의 ceil/floor 합이 T인지, 같은 경로 구간의 복수 식사에서 직접 이동을 한 번만 더하고 식사마다 2b를 확보하는지 검증한다. 다른 저장 슬롯·예약 구간 침범을 거절한다.
- 하루와 식사 시간대의 겹침 59분이면 슬롯 생략, 60분이지만 일반 식사 여유를 넣을 수 없으면 슬롯을 생략하지 않고 용량 초과를 반환한다. b=0과 긴 체류 내부 식사는 각자의 규칙으로 검증한다.
- PUT 여유 15→30은 시간표·슬롯 재계산, 생략 시 15로 초기화, 용량 초과·외부 실패·DB 실패 시 이전 여유와 일정 보존을 검증한다. 음식만 변경하고 여유 등 일정 조건이 같으면 재계산하지 않는다.
- 검색 범위의 조건 일치 후보 없음은 NO_MATCHING_CANDIDATES, 일치 후보가 모두 시간 탈락이면 NO_TIME_FEASIBLE_CANDIDATES, 유효 후보가 있으면 emptyReason=null이다. 모두 검색 전후 DB가 같고 provider 장애는 503이다. 이동 여유가 있어도 빈 결과가 가능한 fixture를 포함한다.
- 같은 행렬을 날짜 평가·보정 동안 재사용하고 외부 호출이 후보 평가 횟수만큼 늘지 않는지 검증한다. 최대 14일·84개 입력에서 평가 횟수 상한과 종료를 확인하고 소요 시간은 실제 측정값만 기록한다.

- 10:00~16:00 체류·12:00~13:00 식사·왕복 20분이면 체류 360분 유지, 관광 가능 280분이며 440분으로 중복 계산하지 않는다.
- 식사와 외출 구간이 체류 시작·종료 경계에 정확히 맞으면 허용하고, 어느 방향이든 1분 벗어나면 후보를 제외한다. 비대칭 왕복 시간을 각각 검증한다.
- 시간 조건에 실패한 내부 후보만 있으면 유효한 인접 후보로 대체하고, 인접 후보도 실패하면 빈 목록을 반환한다.
- 일반 구간은 음식점 도착이 식사 시작보다 1분 늦거나 식사 후 이동이 다음 장소 도착보다 1분 늦으면 제외한다. 정확히 맞으면 허용한다.
- 동일 체류 안의 복수 식사·외출 구간이 겹치면 후보를 제외하며 저장된 식사·출발·후속 도착 시각은 유지한다.

### AI

- 국가를 입력하면 중복 없는 3~5개의 도시 이름·국가 코드·추천 이유가 DTO로 변환되는지
- 선택 국가와 다른 국가 코드, 잘못된 후보 수, JSON 파싱 실패, 누락 필드가 `AI_RESPONSE_INVALID`로 변환되는지
- AI 도시 후보가 Google Places에서 실제 도시로 검증되고 유효한 Google Place ID를 받은 뒤에만 응답되는지
- timeout과 5xx가 최대 한 번 재시도된 뒤 `AI_UNAVAILABLE`으로 변환되는지
- 인증·요청 오류는 재시도하지 않는지
- 실제 API 키 없이 fake 클라이언트로 테스트가 통과하는지

### 실제 서비스 화면

- 국가를 선택하면 AI 도시 후보 단계로 이동하고, 도시를 직접 선택하면 그 단계를 건너뛰는지 검증한다.
- 날짜·하루 시간·식사 이동 여유·음식 입력을 유지한 채 필수 장소와 추천 관광지를 선택하고 체류 시간을 수정할 수 있는지 검증한다.
- 선택 장소를 기준으로 호텔 후보를 조회하고 호텔 선택 전에는 일정 생성을 요청하지 않는지 검증한다.
- 일정 생성 성공 후 날짜별 시간표와 호텔·관광지 마커·방문 번호를 표시하는지 검증한다. 좌표 오류나 지도 로딩 실패에도 시간표를 유지한다.
- 사용자 날짜 배정으로 PUT을 호출하고 성공 결과를 교체하며, validation·용량·provider·저장 실패 시 기존 화면 일정을 유지하는지 검증한다.
- 저장된 식사 슬롯에서만 음식점을 검색하고 `emptyReason` 두 종류와 provider 장애를 서로 다른 안내와 행동으로 표시하는지 검증한다.
- 로그인 후 내 일정 목록에서 계획을 선택해 상세 조회로 다시 여는지와 다른 사용자의 계획을 열 수 없는지 검증한다.
- 각 단계에서 로딩 중 중복 제출을 막고, 뒤로 이동해도 완료한 입력·선택을 유지하며, 오류 후 다시 시도할 수 있는지 검증한다.
- 모바일과 데스크톱의 핵심 입력·선택·시간표가 가려지지 않고 키보드로 주요 동작이 가능한지 확인한다.

핵심 9단계 성공 흐름과 대표 실패 흐름은 자동화한다. Google 자동완성·Maps JavaScript 렌더링·실제 OpenAI 응답은 자동 테스트의 완료 조건으로 삼지 않고 제한된 키를 사용한 수동 smoke test로 별도 확인한다.

## 6. 기능 완료 기준

한 기능은 아래를 모두 만족할 때 완료로 표시한다.

1. 핵심 성공 시나리오와 최소 한 개의 실패/경계 시나리오를 자동 테스트한다.
2. API가 있으면 성공·validation·not found 상태 코드를 테스트한다.
3. DB를 변경하면 migration 적용과 제약조건을 통합 테스트한다.
4. 외부 API는 fake 테스트와 수동 smoke test 절차를 분리한다.
5. 전체 `./gradlew test`가 통과한다.
6. 화면 기능이면 관련 브라우저 흐름 테스트가 통과하고 수동 확인이 필요한 항목을 분리해 기록한다.

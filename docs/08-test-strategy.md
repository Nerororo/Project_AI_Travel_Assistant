# 테스트 전략

## 1. 목표

테스트는 코드 존재 여부보다 일정 결과의 정확성, 권한과 데이터 수명, 외부 장애 시 동작, DB 무결성을 검증한다. 각 규칙은 가장 작은 테스트 수준에서 확인하고, 순수 알고리즘에 Spring Context나 실제 DB를 사용하지 않는다.

이 문서는 목표 테스트 계약을 정의한다. 아직 구현되지 않은 항목은 테스트가 작성되기 전까지 완료로 표시하지 않는다.

## 2. 테스트 수준과 책임

| 수준 | 대상 | 주요 검증 | 외부 의존성 |
|---|---|---|---|
| 단위 | 값 객체, 정책, 경로 알고리즘 | 경계값, 결정성, 반올림, 불변식 | 없음 |
| Service | 도메인 use case | 규칙 조합, 호출 순서, 실패 변환 | Repository·Client fake/mock |
| Repository 통합 | Entity, Repository, migration | 실제 SQL, UNIQUE·CHECK·FK, rollback | Testcontainers MySQL 8.4 |
| API | Controller, Security, 예외 처리 | 인증, validation, 상태 코드, JSON 계약 | MockMvc, Service mock/fake |
| 핵심 통합 | 인증부터 Aggregate 저장·조회 | 계층 연결, 원자성, 외부 호출 경계 | 테스트 DB, 외부 Client fake |
| 브라우저 | 작성·완료·공유 화면 | 입력 유지, 단계 전환, 오류 복구, 저장 금지 | 테스트 서버, 외부 Client fake |

## 3. 공통 원칙

- `./gradlew test`는 OpenAI와 카카오 API를 실제 호출하지 않는다.
- 실제 제공자 연결은 명시적으로 실행하는 별도 smoke profile에서만 확인한다.
- API 키가 없는 환경에서도 전체 자동 테스트가 통과해야 한다.
- 같은 입력과 같은 fake 응답은 항상 같은 일정 결과를 만들어야 한다.
- 테스트는 실행 순서와 공유 DB 상태에 의존하지 않는다.
- 시간 기반 규칙에는 주입한 `Clock`과 `Asia/Seoul`을 사용한다.
- 비밀값, 개인정보, AI 사용자 원문, 외부 API 원문과 실제 좌표를 fixture·로그·실패 메시지에 남기지 않는다.
- 좌표가 필요한 알고리즘 fixture는 명시적인 가상 좌표 또는 사용 허가가 분명한 공개 기준값을 사용한다.

### 공통 HTTP 오류 계약

- 모든 오류 테스트는 `code`, `message`, `fieldErrors`, `details`, `adjustments`, `retryAfterSeconds` 여섯 필드가 생략되지 않는지 검증한다.
- validation 테스트는 필드 경로와 안정적인 reason의 정렬·중복 제거를 확인하고 Spring·Jackson의 exception message가 노출되지 않는지 확인한다.
- 401은 token 없음·잘못됨·만료와 로그인 실패가 같은 공개 응답인지, 403은 인증 성공 후 권한 부족에만 사용되는지 검증한다.
- 404·409·422는 도메인 예외의 code와 HTTP 상태가 정확히 대응하고 명세되지 않은 details가 추가되지 않는지 검증한다.
- 429는 본문의 `retryAfterSeconds`와 `Retry-After` 헤더가 같은 양의 정수인지 검증한다.
- 503과 예상하지 못한 500은 provider 원문, URL, stack trace, exception class, 비밀값과 사용자 입력을 포함하지 않는지 검증한다.
- 각 테스트는 HTTP status만 확인하지 않고 전체 오류 JSON 계약을 확인한다.

### DB 테스트 기반 선택

Repository·migration·핵심 통합 테스트는 MySQL 8.4 Testcontainers를 사용한다.

| 선택지 | 판단 | 이유 |
|---|---|---|
| Testcontainers MySQL 8.4 | 선택 | 테스트마다 격리된 실제 MySQL을 제공해 migration과 MySQL 제약을 같은 엔진에서 검증할 수 있음 |
| 개발자 전용 또는 공용 MySQL | 기본 자동 테스트에서 제외 | 별도 설치·계정이 필요하고 잔여 데이터와 실행 순서에 의존할 수 있음 |
| H2 | 제외 | MySQL dialect, CHECK·FK·UNIQUE와 migration 호환성을 운영 DB와 동일하게 보장하지 못함 |

- Spring Boot의 `@ServiceConnection`으로 컨테이너 JDBC·Flyway 연결 정보를 주입하며 테스트 설정에 URL·사용자명·비밀번호를 고정하지 않는다.
- DB 통합 테스트는 production migration만으로 생성된 빈 schema에서 시작한다. 테스트 데이터는 테스트 준비 코드로 넣고 schema를 만드는 별도 test migration으로 production migration의 누락을 감추지 않는다.
- migration 적용 성공 뒤 `ddl-auto: validate`가 통과해야 하며, Repository 제약·rollback 테스트는 같은 MySQL 의미론에서 실행한다.
- 테스트 클래스 간 상태를 공유하지 않는다. 컨테이너 재사용 최적화는 격리 보장이 확인되기 전에는 적용하지 않는다.
- Docker를 사용할 수 없으면 DB 테스트를 H2로 대체하거나 성공 처리하지 않고 환경 원인과 미실행 범위를 명확히 실패로 보고한다.

## 4. 외부 Client 테스트

```text
AiService    → AiClient        → FakeAiClient / mock
PlaceService → KakaoPlaceClient → FakeKakaoPlaceClient / mock
RouteService → RouteClient      → FakeCarRouteClient
                                → FakeTransitRouteClient
```

각 Client 계약은 성공, 빈 결과, timeout, 4xx, 5xx, 잘못된 응답을 재현할 수 있어야 한다. 실제 HTTP 구현 테스트는 요청 URL·헤더·timeout·응답 매핑까지만 검증하며 운영 API 호출을 기본 테스트에 포함하지 않는다.

기술적 경로 장애는 최초 실패 뒤 한 번만 재시도하는지 검증한다. 두 번째 기술적 실패는 Haversine 추정값과 warning으로 대체할 수 있다. 정상적인 “경로 없음”은 재시도나 fallback 없이 `ROUTE_NOT_FOUND`로 끝나야 한다.

## 5. Fixture 규칙

- fixture는 `src/test` 아래 도메인별 factory 또는 builder에 둔다.
- 장소 ID, 날짜, 시각, 거리와 예상 결과를 테스트 안에 명확히 드러낸다.
- 동일 거리 후보는 안정적인 내부 키 등 설계된 동률 규칙으로 결정한다.
- 각 테스트는 한 가지 규칙이 실패했을 때 원인을 알 수 있는 크기로 만든다.
- 외부 제공자 응답 fixture에는 필요한 필드만 포함하고 원문 전체를 복제하지 않는다.
- 사용자가 직접 작성하는 장소 표시 이름과 카카오 제공 장소명을 서로 다른 값으로 둔다.

## 6. 도메인별 필수 테스트

### 6.1 인증과 소유권

- 회원가입 시 비밀번호 원문이 저장·응답·로그에 남지 않는지
- 이메일 중복과 입력 형식 오류가 계약된 상태 코드로 변환되는지
- 회원가입 저장 중 실제 중복 키만 `EMAIL_ALREADY_EXISTS`로 변환하고 다른 DB 무결성 오류를 중복 이메일로 오인하지 않는지
- 로그인 성공, 잘못된 비밀번호, 만료·변조 JWT가 구분되는지
- 호출 한도 창에 소수 초가 남아도 `retryAfterSeconds`를 올림하고 최소 1초를 반환하는지
- 인증 없는 일정 작성·목록·상세·수정·삭제가 차단되는지
- 다른 사용자의 일정 조회·수정·삭제가 차단되는지
- 공개 소개·샘플·유효한 공유 링크만 인증 없이 접근 가능한지
- 명세에 없는 개발 확인용 endpoint가 운영 애플리케이션에 노출되지 않고 공통 404를 반환하는지

### 6.2 지역 기준 데이터

- `regions.json`이 시작 시 중복 ID, 잘못된 상위 관계, 누락 이름·좌표를 거절하는지
- 서울특별시·광역시·세종특별자치시를 자체 최종 지역으로 선택할 수 있는지
- 도·특별자치도는 자체를 최종 선택하지 못하고 그 아래 시·군 하나만 선택할 수 있는지
- 특별시·광역시 아래 구·군이 장소 검색 필터로만 제공되고 최종 일정 regionId로 거절되는지
- 광주는 전남광주통합특별시의 5개 구만 묶은 하나의 최종 지역이며 각 구는 검색 필터로만 제공되는지
- 수원처럼 일반구가 있는 도 산하 시는 시 하나만 최종 지역으로 제공하고 일반구는 주소 경계에만 포함하는지
- 모든 최종 지역과 검색 필터의 `addressBoundary`가 공식 1단계·2단계 주소 이름을 빠짐없이 가지며, 세종의 빈 2단계 목록은 2단계 제한 없음으로 처리하는지
- 읍·면·동과 해외 지역이 결과에 포함되지 않는지
- 동일 검색어 결과와 정렬이 결정적인지
- 완료 일정에 지역 ID와 당시 표시 이름 snapshot이 보존되는지

### 6.3 AI

지역 추천:

- 서버가 제공한 허용 지역 목록 안에서 중복 없는 정확히 3개 ID와 이유를 반환하는지
- 목록 밖 ID, 중복 ID, 잘못된 개수, 누락 필드와 JSON 오류를 `AI_RESPONSE_INVALID`로 변환하는지

메뉴 분석:

- 자연어가 메뉴 이름과 장소 검색어로만 구조화되는지
- 사용자가 입력하지 않은 메뉴를 임의로 확정하지 않는지
- 최종 선택 가능한 국내 regionId만 허용하고 미존재·상위 도·검색 필터용 구·군은 외부 호출과 차감 전에 거절하는지
- 관광지 맥락 0·35개를 허용하고 36개, clientPlaceId 중복·공백·길이 초과와 displayName 길이 초과를 거절하는지
- 잘못된 구조 응답을 최대 한 번 재시도하고 다시 실패하면 오류로 끝나는지

공통:

- 인증·요청 오류는 재시도하지 않는지
- Fake Client만으로 성공·계약 위반·장애 테스트가 통과하는지
- 사용자별 지역 AI 2회/분·10회/일, 메뉴 AI 3회/분·15회/일을 검증하는지
- 일일 한도가 `Asia/Seoul` 자정에 초기화되는지

### 6.4 장소 검색과 선택

- 역할별 요청과 검색 반경이 Kakao Client 계약으로 올바르게 전달되는지
- 관광지가 대표 좌표 20km 안이거나 주소 행정구역이 선택 지역과 일치할 때만 후보로 남는지
- 특별시·광역시·세종특별자치시에서 20km 반경을 전체 경계로 간주하지 않고 지역명 결합 검색과 주소 검증으로 도시 전역 후보를 처리하는지
- 특별시·광역시의 선택적 구·군 필터를 적용하면 다른 구·군 결과가 제외되는지
- 장소 검색 20회/분·300회/일 한도가 적용되는지
- 결과 부족 시 임의 장소를 생성하지 않는지
- 카카오 카테고리가 노출되지 않고 기본 체류 시간으로만 변환되는지
- 일반·자연 90분, 박물관 120분, 체험 180분, 등산 240분, 테마파크 360분, 식사 60분 규칙과 경계 분류를 검증하는지
- 호텔에는 관광 체류 시간이 적용되지 않는지
- 사용자 표시 이름이 빈 값으로 시작하며 카카오 장소명을 기본값이나 placeholder로 복사하지 않는지
- 표시 이름 trim 후 1~50자, 체류 시간 30~480분과 10분 배수를 검증하는지
- `selectionToken`의 정상값, 만료, 서명 변조, 역할 불일치와 payload 변경이 구분되는지
- 검색 결과의 좌표·주소·카테고리·제공자 장소명이 Repository에 저장되지 않는지
- 숙소 기본 검색이 관광지 기하 중앙값과 5km를 사용하고 10km 확대를 사용자가 선택하는지
- 중심 관광지 검색이 다른 관광지까지 거리 합이 가장 작은 메도이드를 사용하는지
- 현재 지도 영역 재검색과 관광지·숙소 마커·목록이 동기화되는지
- 숙소에 거리 합 점수나 자동 추천 순위를 부여하지 않는지

카카오 DevTalk 답변은 허용 범위를 확인한 근거다. 실제 좌표 전달 흐름이 일시 사용·즉시 폐기 계약을 지키는지는 별도 테스트로 증명한다.

### 6.5 순수 경로 알고리즘

Haversine:

- 같은 좌표의 거리가 0인지
- A→B와 B→A가 같은지
- 알려진 짧은 거리에서 단위와 허용 오차가 맞는지
- 위도·경도 범위 밖 입력을 거절하는지

Nearest Neighbor:

- 빈 목록과 단일 장소
- 모든 장소를 정확히 한 번 방문
- 시작점 고정 여부
- 같은 거리에서 결정적인 동률 해소

2-opt:

- 결과가 입력 경로보다 길어지지 않는지
- 장소 집합과 시작점이 보존되는지
- 개선 없음과 반복 상한에서 종료하는지
- 같은 행렬에서 항상 같은 결과인지

추정 시간:

- `CAR`과 `PUBLIC_TRANSIT` 정책이 혼합되지 않는지
- 거리 0, 짧은 거리와 정책 경계값
- 추정값을 실제 검증값으로 표시하지 않는지

### 6.6 일정 추정

`POST /api/travel-plans/estimate`는 다음을 검증한다.

- 1일·7일 허용, 0일·8일과 역전 날짜 거절
- 각 날짜의 시작 시각이 종료 시각보다 빠른지
- 하루 관광지 최대 5개
- 1박 이상일 때 호텔 필수, 당일치기 호텔 null
- 일정 전체에서 하나의 이동수단만 허용
- 체류 시간과 사용자 표시 이름 규칙
- 점심 11:30~14:00·저녁 17:30~20:30과 하루 범위가 60분 이상 겹칠 때 60분 슬롯을 만들고 12:00·18:00을 우선하는지
- 일반 식사에 한쪽 기본 15분을 확보하고 0·60 경계를 허용하며 긴 체류 안에서는 식사·왕복 이동을 중복 합산하지 않는지
- 실제 Route Client와 Repository를 호출하지 않는지
- 응답이 `routeVerified=false`인지
- 같은 입력에 방문 순서와 시각이 결정적인지
- 작성 초안이 DB나 서버 세션에 저장되지 않는지
- 모든 day·order가 null이면 자동 배치하고 모두 지정되면 사용자 배치를 보존하는지
- 일부 장소에만 day·order가 있거나 clientPlaceId·순서가 중복되면 400인지

### 6.7 실제 경로 검증과 완료 일정 생성

- 추정 시간은 신뢰하지 않고 서버가 다시 계산하되 사용자가 확정한 날짜·순서는 보존하는지
- 최종 후보의 인접 구간 수만큼만 Route Client를 호출하는지
- `CAR`은 자동차 Client, `PUBLIC_TRANSIT`은 대중교통 Client만 사용하는지
- 1~600초는 10분, 601~1200초는 20분처럼 `ceil(seconds/600) * 10`이 적용되는지
- 별도의 고정 이동 여유를 더하지 않는지
- 경로 API가 반환한 예상 이동시간 반영 후 종료 시각을 넘으면 422이며 저장하지 않는지
- 시간 초과 때 장소 삭제나 체류 시간 축소를 하지 않는지
- 정상 경로 없음은 422이고 fallback하지 않는지
- 일시적 장애는 한 번 재시도하고, 재실패 fallback 때 생성 응답에 warning을 반환하되 MOVE에는 10분 단위 예상시간만 저장하는지
- API 결과와 Haversine fallback을 구분하는 출처·상태 및 생성 warning이 DB에 저장되지 않는지
- 외부 호출과 계산 중 DB 트랜잭션이 열리지 않는지
- 모든 계산 성공 후 TravelPlan Aggregate 전체가 한 트랜잭션으로 저장되는지
- 저장 실패 시 TravelPlan, Day, Item, PlanPlace가 모두 rollback되는지
- 좌표·주소·카테고리·제공자 장소명·경로 원문이 어느 Entity에도 저장되지 않는지
- `requestId` 중복 요청은 10분간 상태만 기억하고 결과 리소스 ID·payload·response를 저장하지 않는지
- 처리 중 같은 requestId는 409 `REQUEST_IN_PROGRESS`, 성공한 같은 requestId는 409 `REQUEST_ALREADY_COMPLETED`이며 두 경우 모두 외부 호출·저장·호출량 차감이 반복되지 않는지
- 10분 수명이 지난 requestId를 새 요청으로 처리할 수 있는지
- 서로 다른 서버 인스턴스를 가정한 동시 요청도 MySQL 공유 카운터의 사용자·서비스 한도를 넘지 않는지
- 조건부 갱신 중 하나라도 한도를 넘으면 같은 확보 트랜잭션의 모든 카운터 증가가 rollback되는지
- 카운터 확보 커밋 뒤 외부 Client를 호출하고 만료 행 삭제 지연이 현재 한도 판정에 영향을 주지 않는지
- 처리 중 중복은 409이며 동일 요청으로 외부 호출이 늘지 않는지
- 자동차·대중교통 경로 각각 60회/분·120회/일 한도가 적용되는지

대중교통은 카카오맵 REST API를 사용하고 서비스 전체 일일 900건에서 신규 호출을 차단하는지 검증한다. 완료 생성 전에 필요한 실제 요청 수만큼 쿼터를 원자적으로 확보하고, 잔여 한도가 부족하면 외부 호출 없이 전체 구간에 Haversine 예상시간과 warning을 사용하는지도 검증한다.

### 6.8 Aggregate와 DB

- User→TravelPlan 소유권 FK
- TravelPlan→Day→Item과 PlanPlace 관계 및 삭제 정책
- 날짜별 item 순서 UNIQUE
- 이동·방문 항목별 nullable 필드 조합과 시간 순서 CHECK
- 체류·이동 시간이 10분 배수인지
- 저장한 지역 이름, 사용자 장소 이름, 시간표와 외부 링크가 그대로 복원되는지
- 적용된 migration을 수정하지 않고 새 migration으로 변경하는지
- Entity를 API Response로 직접 반환하지 않는지

### 6.9 완료 일정 조회·수정·삭제·공유

- 목록과 상세가 인증 사용자 소유 일정만 반환하는지
- 상세와 공유 조회가 Kakao·OpenAI·Route Client를 호출하지 않는지
- 좌표, 주소, 카테고리와 경로선이 응답에 없는지
- 제목, 사용자 장소 표시 이름과 메모만 수정되는지
- 날짜, 순서, 시각, 체류 시간, 이동수단, 장소 ID·URL 수정 시도가 거절되는지
- 텍스트 수정이 경로 재계산이나 외부 호출을 일으키지 않는지
- 삭제 시 Aggregate 전체가 제거되는지
- 유효·만료·변조 공유 토큰과 비공개 필드 노출을 검증하는지
- 고정 HTML 화면이 저장된 이름·시간표·카카오 외부 링크만 표시하는지

### 6.10 추천

- 숙소가 추천 점수 없이 제작 중 지도와 목록에서 사용자 선택으로 확정되는지
- 음식점 점수가 식사 시각 전후 위치에서의 이탈 비용을 사용하는지
- 음식점 후보 목록과 지도 마커가 연동되고 직전·직후 장소, 기준 관광지, 현재 지도 영역 재검색을 지원하는지
- 동률 정렬이 결정적인지
- 후보 없음과 제공자 장애가 구분되는지
- 추천이 사용자의 장소 선택이나 완료 일정을 자동 변경하지 않는지
- 음식 자연어가 지역·관광지 맥락에서 메뉴 1~5개·검색어·이유·대상 관광지를 구조화하고 사용자가 수정·삭제·확정할 수 있는지
- AI 결과가 식당 선택이나 추천 점수 자체를 결정하지 않고 실패 시 직접 메뉴 입력이 가능한지

## 7. 저장 금지 데이터 검증

저장 금지는 단위 테스트 하나로 끝내지 않는다.

- Entity와 migration에 금지 열이 없는지 schema 통합 테스트로 확인한다.
- 생성 Service가 영속 DTO를 만들 때 금지값을 폐기하는지 확인한다.
- Repository 저장 뒤 DB를 다시 조회해 금지 데이터가 복원될 수 없음을 확인한다.
- API 응답 직렬화에서 완료 일정에 금지 필드가 없는지 확인한다.
- 로그 캡처 테스트가 필요하면 원문 대신 필드 부재만 검사한다.

금지 대상은 카카오 좌표·주소·전화번호·카테고리·제공자 장소명·원문 응답·경로선과 AI 사용자 원문·응답 원문이다.

## 8. 브라우저 흐름

핵심 사용자 흐름과 확정된 카카오 데이터 수명 계약에 맞춰 다음 흐름을 자동화한다.

- 회원가입 성공과 validation·중복 이메일 실패
- 로그인 성공과 잘못된 인증 정보 실패
- 비로그인 사용자의 보호 화면 진입 차단
- 인증 만료 시 작성 중 메모리 상태를 폐기하고 로그인 화면으로 안전하게 복귀
- 인증 실패 응답·DOM·브라우저 console에 비밀번호와 JWT가 노출되지 않는지
- 지역 검색 또는 AI 지역 추천
- 이동수단 하나 선택
- 장소 검색, 빈 사용자 표시 이름 작성, 체류 시간 10분 단위 조정
- 추정 일정 확인과 입력 유지
- 완료 요청 성공 후 고정 일정 화면 표시
- 시간 초과·경로 없음·한도 초과·인증 만료 후 안전한 복구
- 완료 화면에서 허용된 텍스트만 수정
- 공유 링크의 읽기 전용 표시
- 새로고침·완료·취소·탭 종료 뒤 작성 좌표가 브라우저 저장소에 남지 않는지

실제 카카오 지도 렌더링은 완료 화면 요구사항이 아니다. 제한된 테스트 키를 사용하는 실제 연결 확인은 자동 회귀 테스트와 분리한다.

## 9. 기능 완료 기준

테스트 관점의 완료 증거는 다음과 같다. 최종 기능 완료 판정은 `docs/10-definition-of-done.md`를 따른다.

1. 핵심 성공과 최소 한 개의 실패 또는 경계 시나리오를 자동화했다.
2. API는 인증, validation, 주요 상태 코드와 응답 계약을 검증했다.
3. DB 변경은 migration 적용, 제약과 rollback을 실제 DB에서 검증했다.
4. 외부 API는 Fake 기반 자동 테스트와 별도 smoke 절차를 분리했다.
5. 저장 금지 데이터와 로그 정책을 확인했다.
6. 관련 테스트와 전체 `./gradlew test`가 통과했다.
7. 화면 변경이면 관련 브라우저 흐름을 확인했다.
8. 좌표 기반 기능이면 카카오 좌표가 한 번의 제작 흐름과 서버 요청에서만 사용되고 즉시 폐기되는지 검증했다.

## 10. 실행 구분

| 명령·환경 | 목적 | 실제 외부 API |
|---|---|---|
| `./gradlew test` | 단위·Service·API 회귀와 Testcontainers MySQL 8.4 기반 DB 회귀 | 호출 금지 |
| 로컬 smoke profile | 인증 설정과 제공자 연결 확인 | 명시적 실행 때만 |
| 브라우저 테스트 profile | 핵심 사용자 흐름 | Fake Client |
| 배포 전 검증 | migration, 보안, 카카오 데이터 수명 계약, 핵심 흐름 | 별도 키와 비용 한도 |

테스트 실행이 환경 문제로 불가능하면 실패로 위장하지 않고 원인, 실행하지 못한 범위와 대체 확인 결과를 기록한다.

DB 테스트가 포함된 `./gradlew test`의 선행 조건은 Docker Engine 사용 가능 상태다. 별도의 로컬 MySQL 계정이나 실제 비밀번호는 선행 조건이 아니다.
